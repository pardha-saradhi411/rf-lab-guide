UE01 QXDM / QCAT / PCAT — Qualcomm UE diagnostic logging UE / Test click to expand ▾
What they are
QXDM (Qualcomm eXtensible Diagnostic Monitor) captures live chipset diagnostic logs from a Qualcomm UE over the USB DIAG port. QCAT analyses the saved logs (.isf/.dlf/.qmdl) offline. PCAT is the packet/performance analysis companion. Together they are the UE-side truth for debugging.
What you can see
Decoded OTA messages (RRC, NAS), L1 serving-cell measurements (RSRP/RSRQ/SINR, PDSCH/PUSCH), MAC/RLC stats, HARQ/BLER, scheduling, and IP throughput — all from the device's perspective, complementing network-side Wireshark.
Workflow
Enable DIAG on the UE → start QXDM logging → reproduce the issue (attach, HO, throughput drop) → save the ISF → open in QCAT to walk the call flow / metrics. This is how you root-cause an attach/HO/throughput problem from the UE end.
Interview Q&A
Q: When would you reach for QXDM over Wireshark?
A: Wireshark shows the network side (S1/NG, GTP, core). QXDM shows what the UE actually saw and did — the RRC/NAS it decoded, its L1 measurements, its HARQ/BLER and scheduling. For a UE-specific failure (bad HO, wrong measurement report, chipset quirk) QXDM/QCAT is the definitive view.
UE02 ADB — Android Debug Bridge for UE control UE / Test click to expand ▾
What it is
A command-line bridge to control an Android UE over USB or TCP — shell access, logs, app install, input injection, radio/data toggles, reboot. The backbone of scripted UE actions in test automation.
Commands you actually use

adb -s <serial> shellshell into a specific UE (multi-UE)
adb logcatstream device logs

svc wifi disableforce cellular

adb rebootreboot the UE (stability loops)
Interview Q&A
Q: How do you drive many UEs at once with ADB?
A: Each device has a unique serial; address it with adb -s . A script iterates serials to start data, launch iperf/dialer, read modem state, and reboot in parallel — the basis of multi-UE orchestration (UE03).
UE03 Appium & Multi-UE Orchestration UE / Test click to expand ▾
Appium
UI automation for mobile apps via the WebDriver protocol — it drives the UE like a real user (dialer, Settings, speed-test apps). Language-agnostic, works across real devices; pairs with ADB for lower-level control.
Multi-UE orchestration
Run many UEs in parallel — each an ADB serial / Appium session — to exercise load, aggregate throughput, and mobility at scale. A controller coordinates attach, starts traffic, and triggers handovers across the fleet, then collects per-UE KPIs. Essential for capacity and stability validation.
Interview Q&A
Q: Why orchestrate multiple UEs instead of one?
A: A single UE can't load a cell or expose scheduler fairness, capacity limits, or multi-user interference. Running a fleet in parallel reproduces real cell load, aggregate throughput, and mobility churn — the conditions where most field defects appear.
UE04 Robot Framework — keyword-driven test automation UE / Test click to expand ▾
What it is
A Python-based, keyword-driven automation framework with human-readable .robot test cases. Libraries (AppiumLibrary, SSHLibrary, custom Python) let non-coders read/write tests. Used for LTE/5G bring-up, throughput, endurance and regression suites.
Structure & output
Sections: Settings / Variables / Test Cases / Keywords, with tags for selection. Produces log.html + report.html with pass/fail and step timing.
vs pytest
ruauto/RCT uses pytest (code-first, see CLI01/FWK1); many UE/system teams use Robot (keyword-first, more readable for mixed-skill teams). Same goal — different style; both drive the same UEs and instruments.
Interview Q&A
Q: Robot Framework vs pytest — when each?
A: pytest is code-first and great for engineers writing rich Python logic (the RCT conformance suites). Robot is keyword-driven and reads almost like English, so it suits large mixed-skill test teams and reusable keyword libraries for UE/system regression. Both can call the same device/instrument libraries.
UE05 TM500 — network tester / UE emulator UE / Test click to expand ▾
What it is
The Viavi/Aeroflex TM500 is an RF UE emulator that emulates many controlled UEs to load-test an eNB/gNB — capacity, peak throughput, scheduler behaviour, mobility. It is a deterministic test UE, not a commercial chipset.
Why use it
Scriptable, repeatable, and scales to hundreds of UEs — perfect for maximum-throughput, multi-UE and base-station RF/protocol validation where you need controlled, reproducible load rather than a phone.
Interview Q&A
Q: TM500 vs a commercial UE?
A: TM500 gives deterministic, scriptable, high-count load for base-station capacity/throughput/mobility testing. A commercial UE gives real chipset behaviour (IMS/VoLTE quirks, band-combo support) for interoperability. You use TM500 for scale/repeatability and real UEs for realism (UE08).
UE06 Amarisoft — software Callbox (eNB/gNB + core + UE sim) UE / Test click to expand ▾
What it is
SDR-based software LTE/5G eNB/gNB + EPC/5GC + UE simulator — a full network-in-a-box (Callbox) and UE-sim. Attach a real UE to the Amarisoft cell, or simulate UEs against a real gNB.
Why it's useful
Fully scriptable (remote API), rich logging, built-in IMS for VoLTE, and cheap/flexible vs full commercial gear. Great for feature validation, protocol testing, and interoperability in the lab.
Interview Q&A
Q: Where does Amarisoft fit in a validation lab?
A: It provides a controllable reference network or reference UE. Point a real UE at the Amarisoft cell to isolate UE behaviour, or run Amarisoft UE-sim against your gNB to isolate the base station — a cheap, scriptable way to bisect where a problem lives.
UE07 Dingli & drive-test tools UE / Test click to expand ▾
What it is
Dingli (Pilot Pioneer / Navigator) is a drive-test & network-optimisation tool: a UE + GPS logging RSRP/RSRQ/SINR, throughput and handovers along a route, with post-processing and coverage heat-maps. Same family as XCAL/TEMS (see PT18).
Used for
Field coverage, mobility and KPI validation — confirming that lab RF results (your RCT) hold up in real deployment: dominance, pilot pollution, HO success along a drive route.
Interview Q&A
Q: What does a drive test add over lab RCT?
A: Lab RCT proves the radio meets spec in controlled conditions; a drive test proves coverage, mobility and KPIs in the real RF environment — multipath, interference, real UE distribution — which the lab cannot fully reproduce.
UE08 Commercial UEs & modules — OnePlus, Samsung, Telit, COMPAL UE / Test click to expand ▾
Why real devices
Emulators miss chipset-specific behaviour. Real UEs — OnePlus/Samsung (Qualcomm/Exynos), Telit (IoT modules), COMPAL (ODM) — expose real band/CA-combo support, VoLTE/IMS behaviour, UE capability and vendor quirks.
What you check
UECapabilityInformation (supported bands, CA band-combos, category, MIMO layers), VoLTE/IMS registration, real throughput, and how each chipset interprets 3GPP — the essence of interoperability (UE11).
Interview Q&A
Q: Why validate with commercial UEs if you have a TM500?
A: Because operators' subscribers use commercial phones. Only real chipsets reveal IMS/VoLTE behaviour, band-combo negotiation, and vendor-specific interpretations of 3GPP that a deterministic emulator will not — which is exactly what breaks in the field.
UE09 Throughput & KPI testing — iperf, TCP/UDP UL/DL UE / Test click to expand ▾
How throughput is measured
iperf/iperf3 generates UL/DL TCP and UDP traffic between a server and the UE; you record peak throughput (e.g. LTE-A CA 1.4 Gbps DL / 250 Mbps UL), latency, jitter, packet loss.
TCP vs UDP
UDP pushes a fixed rate — measures raw PHY/MAC capacity (and loss). TCP is window/RTT-limited and reacts to loss — measures realistic user throughput. Report both; a gap points to latency/loss issues.
The KPI chain
Throughput is the end of a chain: RF (SINR) → CQI → MCS → scheduled bits → throughput (see L38). A bad ACLR/EVM upstream shows up here as low DL rate.
Interview Q&A
Q: Why measure both TCP and UDP throughput?
A: UDP at a forced rate reveals the true PHY/MAC capacity and packet loss; TCP reveals what a real application achieves after congestion control and RTT. If UDP is high but TCP is low, the radio is fine and the problem is latency/loss/buffering.
UE10 Endurance / Stability / Stress testing UE / Test click to expand ▾
What it is
Long-duration and repeated-action tests that surface the defects short runs miss: 8–72 hr attach/detach and mixed-traffic soak, and reboot loops (100+ RU reboots). Targets memory leaks, resource exhaustion, sync drift, and rare race conditions.
What you track & deliver
Success rate, drop rate, recovery time, and resource trends over time; then a developer-ready RCA correlating radio/baseband/management/automation logs. (Related: the self-healing traffic watchdog.)
Interview Q&A
Q: Why run 72-hour and reboot-loop tests if the feature already passes functionally?
A: Functional tests catch logic bugs; endurance/stress catch time-and-repetition bugs — memory leaks, handle exhaustion, clock/sync drift, and one-in-hundreds race conditions on reboot. Those are exactly the failures that take down a live network, so they must be found before release.
UE11 Interoperability (IOT) testing UE / Test click to expand ▾
What it is
Verifying the RAN/core works correctly with multiple UE vendors/chipsets (and network vendors) — a matrix of UE × band × feature. Catches vendor-specific interpretations of 3GPP that conformance alone misses.
vs conformance
Conformance = does the device/BS meet the 3GPP spec (SPEC01-03). Interoperability = do independently-built devices actually work together in the real world. Tier-1 operators (DTAG/VMO2-style acceptance) require both.
Interview Q&A
Q: Conformance vs interoperability — why both?
A: Two vendors can each pass conformance yet still fail together because the spec allows options or is read differently. Conformance proves spec compliance in isolation; interoperability proves the RAN, core and real UEs actually interwork — which is what the operator ultimately buys.

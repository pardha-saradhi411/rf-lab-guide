1 · Qualcomm (fresher) — the RF transceiver chain · result: rejected — this is why
Asked: Trace the signal end-to-end through the radio — digital → analog → gain/attenuator → modulation → power amplifier → up-conversion → antenna, and on receive, down-conversion → LNA.
Model answer. TX: digital baseband → DAC (digital→analog) → baseband/IF filter → variable gain / attenuator (set output level) → I/Q modulator → up-conversion mixer (baseband/IF × LO → RF) → driver + Power Amplifier (adds the output power, last active stage) → duplexer/band filter → antenna. RX: antenna → duplexer/filter → LNA (first stage — it sets the system Noise Figure) → down-conversion mixer (RF × LO → IF/baseband) → filter → variable gain (AGC) → ADC (analog→digital) → digital baseband.
Gap to close: know the two boundaries cold — DAC/ADC is the digital↔analog line; PA is the last active TX stage before the antenna (why: it delivers the transmit power) and LNA is the first RX stage after the antenna (why: a low-noise first stage dominates the cascade NF — Friis). Also name the LO/mixer for up/down conversion. See the full chain on Foundation.
2 · Samsung — LTE Attach, UE identities & authentication
Asked: Walk the basic Attach. What are the UE identities and how many digits? What are the authentication request/response? What does AUSF do — comparing the unique ID from the UE? IMSI, IMEISV; and the PDU session / AMF flow.
Model answer. Attach (4G): RRC setup → Attach Request (IMSI or GUTI) → Authentication (EPS-AKA) → NAS Security (integrity + ciphering) → ESM default-bearer / PDN connectivity → Attach Accept (new GUTI) → Attach Complete.
UE identities: IMSI = 15 digits (MCC 3 + MNC 2–3 + MSIN); IMEI = 15; IMEISV = 16 (IMEI + 2-digit software version); GUTI / S-TMSI = temporary identities used on air after first attach (privacy).
Authentication (EPS-AKA): MME fetches auth vectors from HSS (RAND, AUTN, XRES, KASME). MME sends RAND + AUTN to UE (auth request); the USIM verifies AUTN and computes RES (auth response); MME checks RES == XRES → authenticated.
4G ↔ 5G map (say this to show range): MME→AMF, HSS→AUSF + UDM/ARPF (AUSF is the 5G authentication server), EPS bearer / PDN → PDU session, IMSI → SUPI carried encrypted as SUCI.
Decode / gap: "IMI / IMIASV" = IMSI / IMEISV; the challenge value is RAND; the compare is RES vs XRES. AUSF is 5G — in 4G it's the MME+HSS doing AKA. Don't mix the two core generations mid-answer. See Protocol.
3 · Samsung — which SIB carries the reselection parameters? · result: rejected — this is why
Asked: In which System Information message are the cell-reselection parameters carried? (I answered "SIB2 — radio configuration" and was rejected.)
Model answer (LTE): SIB1 = cell access + PLMN + SIB scheduling. SIB2 = common radio resource config (RACH, PRACH, PUCCH/PUSCH, UL power control, timers) + barring — not reselection. SIB3 = serving-cell + intra-frequency reselection common (q-Hyst, s-IntraSearch, s-NonIntraSearch, threshServing). SIB4 = intra-frequency neighbour list (+ blacklist). SIB5 = inter-frequency carriers + reselection. SIB6/7/8 = UTRAN / GERAN / CDMA2000. So reselection lives in SIB3 (params), SIB4 (intra neighbours), SIB5 (inter-freq).
The trap that got me: NR renumbers them — in 5G NR, SIB2 = reselection common, SIB3 = intra-freq, SIB4 = inter-freq. Mixing LTE and NR numbering is almost certainly what sank the answer. Memorise both columns: LTE 3/4/5, NR 2/3/4.
4 · RAN role (2 rounds) — flows, IEs, X2 handover, throughput, VoLTE
Asked: All basic flows with the IEs of each; handover (X2); throughput-issue debug; VoLTE call. The two misses: (a) how does the source eNB know which target eNB to send the HO Request to? (b) what vital info is exchanged in the X2 HO Request / Response?
(a) Target selection: the UE's A3 measurement report carries the target PCI (and, if configured, its ECGI read from the target's SIB1). The source resolves PCI → target eNB + cell via its Neighbour Relation Table / ANR, which corresponds to an X2 link already set up beforehand (X2 Setup Request/Response earlier exchanged each eNB's served-cell info: PCI, ECGI, TAC, PLMN, EARFCN). The HO Request then goes over that X2AP association.
(b) X2AP HANDOVER REQUEST (source→target): target ECGI, GUMMEI, UE-AMBR, the E-RAB list (each with E-RAB ID, QoS = QCI/ARP/GBR-MBR, S-GW UL GTP-TEID), UE security capabilities + KeNB* + NCC, and the Source-eNB→Target-eNB transparent container (the UE's RRC context / meas config / C-RNTI). HANDOVER REQUEST ACKNOWLEDGE (target→source): admitted E-RABs (+ DL/UL forwarding TEIDs) and the Target→Source transparent container = the RRCConnectionReconfiguration with mobilityControlInfo (target PCI/EARFCN, new C-RNTI, dedicated RACH preamble for contention-free access, T304).
Throughput debug (the checklist): RSRP/RSRQ/SINR/CQI → MCS & rank (MIMO layers) → BLER/HARQ retx → RB allocation/scheduler → CA (all CCs active?) → TM mode → UL/DL & TDD split → transport/backhaul (S1/X2, GTP) → UE category / TCP window / MTU → interference / PCI collision.
VoLTE: default bearer QCI 5 to the IMS APN (SIP signalling) → IMS registration (P-/S-CSCF, IMS-AKA) → SIP INVITE + SDP → dedicated bearer QCI 1 (GBR conversational voice, RTP) → media flows; SRVCC hands voice to 3G/2G if LTE coverage drops.
Gap to close: the two transparent containers are the crux — source→target carries the old RRC/UE context, target→source carries the new RRCReconfig (with the dedicated preamble & new C-RNTI). And X2 must pre-exist (set up + ANR) before any HO. See the Handover — and Call Flow — cards via the Protocol filter.
5 · Current company — the automation honesty question · result: accepted
Asked: Same domain flows, plus automation. I said honestly: "I can read and modify code and write a little, but I haven't worked on automation." They were fine with it and made the offer.
Lesson & the upgraded answer: honesty + willingness to learn beat a bluff — a senior interviewer can tell in two follow-ups. But you can now go one better: "I was light on automation then; since, I've built pytest and Robot-Framework patterns, SCPI/pyvisa instrument control, and traced a full RCT feature (RSSI accuracy) in code." That turns the old weakness into evidence of growth. See the Automation tab (AUTO01–AUTO08).

PD01 Debug — PDCP (ciphering mismatch, ROHC context, SN wrap) Protocol Debug click to expand +

PDCP = ciphering, integrity, header compression (ROHC), SN + reordering · top of the L2 stack, just under RRC/IP

Why it exists / what breaks
PDCP secures and orders each bearer's PDUs. Three classic failure families: ciphering/integrity mismatch (wrong key or algorithm → garbage after decryption / MAC-I failure → the UE can't decode anything), ROHC context desync (compressor/decompressor disagree → headers can't be rebuilt → packets dropped), and SN wrap / HFN desync (the sequence number rolls over and the two ends disagree on the hyper-frame number → COUNT mismatch → deciphering fails).
Where each failure shows up
COUNT = HFN : PDCP-SN            (input to ciphering)
cipher mismatch : SecurityModeComplete ok, then user-plane
                  fails -> decode errors, no throughput
integrity fail  : MAC-I check fails on SRB -> RRC msg discarded
ROHC desync     : IR/IR-DYN not received -> decompress fail ->
                  drops until context refresh (U/O/R mode)
SN/HFN desync   : after long gap or lost PDUs -> COUNT diverges
Key parameters
ParamMeaning
pdcp-SN-Size12 or 18 bit (5G also 7-bit for SRB); sets wrap point
cipheringAlgorithmEEA0/NEA0 (null), 128-EEA1/2/3 (SNOW3G/AES/ZUC)
integrityProtAlgorithmEIA/NIA; 5G can also integrity-protect DRBs
t-Reorderingreordering timer; expiry delivers with gaps
Debug checklist
Decode fails right after SecurityModeCommand → algorithm/key mismatch (KgNB/KeNB derivation, count-of-security) → verify SMC IEs match on both ends. Integrity fail on SRB → wrong KRRCint or replayed COUNT. Throughput dies after long idle/large transfer → SN wrap / HFN desync → look at PDCP COUNT. Sporadic packet loss → ROHC context lost → force IR refresh / disable ROHC to isolate. Gaps delivered → t-Reordering expiring due to lower-layer loss.
Interview Q&A
Q: What is COUNT and why does it matter? COUNT = HFN ‖ PDCP-SN; it's the ciphering/integrity input. If the two ends disagree on HFN (SN wrap), the keystream diverges and deciphering fails silently.
Q: How do you isolate a ROHC issue quickly? Disable ROHC (or force IR mode) — if the drops stop, it's compression context, not ciphering.
Q (PW): During a long soak, throughput collapses on one bearer only — where do you look? PDCP COUNT/HFN on that DRB for SN wrap desync, before blaming RF.
PD02 Debug — RLC (AM stall, STATUS PDU, window stuck) Protocol Debug click to expand +

RLC = segmentation + ARQ · AM (acknowledged, retransmits), UM (unacknowledged), TM · classic bug = AM window stall

Why it exists / what breaks
RLC-AM guarantees delivery via ARQ: the receiver sends STATUS PDUs (ACK/NACK), the transmitter retransmits NACKed segments. The classic failure is a window stall: if a PDU at the low edge of the window is never acknowledged, the transmit window can't advance and everything behind it blocks → throughput drops to zero even with good RF. Causes: lost STATUS PDUs, t-PollRetransmit not firing, or t-Reassembly expiry mishandling.
AM ARQ mechanism
TX  → RX :  AMD PDU (SN), Poll bit set every pollPDU/pollByte
TX          start t-PollRetransmit
RX  → TX :  STATUS PDU (ACK_SN, NACK list)
TX          advance TX window; retransmit NACKed SNs
stall:  low-edge SN never ACKed -> window frozen
        (VT(A) stuck) -> maxRetxThreshold hit -> RLF
RX side: t-Reassembly expiry -> declare missing, send STATUS
Key parameters
ParamMeaning
t-PollRetransmitre-poll if no STATUS received → recovers lost polls
t-ReassemblyRX timer to wait for missing segments
maxRetxThresholdretx limit; reaching it declares RLF → re-establish
pollPDU / pollBytehow often the Poll bit is set to solicit STATUS
Debug checklist
Throughput freezes, RF is fine → AM window stall → check VT(A)/VT(S) not advancing, STATUS PDUs arriving. Repeated retransmits then drop → maxRetxThreshold hit → RLF (root cause is the persistent NACK, often UL STATUS loss). UM: missing packets, no recovery → expected (no ARQ) → check if bearer should be AM. STATUS storm → t-Reassembly too short. One-way stall → poll not being set (pollPDU too high on a low-rate bearer).
Interview Q&A
Q: Describe an RLC-AM window stall. The lowest un-ACKed SN (VT(A)) never gets acknowledged, so the transmit window can't slide; new PDUs beyond the window can't be sent and throughput halts despite good radio.
Q: What eventually breaks a stall? t-PollRetransmit re-polls; if still unresolved, maxRetxThreshold triggers RLF and RLC re-establishment.
Q (PW): Zero DL throughput but PDCCH/PDSCH look scheduled — RLC or MAC? Check RLC first: an AM stall or missing STATUS blocks delivery even when MAC is granting resources.
PD03 Debug — MAC (HARQ mismatch, NDI errors, BSR/SR) Protocol Debug click to expand +

MAC = scheduling, HARQ, multiplexing, random access · fastest layer; bugs show as retransmission storms or UL starvation

Why it exists / what breaks
MAC runs HARQ (fast L1 retransmit with soft combining) and manages UL grants. Three common bugs: HARQ process mismatch (TX and RX disagree on which of the 8/16 processes a TB belongs to → wrong soft-buffer combining → CRC fails), NDI errors (New Data Indicator toggles wrongly → a retransmission is treated as new data, or vice-versa → corruption), and the SR/BSR flow breaking (UE has UL data but can't tell the gNB → no grant → UL starvation).
UL grant request flow (SR → BSR → grant)
UE has UL data, no grant:
UE  → gNB :  SR on PUCCH  (Scheduling Request)
gNB → UE  :  small UL grant (PDCCH)
UE  → gNB :  BSR MAC CE (how much data, per LCG)
gNB → UE  :  right-sized UL grant
UE  → gNB :  PUSCH data
no SR resource / sr-ProhibitTimer stuck -> RACH for UL access
HARQ:  NDI toggled = new TB ; NDI same = retransmission (combine)
Key parameters
ParamMeaning
NDINew Data Indicator — toggled = new TB, unchanged = retx
HARQ process ID8 (FDD LTE) / up to 16 (NR) parallel stop-and-wait
BSR / LCGBuffer Status Report per Logical Channel Group
sr-ProhibitTimer / dsr-TransMaxlimit SR frequency; exhaustion → RACH fallback
Debug checklist
High HARQ BLER / re-tx storm → NDI handling or process-ID mapping → check soft-combining is on the right process. UL data but no PUSCH → SR not sent (no PUCCH-SR resource) or BSR not triggering → UL starvation. Residual BLER after HARQ → hand-off to RLC ARQ; if that also fails → link budget. UE keeps doing RACH for UL → SR resources exhausted (dsr-TransMax) → check PUCCH config. DL CRC fail only on retx → wrong redundancy version / process combine.
Interview Q&A
Q: How does the UE tell the gNB it has UL data with no grant? Sends an SR on PUCCH; the gNB gives a small grant, the UE sends a BSR, then gets a right-sized grant.
Q: HARQ vs RLC ARQ? HARQ is fast, physical-layer, with soft combining (µs–ms); RLC ARQ is the slower L2 safety net for what HARQ can't recover.
Q (PW): UL throughput near zero but DL is fine — first MAC check? SR/BSR flow — confirm the UE has PUCCH-SR resources and BSRs are being sent/served before suspecting UL RF.
PD04 Debug — RRC (connection failures, T300/T310/T311) Protocol Debug click to expand +

RRC = the control-plane state machine (IDLE/CONNECTED/INACTIVE) · failures live in a handful of supervision timers

Why it exists / what breaks
RRC sets up/maintains the connection and configures every lower layer. Most "call won't connect" or "call drops" issues map to a timer: T300 (connection setup), T310 (radio problem while connected), T311 (re-establishment search). Knowing which timer fired tells you where it broke — setup vs mid-call vs recovery.
Setup + RLF/re-establishment timeline
Setup:
UE → gNB : RRCSetupRequest   (start T300)
gNB→ UE  : RRCSetup
UE → gNB : RRCSetupComplete   (stop T300)  -- T300 expiry = setup fail
Radio problem while connected:
L1 N310 consecutive "out-of-sync" -> start T310
  T310 running + N311 "in-sync" -> recover (stop T310)
  T310 expiry -> Radio Link Failure (RLF)
RLF -> start T311, search a suitable cell
  found -> RRCReestablishmentRequest  (stop T311)
  T311 expiry -> go to IDLE (call dropped)
Key timers/counters
TimerMeaning / expiry effect
T300RRC setup supervision; expiry = setup failure → retry/IDLE
T310started on N310 out-of-sync; expiry = RLF
T311re-establishment cell search; expiry = drop to IDLE
N310 / N311consecutive out-of-sync / in-sync counts from L1
Debug checklist
T300 expiry → gNB never sent RRCSetup (admission/overload) or Msg3/4 lost → check RACH & PRACH. T310 expiry (RLF mid-call) → coverage drop / interference → N310 out-of-sync from bad DL SINR. T311 expiry → no suitable cell for re-establishment → neighbor/coverage gap. Frequent re-establishment → tune N310/T310 vs real mobility. SetupComplete never seen → Msg5 lost or NAS piggyback issue.
Interview Q&A
Q: A call drops mid-session — which timer and what does it mean? T310 expired: L1 reported N310 consecutive out-of-sync (bad DL), recovery via N311 in-sync didn't happen → RLF.
Q: What's the difference between T310 and T311? T310 supervises radio problems while connected; T311 supervises the search for a cell to re-establish after RLF.
Q (PW): Attach fails and you see T300 expiry — RF or core? Likely access side (PRACH/Msg2-4) or gNB admission, not NAS; confirm RACH success and RRCSetup was actually sent before escalating to core.
PD05 Debug — NAS (EMM cause codes, attach reject, TAU failure) Protocol Debug click to expand +

NAS = UE ↔ core (MME/AMF) signaling, transparent to the RAN · EMM/MM cause codes tell you exactly why the core said no

Why it exists / what breaks
NAS handles registration (Attach / 5G Registration), mobility (TAU / Registration Update), and session/bearer management — carried inside RRC but terminated at the MME/AMF. When it fails, the core returns an EMM/5GMM cause code that pinpoints the reason (subscription, auth, region), so NAS debug is mostly "read the cause code, then check the matching subscriber/core config."
Attach / registration flow
UE → MME/AMF :  Attach/Registration Request (IMSI/GUTI)
MME → UE     :  Authentication Request / Response (AKA)
MME → UE     :  Security Mode Command / Complete (NAS cipher+integ)
MME → UE     :  Attach Accept / Registration Accept (+ default bearer)
   OR  Attach Reject / Registration Reject (EMM cause) -> fail
TAU/Reg-Update: on TA change -> Request -> Accept/Reject(cause)
Common EMM cause codes
CauseMeaning
#3 Illegal UE / #6 Illegal MEauth failed / IMEI blocked
#7 EPS services not allowedsubscription has no LTE/5G
#11 PLMN not allowedroaming/PLMN restriction
#12/#13 TA / roaming not allowedtracking-area / region barred
#15 No suitable cells in TATA config / cell selection issue
Debug checklist
Attach Reject #3/#6 → auth (K/OPc mismatch in HSS/UDM, SIM provisioning). #7/#11 → subscription/PLMN in HSS. #12/#13/#15 → TAI list / broadcast TAC vs core config. Auth Failure from UE → SQN out of sync → resync (AUTS). TAU reject looping → TAI mismatch between broadcast SIB1 and core. Reject with no cause visible → decode the NAS PDU in the trace, not just the RRC container.
Interview Q&A
Q: Is NAS visible to the eNB/gNB? No — NAS is transparent to the RAN; it rides inside RRC and terminates at the MME/AMF, so cause codes come from the core.
Q: UE attaches on band A but rejects on band B with #15 — why? The TAC broadcast on band B's cell isn't in the UE's allowed TAI list / core TA config, not an RF problem.
Q (PW): On the bench, attach fails with EMM #7 — where do you look? Subscriber profile in the core (EPS/5G subscription), not the RU — the RF chain already carried the NAS message end to end.

RLF01 Radio Link Failure — N310/T310/N311, re-establishment, T311 RLF click to expand +
Why it matters
RLF is the connection breaking while connected (bad radio), as opposed to a setup failure. What happens next (recover vs drop) is a tight timer/counter dance — and the RLF report is gold for root-causing coverage/interference.
Detection & recovery sequence
L1: RSRP/SINR below Q_out (~ -8 dB) or PDCCH BLER high -> "out-of-sync" indications N310 consecutive out-of-sync -> start T310 in-sync >= Q_in (~ -6 dB) x N311 -> stop T310 (recovered) T310 expiry -> RADIO LINK FAILURE RLF -> start T311, search a suitable cell found -> RRCConnectionReestablishmentRequest T311 expiry / no cell -> RRC_IDLE (call dropped)
Common causes & debug
Coverage hole (RSRP collapse) · interference (SINR down, RSRP ok) · fast fading/high speed · no suitable neighbour for re-establishment. Debug: check N310/T310 config vs real mobility (too sensitive = false RLF), neighbour list, and whether re-establishment is rejected (target has no prepared context → X2/Xn issue).
RLF report
The UE stores the RLF report (failed cell ID, measurements, timing) for ~48 h — used by SON/ANR and MDT to auto-tune mobility.
Interview Q&A
Q: T310 vs T311? T310 supervises the radio problem while connected; T311 supervises the search for a cell to re-establish after RLF is declared.
Q: Frequent RLF with decent RSRP — first check? SINR/interference (RSRP can be fine while SINR is low), and whether N310/T310 are set too aggressively.

PDCAP Reading a Control-Plane Capture — identify protocol & procedure (S1AP/NGAP/X2AP/F1AP) Debug click to expand ▾
In plain English
Open a control-plane pcap and the first two questions are: which interface/protocol is this, and which procedures are happening? Even without a full decoder, SCTP tells you the protocol by port & PPID, and one byte of each message tells you the procedure — enough to characterise any S1AP/NGAP/X2AP/F1AP trace.
How it works
Control plane runs over SCTP (reliable, multi-stream). Identify the interface three ways:
• SCTP port: S1AP 36412 · NGAP 38412 · X2AP 36422 · XnAP 38422 · F1AP 38472 · E1AP 38462 · E2AP 37464.
• SCTP DATA chunk PPID (definitive): S1AP 18 · NGAP 60 · X2AP 27 · XnAP 61 · F1AP 62 · E1AP 64.
• Procedure: each application PDU starts with a CHOICE — initiatingMessage / successfulOutcome / unsuccessfulOutcome — then the procedureCode. So one byte ≈ init/ok/fail and the next = the procedure. S1AP examples: 10=Paging, 12=initialUEMessage, 9=InitialContextSetup, 11/13=DL/UL NAS, 5=E-RABSetup, 23=UEContextRelease, 17=S1Setup, 0=HandoverPrep, 3=PathSwitchReq.
What a healthy trace looks like: the association opens with S1Setup (init→success); steady Paging; per call initialUEMessage → InitialContextSetup(success) → NAS transport → E-RABSetup → UEContextRelease. Balanced init/success counts = procedures completing.
Red flags: frequent Reset, an S1Setup unsuccessfulOutcome (association won't come up), or InitialContextSetup with no matching success. Tip: 127.0.0.1 loopback = internal components — filter to the real node IPs; use SCTP stream/PPID to separate interleaved procedures.
Interview Q&A
Q: You have a control-plane pcap but limited decode — how do you tell the interface and the procedures?
A: It's SCTP: the port identifies the interface (S1AP 36412 / NGAP 38412 / F1AP 38472 / X2AP 36422 / XnAP 38422 / E1AP 38462) and the SCTP DATA PPID confirms it (S1AP 18 / NGAP 60 / F1AP 62…). Each application PDU begins with initiating/successful/unsuccessful + a procedureCode, so you can tally procedures (Paging, InitialContextSetup, S1Setup, handover) even without full ASN.1 decode.
Q: What in an S1AP/NGAP trace hints at instability?
A: Frequent Reset procedures, an S1Setup/NGSetup unsuccessfulOutcome (the eNB/gNB↔core association won't establish), or InitialContextSetup with unsuccessfulOutcome / no matching successfulOutcome. Healthy traces show a single Setup success at the start and balanced initiating↔successful counts thereafter.

Level 2 — what each layer can tell you (and the log to open)
RU / fronthaul: carrier state, alarms, PTP state, U-plane RX/TX counters and timing-window drops. If the radio is not on air, nothing above matters.
PHY: CQI, RI, PMI, SINR, BLER, PRACH detections, UL RSSI. The per-UE radio report (CQI 14–15, RI 4, SNR 30 dB) tells you whether the link is good. If it is good and throughput is bad, look higher.
MAC: the per-TTI log (allocated PRBs, MCS, HARQ ACK/NACK/DTX), BSR/SR, TA. NACK means the UE decoded the grant but not the data. DTX means no feedback at all: the UE missed the PDCCH, or the eNB missed the PUCCH. Different causes.
RLC: AM retransmissions, STATUS PDUs, a window stall (PD02). A stuck window caps throughput while the radio looks perfect.
PDCP: ciphering/integrity failures (mismatched keys after HO), ROHC context loss, discard timer drops (PD01).
RRC/NAS: the message sequence and cause codes (PD04/PD05, TMR01). UE-side traces (e.g. QXDM) and eNB/gNB logs show both ends.
Between nodes: S1AP/NGAP/X2AP/F1AP in a pcap (PDCAP): Setup success, InitialContextSetup outcome, HO procedures, errors. GTP-U counters and end markers for the user plane.
Level 3 — method: bottom-up vs top-down, and "compare the layers"
Nothing works (no cell, no attach): go bottom-up. RU on air? → PHY broadcasting and PRACH detected? → RRC setup complete? → NAS accepted? → bearer and GTP-U up? The first "no" is your layer.
Works, but poorly (throughput, drops): go top-down by comparing the same quantity across layers. Throughput at eGTP (offered) vs PDCP (delivered) vs MAC (scheduled) (LF20). Where the drop first appears is where to dig. For example, eGTP 177, MAC 169 and PDCP 167 is normal. A PDCP far below MAC suggests PDCP/RLC issues, and MAC far below eGTP with good CQI suggests scheduling or configuration limits.
Always correlate time: line up UE logs, eNB logs, pcaps and KPI counters on one timeline (mind UTC vs local time). Most "mysterious" failures become obvious when two sources are put side by side.
Always rule out the harness: expired automation sessions, a dead iPerf client or a CLI race can fake a RAN failure (AUTO09, CM16).

Interview Q&A
Q: A UE cannot attach. Which order do you check things in?
A: Bottom-up: is the cell on air (RU carriers ACTIVE, PTP locked)? Is the UE camping (SIBs, PLMN, RSRP vs q-RxLevMin)? Is PRACH detected and Msg2/Msg4 sent? Does RRC setup complete? What does NAS say (EMM/5GMM cause)? Did InitialContextSetup succeed and the bearer and GTP-U come up? The first failing step is the layer to debug.
Q: What is the difference between HARQ NACK and DTX?
A: NACK: the UE decoded the scheduling grant (PDCCH) but failed to decode the data, and said so. DTX: no feedback was received at all, because the UE missed the PDCCH or the eNB failed to detect the PUCCH/feedback. High DTX points at control-channel or UL-detection problems, and high NACK at data-channel link adaptation or SINR.
Q: Throughput is low but the radio report says CQI 15, RI 4, BLER 0. Where do you look?
A: Above the PHY: MAC scheduling and allocated PRBs (other UEs? PRB caps?), RLC window stalls or retransmissions, PDCP discards, and transport/TCP limits (RTT, window, server). Compare throughput at eGTP, MAC and PDCP to see where the drop starts.
Q: Why correlate logs from several sources on one timeline?
A: Because each source sees only its own layer. UE traces, eNB logs, pcaps and KPI counters together reveal cause and effect (e.g. an RU fault seconds before a NETCONF error). Check the clocks and time zones first (UTC vs local), or the correlation will mislead.
PDX2 X2 Handover in a Capture — what you see on S1 vs X2, reading two real eNB captures (X2 over IPv6 + Path Switch), filters, and what a missing message means Debug click to expand ▾
In plain English
An X2 handover is negotiated directly between the two eNBs over X2. The core (MME) only hears about it at the end, when the target eNB asks it to move the data path (Path Switch). So what you see in a capture depends on where you captured. On the S1 side a successful X2 HO is a single request/response pair. To see the handover itself you need the X2 link. This card builds that intuition from two real eNB captures, and also shows how easy it is to miss X2 completely if you filter the wrong way.

Correction and lesson — "no X2AP" was a filtering mistake
An earlier version of this card said these captures held no X2AP at all and that X2 "was not on the captured interfaces". That was wrong. The first check looked only at IPv4 SCTP (an IPv4-only filter and a Python parser that only walked IPv4 headers). The X2 association was on IPv6, so it was silently skipped.
• Filter on the payload protocol, not on the IP version: sctp.data_payload_proto_id == 27 (X2AP) or simply x2ap. Both match IPv4 and IPv6.
• Do not start with ip or ip.addr == … when you are hunting for a protocol. In Wireshark ip means IPv4 only; IPv6 is ipv6. Use ip || ipv6 if you need both.
• X2 and S1 often use different transport networks (different VLAN, IP version or interface). An empty result means "not in this filter", not "not in the capture". Run Statistics → Protocol Hierarchy (tshark -q -z io,phs) first and look for SCTP under both IPv4 and IPv6.
• If you write your own parser, handle Linux-cooked (SLL) framing, both ethertypes (0x0800 IPv4 and 0x86DD IPv6) and bundled SCTP DATA chunks (one packet can carry two X2AP messages).
Level 2 — how to read an X2 HO from S1 only
• PathSwitchRequest from eNB-B means a UE has just completed an X2 HO into eNB-B, which now asks the MME to point the S1-U bearer at it.
• PathSwitchRequestAcknowledge means the MME/SGW moved the path, so the HO is complete from the core's view. PathSwitchRequestFailure means the core refused (e.g. bearer or security problem), and the UE is usually released.
• UECapabilityInfoIndication right after means the target reports the UE's capabilities to the MME.
• No Path Switch after an HO attempt means the HO did not complete (target admission reject, UE failed RACH on the target, cancel, or RLF). You need X2 or RRC traces to know which.
• An S1-based HO looks completely different on S1: HandoverRequired → HandoverRequest/Ack → HandoverCommand → eNB/MME Status Transfer → HandoverNotify (PT08/HO04). If you see those, it was not an X2 HO, for example because X2 was not available or the neighbour was blacklisted (LF10).

Level 4 — measuring and debugging an X2 HO
• Interruption time is measured at the UE/RRC level: from RRC Reconfiguration (with mobilityControlInfo) on the source to RRC Reconfiguration Complete on the target (tens of ms is typical in LTE). Path Switch latency is a separate core-side number.
• Data loss check: SN Status Transfer carries PDCP sequence numbers, so the target can continue without loss. Forwarded DL data on X2-U plus the End Marker tells the target when the old path is drained.
• Failure signatures: HandoverPreparationFailure (target refused: admission or resources), RLF on the target shortly after the HO (too-early/wrong-cell, LF11), Path Switch failure (core), repeated ping-pong HOs (A3 offset/TTT tuning).
• Automation tip: a Python pass over the pcap that reads SCTP DATA chunks (over IPv4 and IPv6, every bundled chunk), takes the PPID and the first two bytes of the APER payload (PDU type + procedure code) and prints a timeline is enough to classify procedures quickly when a full decoder is not available.
Interview Q&A
Q: In an S1-side capture, how do you recognise a successful X2 handover?
A: By S1AP PathSwitchRequest from the target eNB followed by PathSwitchRequestAcknowledge from the MME. The handover preparation itself (HandoverRequest/Ack, SN Status Transfer, UE Context Release) happens on X2, so you only see it if the capture includes the X2 transport.
Q: You see HO attempts in the eNB logs but no Path Switch in the S1 capture. What happened?
A: The handover did not complete from the core's view. The target rejected admission, the UE failed to access the target (RACH), the HO was cancelled, or the UE dropped. Look at X2AP (HandoverPreparationFailure/Cancel) and RRC traces to pin it down.
Q: How does an S1 handover look different on S1 from an X2 handover?
A: S1 HO uses S1AP HandoverRequired (source → MME), HandoverRequest/Ack (MME ↔ target), HandoverCommand (MME → source), eNB/MME Status Transfer and HandoverNotify. X2 HO shows only Path Switch on S1.
Q: What is the GTP-U End Marker for?
A: After the path switch the SGW sends an End Marker on the old path, which is forwarded to the target, to mark that no more DL packets will arrive via the source/forwarding path. The target can then deliver forwarded and new-path packets in order and release the forwarding tunnel.
Q: Your filter shows no X2AP in an eNB capture, but handovers clearly happened. What do you check?
A: Whether the filter excluded it. Use sctp.data_payload_proto_id == 27 or x2ap, not an ip-based filter, because X2 is often on IPv6 or another VLAN. Check the protocol hierarchy for SCTP under IPv6, and check that a non-standard X2 port is decoded (Decode As). In the lab captures on this card X2 was on IPv6, and an IPv4-only check reported "no X2AP" by mistake.

OPT02 Mobility Parameter Tuning — A3 offset, hysteresis, TTT & CIO: what each knob does and which way to turn it for too-early, too-late and ping-pong Debug click to expand ▾
In plain English
A handover is a decision the network makes on behalf of a moving phone: "the neighbour is now clearly better, move". Four knobs set what clearly and now mean. The A3 offset and hysteresis say how much better the neighbour must be (in dB). Time-to-trigger (TTT) says for how long it must stay better. The cell individual offset (CIO) tilts the scales for one particular neighbour. Set them too loose and the phone bounces back and forth (ping-pong, too-early HO). Set them too tight and the phone hangs on to a dying cell and drops (too-late HO). Think of a thermostat: the dead-band stops the heater clicking on and off, but too wide a dead-band and the room gets cold.
A3 event: the neighbour must beat serving by the margin, continuously for TTT
The gap between the equal-level point and "A3 entering" is the dB margin (Off + Hys − Ocn). The TTT window adds a time delay on top. Both push the HO later; CIO for this neighbour pulls it earlier.
Level 1 — the formula and the four knobs
Entering condition (TS 36.331 / 38.331, event A3): Mn + Ofn + Ocn − Hys > Mp + Ofp + Ocp + Off. Leaving condition: Mn + Ofn + Ocn + Hys < Mp + Ofp + Ocp + Off. The entering condition must hold for the whole TTT; then the UE sends a Measurement Report and the eNB/gNB decides (it may still refuse, e.g. on load or admission).

KPIs: HOSR = successful HO ÷ HO attempts × 100 (targets typically ≥ 95–98 %); HO failure rate = failed ÷ attempts; ping-pong rate = ping-pong HOs ÷ total HOs (often targeted ≤ 1–2 %); HO interruption/execution time (often < 300 ms in field specs).
Level 3 — the subtleties experts get asked about
Hys vs Off — not the same knob. Both raise the entering bar by the same dB, but Hys also creates a gap before the leaving condition, so it damps oscillation around the threshold. Off moves the whole boundary. If the problem is instability, use Hys; if the boundary is simply in the wrong place, use Off or CIO. CIO is the surgical tool: it moves the boundary for one relation only, and is directional (A→B can differ from B→A).
Hidden knobs that behave like TTT. The L3 filter coefficient (filterCoefficient, default fc4) smooths Mn/Mp: a larger k means slower response, i.e. an extra delay on top of TTT. Mobility-state scaling (speedStateScaleFactors) multiplies TTT by 0.25–1 for medium/high-speed UEs. reportInterval/reportAmount decide whether a lost report is retried. If a TTT change "does nothing", check these.
Two real directions, both correct (anonymised field cases):
  • Busy arterial road, HOSR 91.2 %. TTT was 2560 ms. Fix: TTT 2560 → 160 ms, hysteresis 2 → 4 dB (to stop the shorter TTT causing ping-pong), added a missing neighbour and removed a PCI conflict. HOSR → 97.6 %. Lesson: a very long TTT on a fast road gives too-late HO and RLF.
  • Slow residential streets, drop rate about 3.2 %. Heavy overlap and ping-pong. Fix: A3 offset raised to 4 dB, TTT lengthened to 2560 ms, TX power −2 dB and azimuth re-aimed by 10° to reduce overlap. Drop rate → 0.9 %. Lesson: long TTT damps ping-pong for slow users in overlap zones.
  • Highway, HO failure 15 %. Classify causes in the logs → retune A3/Hys/TTT → fix neighbour list and coverage → re-drive. HO failure fell to about 2 %.
The right direction depends on the failure type and the user speed, which is why the same TTT value can be right in one cell and wrong in the next.
Pitfalls. (1) A "neighbour 10 dB stronger but no HO" is usually a configuration fault (missing relation, blacklist, wrong measObject), not tuning. (2) Tuning parameters cannot fix an overshooting or polluted area — fix tilt/power first (OPT03). (3) A formula of the form "TTT = (Δ + Hys)/slope" sometimes circulates in notes; it is not a 3GPP relation — TTT is a configured enumerated value. (4) Idle-mode reselection has its own set (Qoffset, Qhyst, Treselection in SIB3/4/5 — PT14); tuning connected-mode HO without matching idle mode causes a UE to camp on one cell and immediately hand over to another.
Interview Q&A
Q: Write the A3 entering condition and name each term.
A: Mn + Ofn + Ocn − Hys > Mp + Ofp + Ocp + Off, held for TTT. Mn/Mp = neighbour/serving measurement, Ofn/Ofp = frequency offsets, Ocn/Ocp = cell individual offsets, Hys = hysteresis, Off = a3-Offset.
Q: HOs are happening too late on a highway. What do you change?
A: Confirm with the RLF/re-establishment pattern (RLF in source, re-establish in target). Then lower TTT (e.g. 320 → 160 or 80 ms), reduce Off/Hys, or raise the CIO of the target on that relation. Check for missing neighbours first. Re-drive at the same speed.
Q: Ping-pong between two cells, no drops — fix?
A: Increase hysteresis and/or TTT on that pair. If it persists, the overlap is too large: tilt or reduce power on one cell. CIO can shift the boundary away from where slow users sit.
Q: What is the difference between hysteresis and a3-Offset?
A: Both add dB to the entering bar, but hysteresis also applies (with the opposite sign) to the leaving condition, creating a dead-band that suppresses oscillation. Offset only moves the boundary.
Q: Why is CIO preferred for fixing a single bad relation?
A: It is per-neighbour and directional, so it changes one boundary without affecting every other HO of the cell, unlike Off, Hys or TTT which apply to the whole report configuration.
OPT03 Optimisation Case Studies (1) — overshooting cell, pilot pollution (no dominant server) and PCI / mod-3 conflicts: telling them apart and fixing them Debug click to expand ▾
In plain English
Two of the most common field problems look the same on a phone screen — full signal bars, terrible speed — but have different causes. An overshooting cell is a cell that shouts too far: its signal reaches streets several kilometres away that should belong to other cells, so it interferes with them and steals their users. Pilot pollution is a crowd problem: at one spot the phone hears four or five cells at almost the same strength and none of them dominates, so each one is noise to the others. A third look-alike, the PCI conflict, is an identity problem (two nearby cells using the same or clashing physical cell ID) and is not pilot pollution, although some field notes call it that. This card shows how to tell the three apart in a drive test, and two real (anonymised) fixes with before/after numbers.

Level 3 — the PCI-conflict case, load-dependent SINR, and pitfalls
Case — "pilot pollution" that was really a PCI conflict. An urban cluster where three cells (A, B, C) carried the same PCI. Serving SINR about −3 dB, RSRQ −14 dB, RLF 6.8 %, HOSR 72 %. The source notes call this pilot pollution; the correct diagnosis is PCI collision/confusion plus overlap. Fix: new PCIs for A and C (chosen with different mod-3 values), tilt adjustment, power −2 to −3 dB, ANR update. Result: SINR −2.8 → 5.6 dB, RLF −74 %, HOSR 72 → 93 %, throughput 5.2 → 11.2 Mbps, CQI 6.1 → 9.3. Lesson: always check the PCI plan before touching tilt — PCI is a free fix.
Case — load-dependent interference in a busy market. Average SINR 3.8 dB at peak. Hourly averages: 9.2 dB (00–06), 7.5 dB (06–12), 3.8 dB (12–18), 6.1 dB (18–24). SINR that tracks traffic means neighbours' PDSCH load is the interferer, i.e. overlap, not a noise source. Fix: re-planned neighbour PCIs, 2° extra downtilt, cut the overshooting neighbour's power, and interference coordination for heavy users (eICIC/ABS is a HetNet tool — it only helps where a macro and small cells overlap). Result: SINR 3.8 → 14.6 dB, throughput about ×3.
Mod-3 example done right. Two strong neighbours with PCI 35 and 38 both have PCI mod 3 = 2 (same PSS, same CRS shift in 2/4-port LTE), so their reference signals collide and SINR stays low even when the cells are empty. Changing one to 36 (mod 3 = 0) removes the clash. (A widely copied example uses 35 and 36 as a "same mod-3" pair — that is arithmetically wrong.)
Pitfalls. (1) Downtilting the polluters can open a coverage hole — check the 5th-percentile RSRP after the change, not just SINR. (2) HO parameters cannot cure pollution; they only hide ping-pong. (3) Fix one cell at a time and re-drive; small changes (2°, 2–3 dB) often give the big gain. (4) Check the neighbours' KPIs after the change — overshoot fixes move traffic.
RCA framing (5W1H): what (symptom), where (cells/area), when (busy hour?), who (which users/devices), why (technical cause), how (impact) → observe → collect → analyse → root cause → act → validate by re-drive.
Interview Q&A
Q: What is pilot pollution? Is it the same as two cells sharing a PCI?
A: No. Pilot pollution is too many cells of similar strength (typically four or more within about 5–6 dB of the best) with no dominant server, so SINR collapses despite good RSRP. Same PCI on nearby cells is PCI collision/confusion — an identity problem fixed by re-planning PCIs.
Q: How do you prove a cell is overshooting?
A: Serving-cell plot showing it serving far outside its tier, scanner top-N showing it strong inside other cells, a long TA tail in PM counters (≈ 78 m per LTE TA step), and RSRP that is abnormally high at distance with poor SINR. Then check tilt, height, power and terrain.
Q: RSRP −80 dBm but SINR −2 dB. Coverage or interference? Next step?
A: Interference. Look at scanner top-N: one strong far cell → overshoot; a flat group → pollution; check PCI mod 3 of the strongest neighbours; if the DL is clean but UL is bad, hunt external interference with a spectrum analyser.
Q: Why is electrical tilt preferred over mechanical tilt for an overshoot fix?
A: Electrical tilt tilts the whole pattern uniformly (and can be done remotely by RET/AISG). Mechanical tilt lowers only the front lobe, raises the back lobe and widens the horizontal pattern at the sides.

Level 3 — definitions, NSA/VoLTE/latency specifics, answer structure
Drop-rate formulas — watch the definitions. Drop rate = abnormal releases ÷ successful setups (E-RAB/QoS-flow or RRC). "(attempts − successes) ÷ attempts" is a setup failure rate, not a drop rate; some notes mislabel it. CSSR in LTE is usually the product RRC setup SR × E-RAB setup SR (×S1 signalling SR in some vendors).
NSA-specific checks (why users "don't get 5G"): B1 threshold and NR measurement configuration (and measurement gaps if the UE needs them), NR neighbour/priority on the anchor, X2 between eNB and gNB up, SgNB addition success and SgNB release causes (NN02), UE band-combination support, NR-leg SINR. A too-high B1 threshold looks like "no 5G coverage" even where NR RSRP is fine.
VoLTE-specific checks: SIP failures (IMS side) vs QCI 1 bearer setup failures (RAN) vs drops (RF/HO/SRVCC). MOS problems split into RTP loss (radio BLER at the edge, HO interruption) and jitter/delay (transport, scheduling, DRX). See DT06.
Latency-specific checks: if ping is high while radio quality and throughput are fine, the RAN is rarely the cause: check backhaul utilisation, transport routing, core (S/P-GW or UPF) location and the test server. Idle-to-connected transitions and DRX add latency to the first packets — always ping with the UE already connected (LAT01).
5G issue taxonomy (useful for structuring an answer): coverage, capacity, interference, mobility, latency, coverage-vs-capacity imbalance (UL-limited edge), QoS/SLA (5QI/GBR mapping), VoNR, massive-IoT (DRX/eDRX/PSM, paging), energy saving (cell DTX/sleep — can look like "missing cell" at night).
STAR answer shape: Situation (KPI, place, time), Task (target), Action (checks in order, then one change at a time), Result (numbers, and that neighbours did not degrade).
Interview Q&A
Q: Throughput is 2–3 Mbps at RSRP −75 dBm. What do you check?
A: SINR and CQI first (interference?), then PRB utilisation and number of users (load?), scheduler limits, CA/MIMO rank, then backhaul and server. Good RSRP rules out coverage, not interference or congestion.
Q: NSA users are rarely on 5G. Where do you look?
A: B1 threshold and NR measurement config on the LTE anchor, NR neighbour definitions, X2 to the gNB, SgNB addition success/failure causes, UE band-combination capability, and NR-leg coverage/SINR.
Q: Ping is 120 ms but radio KPIs and throughput are fine. Cause?
A: Transport or core: backhaul congestion/routing, far core/UPF, test-server location. Confirm by pinging from the site router/transport side vs from the UE; fix routing/capacity/QoS.
Q: A cell has PRB 98–100 % in the busy hour. Options?
A: Short term: load balancing to neighbours/other layers, CA. Long term: add a carrier, sector split (3 → 6), small cells. Parameter tuning does not create capacity.
Q: How do you present an optimisation result in an interview?
A: STAR: the KPI and where/when, the target, the evidence-driven checks and single-step changes, and the before/after numbers including a check that neighbouring cells did not degrade.

In plain English
Voice testing asks two questions: did the call work (set up, stay up, hand over) and did it sound good. The first is answered by SIP signalling and bearer events in the log. The second is answered by a score from 1 to 5 called MOS (mean opinion score), which drive-test tools compute by comparing the received speech against a reference clip. Speech quality is killed by three things: packets lost, packets arriving unevenly (jitter), and delay. And the classic mystery — "I can hear them, they can't hear me" — is one-way audio, which almost always means the voice packets are flowing in only one direction somewhere in the path. This card covers VoLTE/VoNR and over-the-top (OTT) app calls. PT10 has the IMS architecture and basic SIP flow; this card is the test and debug angle.

Level 3 — the E-model, RTCP jitter and a one-way-audio RCA table
R-factor maths. R = R0 − Is − Id − Ie,eff + A, where R0 ≈ 93.2 by default (basic signal-to-noise), Is = simultaneous impairments, Id = delay impairment, Ie,eff = equipment/codec impairment including packet loss, A = advantage factor (0 for fixed lines). MOS from R (0 < R < 100): MOS = 1 + 0.035·R + 7·10−6·R·(R − 60)·(100 − R). Check: R = 93.2 → MOS ≈ 4.41; R = 80 → 4.02; R = 70 → 3.60; R = 50 → 2.58. Delay costs little below about 150–175 ms, then Id rises steeply; loss costs much more with bursty loss than with random loss, which is why HO interruption hurts more than its average loss suggests.
Jitter as RTCP reports it (RFC 3550): a running estimate J ← J + (|D| − J)/16, where D is the change in packet transit time between consecutive packets. RTCP receiver reports also carry fraction lost and cumulative lost — the quickest way to see which direction is bad.

Interview Q&A
Q: What MOS and R-factor do you expect for good VoLTE?
A: MOS ≥ 4.0 with AMR-WB, i.e. R about 80 or more. R ≥ 70 (MOS ≈ 3.6) is the usual "acceptable" floor. Measured in the field with POLQA (P.863).
Q: A user can hear the other party but is not heard. How do you debug?
A: It is one-way audio: check RTP packet counters per direction at each hop (UE, RAN GTP-U, SBC). Check the SDP IP/port, NAT/firewall pinholes at the SBC, that the UL dedicated bearer/TFT exists, and ROHC context. The direction where packets stop is the fault location.
Q: What is SIP Timer B and what happens when it expires?
A: The INVITE client transaction timeout, 64 × T1 = 32 s with RFC 3261 defaults (IMS UE side often T1 = 2 s → 128 s). On expiry the transaction fails as a timeout (408) and the call attempt fails.
Q: Why does a 401 during IMS registration not mean failure?
A: It is the normal authentication challenge: the S-CSCF returns 401 with the AKA challenge, and the UE re-sends REGISTER with the response; 200 OK completes registration.
Q: Why is bursty packet loss worse than the same average random loss?
A: Packet-loss concealment handles isolated losses well, but consecutive lost frames (e.g. during a HO gap) produce audible dropouts; the E-model's Ie,eff grows faster with burstiness.

Level 2 — test method and the triage order
The session ladder. Before blaming RF, localise the failure to one step: attach/registration → PDN/PDU session → IP address → DNS → server reachable → transfer → release. "No data" with a good radio link is usually a session, APN/DNN or DNS problem (CM06 for GTP-U counters).
Method that produces defensible numbers:
  • Use an on-net server close to the core (or at the site for a RAN-only test) to exclude the internet.
  • Run UDP first to find what the radio can carry, then TCP to see what users get. A big gap means TCP/transport/server, not radio.
  • Test DL and UL separately; lock RAT/band when testing one layer; note CA and rank state.
  • Log the RF snapshot with every sample: RSRP, SINR, CQI, MCS, rank, scheduled PRBs, BLER, number of CCs.
  • Report percentiles (5th / 50th / 95th) and cell-edge throughput, not only the average or peak.
  • Repeat at busy and quiet hours — the difference is the load effect.
Low-throughput triage order: RSRP/RSRQ → SINR → CQI → MCS and BLER → CA active? → MIMO rank → PRB share / cell load / users → UE category and band-combo support → TDD pattern (DL:UL share) → backhaul utilisation → core → server/TCP. Stop at the first abnormal item.
Expected radio ceiling comes from TPUT01: PRBs × layers × modulation order × code rate × (1 − overhead) × DL/UL share. Compare the measured value with that ceiling at the logged MCS and rank before calling it low.
Level 3 — TCP maths, radio subtleties and transport traps
TCP limits you must be able to calculate.
  • Window limit: throughput ≤ window ÷ RTT. A 64 KB window over 40 ms RTT caps one stream at ≈ 13 Mbit/s — no matter how good the radio is. That is why high-rate tests need window scaling and parallel streams.
  • Bandwidth-delay product: BDP = rate × RTT. 1 Gbit/s × 20 ms = 2.5 MB must be in flight to fill the pipe.
  • Loss limit (Mathis approximation): throughput ≈ (MSS / RTT) × (1.22 / √p). With MSS 1400 B, RTT 40 ms, loss p = 10−4 → ≈ 34 Mbit/s per stream. Tiny residual loss on transport caps TCP hard.
  • Slow start: a 5 MB file on a 300 Mbit/s link finishes before TCP reaches full rate; the average looks low. Use large files or time-based tests.
Radio-side subtleties. BLER around 10 % on first transmissions is normal — link adaptation targets it; residual loss after HARQ/RLC should be near zero. Rank 1 in a good-SINR area points to antenna/branch imbalance or correlation (check per-branch RSRP). UL is often power-limited at the edge: check PHR (negative = power-limited) before blaming the scheduler. In TDD, a DL-heavy frame pattern caps UL — it is configuration, not a fault.
Transport and core traps. MTU/fragmentation issues on GTP-U tunnels (large packets dropped or fragmented) show up as good ping but poor TCP; a test with smaller MSS confirms it. Policing/shaping on the backhaul shows a flat ceiling at a round number regardless of radio quality. A server with a 1 GbE port cannot demonstrate 1.5 Gbit/s.
Latency split (LAT01): radio scheduling (SR→grant→data, HARQ retransmissions), DRX wake-up, transport, core, server. Ping from the UE and from the site transport side at the same time to split RAN from beyond-RAN.
Interview Q&A
Q: Why run UDP before TCP in a throughput test?
A: UDP shows what the radio and transport can carry without TCP congestion control. If UDP reaches the expected rate but TCP does not, the limit is TCP window, RTT, loss or the server — not the RAN.
Q: One TCP stream gives 13 Mbit/s over a link with 40 ms RTT. Why?
A: Window-limited: 64 KB ÷ 40 ms ≈ 13 Mbit/s. Enable window scaling or use parallel streams (iperf3 -P).
Q: Good RSRP, good SINR, but low throughput. What next?
A: Check scheduled PRBs and cell load/users, CA and rank state, UE category, TDD pattern, then backhaul utilisation, core and server; compare the measured rate with the TPUT01 ceiling at the logged MCS and rank.
Q: What does iperf3 -R do?
A: Reverse mode: the server sends and the client receives, so with the client on the UE it measures downlink.
Q: BLER is 10 % in the log. Is that a problem?
A: Not by itself: link adaptation deliberately targets about 10 % first-transmission BLER for efficiency. Look at residual BLER after HARQ and at whether MCS is dropping.

Level 3 — problem statements, evidence hierarchy and false trails
Write a precise problem statement first: "drop rate 4 % in sector X between 10:00 and 14:00 on weekdays, since the change on date Y" beats "sector X is bad". It already tells you to look at load (time), recent changes (date) and one sector.
Evidence hierarchy. Layer-3 messages and cause codes beat RF levels; RF levels beat KPI trends; a reproducible re-drive beats everything. A 3 dB RSRP difference between two drives on the same road is within normal fading and shadowing — compare binned averages (50–100 m bins) and percentiles, not single samples.
Change control. One change per cell per iteration, a baseline drive before, a validation drive after on the same route, speed and time of day, plus about 3 days of counter trend. Check that neighbouring cells did not degrade. Keep a rollback plan.
Common false trails.
  • Blaming HO parameters for drops that are really coverage holes (no neighbour was strong enough either).
  • Blaming RF for a data problem that is DNS, APN/DNN or MTU (good ping, no pages).
  • Treating energy-saving cell sleep at night as a site outage.
  • Test UE issues: overheating throttle, wrong band lock left from a previous test, battery saver.
  • Assuming the scanner and the UE agree: the scanner sees every cell; the UE only reports what it was configured to measure.
Corrective-action menu (from cheapest/fastest): parameter (neighbour list, HO thresholds, PCI) → electrical tilt/power → azimuth/mechanical → hardware (feeder, connector, PIM, antenna) → new sector/site. Transport/core findings go to those teams with the evidence. Always re-drive to validate.
Report: executive summary, KPI vs target, plots (RSRP, SINR, serving cell, throughput, events), each issue with evidence and root cause, actions, before/after comparison.

Interview Q&A
Q: Where is the RRC message that tells the UE to hand over, in an X2 capture?
A: Inside the X2AP HandoverRequestAcknowledge, in the TargeteNBtoSource-eNBTransparentContainer. It holds an RRC HandoverCommand wrapping the RRCConnectionReconfiguration with mobilityControlInfo. The target builds it; the source only forwards it to the UE.
Q: What is in SN Status Transfer and why does it matter?
A: For each AM bearer, the UL and DL COUNT (PDCP SN plus HFN), optionally with a bitmap of missing UL PDCP SDUs. The target continues ciphering from that COUNT and delivers data in order without loss or duplicates. A wrong or missing value causes deciphering errors or data loss after the HO.
Q: HO Request to Ack took 26-44 ms and Path Switch to Ack 0.3 ms. What does each number measure?
A: The first is target eNB processing: admission control and building the RRC reconfiguration. The second is the core: MME plus SGW moving the S1-U path. Neither is the user-plane interruption time, which is measured at the UE from the RRC Reconfiguration to RRC Reconfiguration Complete.
Q: The HO command has ra-PreambleIndex 53 and the cell uses 52 preambles. So what?
A: Preambles 0-51 are for contention-based access, so 53 is one of the reserved dedicated preambles. The UE does contention-free random access on the target, which is faster and avoids collisions. If the dedicated preamble were inside the contention range, two UEs could collide during the HO.
Q: What does nextHopChainingCount = 0 in the HO Request tell you?
A: No fresh Next Hop key has been provided yet, so the target key KeNB* is derived horizontally from the current KeNB. After the Path Switch, the MME returns a new NH with NCC = 1 so the next HO can use vertical derivation.

In plain English
Sometimes a phone loses its radio link before any handover happens. It then knocks on the door of a nearby cell and says "I was just in cell 47, please take me back" (RRC re-establishment). The new eNB does not know this phone, so it sends an RLF Indication over X2 to the eNB that owns cell 47: "your UE failed and turned up here". In the lab captures the old eNB answers by running a handover preparation toward the new eNB, which hands over the UE's file so the call survives instead of dropping. The same captures also show a message arriving after the UE's file was already closed, which is exactly the kind of ordering bug a test engineer should catch and report.

Interview Q&A
Q: Who sends an X2 RLF Indication, to whom, and why?
A: The eNB where the UE re-established sends it to the eNB that owns the cell where the radio link failed. It carries the failure-cell PCI, the re-establishment cell ECGI, the old C-RNTI, ShortMAC-I and the re-establishment cause, so the owner can classify the failure for MRO (too early, too late, wrong cell).
Q: Why does a HandoverRequest follow the RLF Indication within 3 ms in the capture?
A: The failure-cell owner pushes the UE context to the eNB where the UE re-established, using the HO preparation, so the re-establishment can succeed and the call survives. LTE X2 has no dedicated context-fetch procedure, so this is vendor behaviour built on standard messages.
Q: The SN Status Transfer comes after UE Context Release. Why is that a problem?
A: UE Context Release means the handover is finished and the source can delete the UE. The COUNTs must reach the target before it starts PDCP on the new bearers. Arriving afterwards (here also with a UE ID that matches nothing), they are ignored, which risks loss, duplicates or ciphering errors on the re-established bearers.
Q: How do you prove an ordering defect is real and not a capture artefact?
A: Capture at both ends and check the same order appears in both, check the SCTP TSNs (sending order), check it repeats every time in the same scenario, and compare with a scenario where it is correct (here the reverse direction). Then attach frame numbers and filters to the bug.
Q: What does RRCConnReestabIndicator = otherFailure mean for MRO?
A: The UE re-established after a radio link failure, not after a failed handover or reconfiguration. With no recent HO into the failure cell this points to a too-late HO toward the re-establishment cell.

In plain English
The S1 link is the eNB's phone line to the core network. Level 2 — reading it step by step
1. Reset direction and type. Every Reset comes from the MME side. S1AP Reset has two types: s1-Interface (reset-all: "the whole interface restarted, drop every UE") and partOfS1-Interface (a list of UE-associated logical connections, by MME-UE-S1AP-ID and/or eNB-UE-S1AP-ID: "forget just these UEs"). Here all but one per file are per-UE. The eNB answers each with ResetAcknowledge in 2-8 ms and releases those UEs locally.
2. The pattern. A Reset [transport-resource-unavailable] for one UE; ~150 ms later that UE (which still had traffic) sends a Service Request; the core answers it 0.4 ms later with another Reset [misc-unspecified] instead of InitialContextSetup. The UE's NAS guard timer T3417 (5 s) expires and it retries ~5.3 s later; this time ICS Request → Response takes 66-80 ms and works. Each cycle = one failed Service Request + about 5 s of user-plane outage. 123 of 243 Service Requests (and 189 of 413) were answered this way, which exactly explains the ~50 % success.
3. What the cause means. transport-resource-unavailable from the core side points at the core or gateway losing the S1-U/GTP path or the bearer context for that UE (SGW/gateway transport problem, a restart, a full tunnel table). The 0.4 ms answer to the next Service Request is too fast for any real processing: the core has simply not recovered that UE yet. No eNB-initiated UEContextReleaseRequest occurs in the 10 s before any transport-cause Reset (the few there are, mostly user-inactivity, happen elsewhere), so the trigger is not radio.
4. om-intervention. 8 and 50 Resets carry om-intervention: someone (or an automated OAM action) restarted things on the core side during the run. In the second file they come in two clusters (about 2.3-3.5 h and 5.5-6.6 h into the run), so mark those periods as "operator activity" and exclude it from stability KPIs.
5. S1 Setup Failure and TimeToWait. About 5 s after the full Reset (most likely after an SCTP association restart) the eNB sent S1SetupRequest (Global eNB ID, eNB name, supported TAs with TAC 0x3131, broadcast PLMNs 001-01 and 002-01, default paging DRX). The core replied S1SetupFailure, cause misc-unspecified, TimeToWait = v20s. The eNB correctly waited exactly 20.000 s and retried; S1SetupResponse followed (MME name, served GUMMEIs, RelativeMMECapacity 1), then eNB/MME ConfigurationTransfer (SON exchange of X2 transport addresses) and X2Setup within 30 ms. Interview Q&A
Q: What is the difference between an s1-Interface and a partOfS1-Interface Reset?
A: s1-Interface resets everything: all UE-associated connections on that S1 are released. partOfS1-Interface lists specific UEs by their S1AP IDs, and only those are released. Either side can send it, and the receiver answers with ResetAcknowledge.
Q: Service Request success is 50 % but there are no InitialContextSetupFailures. How?
A: The failures happen before ICS. The core answers the Service Request with a per-UE Reset, so no ICS is ever attempted. The UE retries after T3417 (5 s) and then succeeds. Count Service Requests against ICS Responses, not ICS Requests against Responses.
Q: What should an eNB do when it receives S1SetupFailure with TimeToWait = 20 s?
A: Wait at least 20 s before sending another S1SetupRequest to that MME. In the capture it retried after exactly 20.000 s and succeeded. Retrying sooner would violate TS 36.413 and add load to an MME that is recovering.
Q: Why do TAU and Service rejects with cause #9 appear after a core reset?
A: Cause #9 means the network cannot derive the UE identity: the core lost the context behind the UE's GUTI. The UE deletes its GUTI and security context and re-attaches with IMSI, which is why full attaches with Authentication and Security Mode follow.
Q: How do you decide whether a Reset storm is the eNB's fault?
A: Check who sends the Resets, their cause class, and what happens just before them. Resets from the core with a transport cause, no eNB-initiated releases before them, prompt ResetAcks and correct TimeToWait handling all point away from the eNB and toward the core or transport.

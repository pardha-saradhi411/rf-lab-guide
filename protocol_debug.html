HO01 Intra-DU Handover — F1AP internal, no core involvement Handover click to expand +
▼ Visual sequence diagram
Solid→request · dashed→response/ack · amber→internal action. Step-by-step detail below.

Source & target cell both under the same gNB-DU (same CU) · fastest HO type · no Xn, no core path switch

Why it exists
When a UE moves between two cells served by the same DU, there's no need to involve a new DU, Xn, or the core. The CU decides the HO from measurement reports and just reconfigures the UE onto the target cell; the DU allocates target-cell L1/L2 resources internally. Same CU-UP, same F1-U/N3 tunnels → no path switch, so the interruption is minimal. On a Metro AAU carrying several cells per sector, this is the common everyday mobility path.
Call flow
UE   → CU :  MeasurementReport (A3: target > serving + offset)
CU   → DU :  F1AP UE Context Modification Request (target SpCell)
DU   → CU :  F1AP UE Context Modification Response (DU→CU RRC:
             target cell cfg, new C-RNTI, RACH resources)
CU   → UE :  RRCReconfiguration (reconfigurationWithSync → target)
UE   → tgt:  RACH  (preamble → RAR/Msg2)
UE   → CU :  RRCReconfigurationComplete  (on target cell)
CU   → DU :  F1AP UE Context Modification (release source cell)
Key parameters
ParamMeaning / typical
A3 offset / hysteresis / TTT2–3 dB / 1–2 dB / 160–320 ms — triggers the report
reconfigurationWithSyncIE that makes it a HO (RACH to target) vs plain reconfig
T304HO supervision timer; expiry → HO failure → RLF/re-establish
newUE-Identity (C-RNTI)re-allocated on target cell
Debug checklist
No MeasurementReport → check A3 thresholds/TTT, meas gaps, target cell not in measObject. T304 expiry → target RACH failing (coverage hole, wrong RACH cfg in DU→CU container, PRACH power). DU→CU container missing → DU rejected UE Context Modification (admission / resource). Ping-pong → TTT too short / hysteresis too small. Data stall after HO → PDCP not re-established / SN discontinuity.
Interview Q&A
Q: Why is intra-DU HO the fastest? No Xn/S1/NG signaling and no UPF path switch — the CU just reconfigures the UE and the DU allocates target resources internally, so only the RACH-to-target interruption applies.
Q: What single IE turns an RRCReconfiguration into a handover? reconfigurationWithSync (contains the target SpCell config + RACH); without it, it's an in-place reconfig with no cell change.
Q (PW): On a Metro AAU with multiple cells per sector, why do most HOs stay intra-DU? Because the whole sector's cells terminate on one DU, so mobility within the site never needs Xn or core path switch — keeping KPIs (interruption time, drop rate) low.
HO02 Inter-DU Intra-CU Handover — F1AP UE Context Setup to new DU Handover click to expand +
▼ Visual sequence diagram
Solid→request · dashed→response/ack · amber→internal action. Step-by-step detail below.

Source & target cell on different DUs but the same CU · CU orchestrates both DUs over F1 · no Xn, no core path switch

Why it exists
A UE moving between cells on two DUs of the same gNB (same CU). The CU stays anchored — it sets up a fresh UE context on the target DU (F1AP UE Context Setup), moves the UE, then releases the source DU's context. Because the CU-UP and its N3 tunnels don't move, there's still no core path switch; only the F1-U tunnel between CU-UP and the target DU is re-pointed.
Call flow
UE     → CU      :  MeasurementReport (target cell on DU-2)
CU     → DU2     :  F1AP UE Context Setup Request (target cell)
DU2    → CU      :  F1AP UE Context Setup Response (DU→CU RRC:
                    target cfg, C-RNTI, RACH; new F1-U DL TEIDs)
CU     → UE      :  RRCReconfiguration (reconfigurationWithSync → DU-2)
UE     → DU2     :  RACH → RRCReconfigurationComplete
CU-UP  ↔ DU2     :  F1-U path switched (DL data now via DU-2)
CU     → DU1     :  F1AP UE Context Release (source)
Key parameters
ParamMeaning
F1AP UE Context Setupcreates the UE context on target DU (vs Modification for intra-DU)
DL/UL F1-U GTP TEIDre-established between CU-UP and target DU
PDCP handlingCU-CP keeps PDCP; SN status preserved, RLC re-established on DU-2
T304HO timer as HO01
Debug checklist
UE Context Setup reject from DU-2 → target-cell admission/resource, cell barred, or F1 not up. Data stall post-HO → F1-U TEID not switched at CU-UP → DL still going to DU-1. RACH fail on DU-2 → target coverage / RACH cfg. Verify F1 SCTP between CU and both DUs is healthy.
Interview Q&A
Q: What's the key F1AP difference vs intra-DU HO? Inter-DU uses UE Context Setup on the target DU (new context) rather than UE Context Modification on the same DU.
Q: Does the core know about this HO? No — CU-UP is unchanged, so no NGAP Path Switch; only the internal F1-U tunnel to the target DU is re-pointed.
Q (PW): Why can two Metro sites still avoid Xn here? If both sectors' DUs share one CU (common in a centralized deployment), the CU handles it over F1 — Xn only appears when the target is a different gNB/CU.
HO03 Inter-CU Xn-based Handover — full XnAP flow Handover click to expand +
▼ Visual sequence diagram
Solid→request · dashed→response/ack · amber→internal action. Step-by-step detail below.

Target is a different gNB/CU, and an Xn interface exists between source and target · core involved only for the path switch

Why it exists
When two gNBs have a direct Xn link, HO is done gNB-to-gNB without routing prep through the core (faster, less core load). The source CU asks the target CU to admit the UE, forwards buffered data over Xn during the switch, and only afterwards does the target tell the AMF to switch the UPF's downlink path. The 4G equivalent is X2-based HO.
Call flow
UE   → S-gNB :  MeasurementReport
S-gNB → T-gNB:  XnAP Handover Request
T-gNB → S-gNB:  XnAP Handover Request ACK (target RRC container)
S-gNB → UE   :  RRCReconfiguration (reconfigurationWithSync → T-gNB)
S-gNB → T-gNB:  SN Status Transfer  +  data forwarding (Xn-U tunnel)
UE   → T-gNB :  RACH → RRCReconfigurationComplete
T-gNB → AMF  :  NGAP Path Switch Request
AMF  → UPF   :  N4 session mod (switch DL to T-gNB)
AMF  → T-gNB :  NGAP Path Switch Request ACK
T-gNB → S-gNB:  XnAP UE Context Release
Key parameters
ParamMeaning
SN Status TransferPDCP UL/DL SN counts handed to target for lossless HO
Data forwarding (Xn-U)source tunnels buffered/in-flight PDUs to target
Path Switch (NGAP)only core step — repoints UPF DL to target
End MarkerUPF sends on old path so target knows forwarding is done
Debug checklist
HO Request rejected/prep-failure → target admission, no matching slice/QoS, security algo mismatch. Xn down → falls back to N2/NG-based HO. Packet loss during HO → data forwarding not set up / SN Status Transfer missing. DL stall after complete → Path Switch failed at AMF/UPF → check N4. Ping-pong across gNBs → cell-individual offsets (CIO) / mobility thresholds.
Interview Q&A
Q: When is Xn HO chosen over N2 HO? When a direct Xn exists between the gNBs — it's faster and offloads the core; N2 is the fallback when there's no Xn.
Q: How is data loss avoided? SN Status Transfer + Xn-U data forwarding, with the UPF End Marker telling the target when the old path is drained.
Q (PW): Between two Metro gNBs on adjacent sites, which HO runs? If Xn is provisioned, Xn-based; the only core touch is the NGAP Path Switch at the end.
Deep Reference Notes
X2 (LTE) ↔ Xn (5G) message parity: HandoverRequest / HandoverRequestAck, SN Status Transfer (PDCP SN counts for lossless HO), and UE Context Release exist on both. Trigger types: normal HO is measurement-triggered (A3 event); a failed link triggers RLF → RRC Re-establishment instead (which needs a prepared context at the target, or it is rejected). Phases: Preparation (admit + reserve) → Execution (RRCReconfig + RACH) → Completion (Path Switch + release). Data forwarding: direct (over X2/Xn-U) or indirect (via S-GW/UPF). Rel-16 DAPS (Dual Active Protocol Stack) keeps the source link alive during execution for near-0 ms interruption.

Reference Detail (ShareTechNote)
X2AP procedures & IEs: X2 Setup (X2 SETUP REQUEST carries global eNB ID, served-cell info, PRACH config → X2 SETUP RESPONSE) establishes the eNB↔eNB link. LTE HO when no X2 exists between eNBs (or MME/S-GW relocation needed) · MME orchestrates via S1AP

If two eNBs have no X2 link, or the HO also needs an MME/S-GW change, the core does the work. Q (PW): In a 4G Metro/FHGW deployment, why might you still see S1 HO? If X2 isn't provisioned to a neighbor (different vendor/region), mobility falls back to S1 via the MME.

HO06 Conditional Handover (CHO) — UE-autonomous execution (5G NR Rel-16) Handover click to expand +
▼ Visual sequence diagram
Solid→request · dashed→response/ack · amber→internal action. Step-by-step detail below.

Network pre-configures candidate targets; the UE decides when to execute — no waiting for a network command at the worst moment

Why it exists
In a normal HO the network sends the command after the measurement report — but by then the serving radio may already have collapsed, so the command itself is lost → HO failure / drop. CHO (Rel-16) fixes this: the gNB prepares one or more candidate cells in advance and hands the UE execution conditions. The UE keeps serving traffic and, the instant a condition is met, executes the prepared HO autonomously. Big win for high-speed and mmWave (fast fading) where the command-to-execution window is fatal.
Call flow
UE → gNB : MeasurementReport (early, before serving degrades) gNB → T-cells : prepare candidates (Xn/F1 HO Request, as normal) gNB → UE : RRCReconfiguration { conditionalReconfiguration: condReconfigToAddModList[ candidate cell + execution condition CondEvent (A3/A5) ] } UE : keeps serving link, EVALUATES conditions each cell UE : when cond met (e.g. RSRP_tgt > thr AND RSRP_srv < thr for TTT) -> EXECUTE autonomously -> RACH on that target UE → T-gNB : RRCReconfigurationComplete T-gNB : PathSwitch (as normal) ; other prepared candidates are released
Key parameters
ParamMeaning
conditionalReconfigurationRRC IE holding the candidate list + conditions
CondEvent A3 / A5execution triggers (A3: tgt>srv+off; A5: srv<thr1 & tgt>thr2)
candidate cell listup to 8 prepared targets (each with its own RACH cfg)
T304still supervises the execution once triggered
Debug checklist
UE never executes CHO → execution-condition thresholds unreachable (A5 thr1/thr2 too strict), or candidate RSRP not crossing → check the measConfig + reported RSRP. UE executes to wrong cell → overlapping conditions on multiple candidates → tighten per-cell offsets. Prepared but stale → candidates released before condition met (prep timer) → re-prepare. RACH fail on execution → candidate's dedicated RACH cfg wrong → check the per-candidate reconfig.
Interview Q&A
Q: How does CHO reduce handover failures? The target is prepared and the command delivered early, while the serving link is still good; the UE then executes at the right moment on its own — so a late-collapsing serving cell can't kill the (already-received) command.
Q: Baseline HO vs CHO — who decides the execution instant? Baseline: the network, via the RRCReconfiguration it sends after the report. CHO: the UE, when its pre-loaded execution condition is met.
Q (PW): Where would CHO matter for Metro? On B41/n41 (higher band, faster fading) and any high-mobility corridor, where the normal command-to-execution gap is where drops happen.
CA01 CA Setup — PCell + SCell addition (RRC Reconfiguration) Carrier Aggregation click to expand +

Aggregate a Secondary Cell (SCell) onto the Primary (PCell) for more bandwidth · added via RRCReconfiguration, but starts deactivated

Why it exists
One carrier caps peak throughput. CA lets the gNB glue extra carriers (SCells) to the anchor (PCell) so a UE can be scheduled across all of them at once. The PCell always handles RRC/security/PUCCH; SCells add data pipes. On a 5-band Metro AAU (B1/B3/B8/B28/B41), CA combos like B3+B1 or B41+B3 are how you hit the throughput KPIs the RCT power/EVM tests underpin.
Call flow
UE   → gNB :  UECapabilityInformation (CA band combos, class)
gNB          decides SCell (load, meas, combo supported)
gNB  → UE  :  RRCReconfiguration (sCellToAddModList: SCellIndex,
             cell cfg, CQI/SRS cfg)   -- SCell added DEACTIVATED
UE   → gNB :  RRCReconfigurationComplete
gNB  → UE  :  MAC CE (Activation)  -- see CA02, SCell goes active
UE   → gNB :  CQI/PMI/RI on SCell -> gNB schedules across CCs
Key parameters
ParamMeaning
sCellToAddModListRRC IE listing SCells to add (index + cfg)
CA band combinationmust be in UE capability (e.g. CA_3A-1A); BW class A/C…
PUCCHon PCell (and PUCCH-SCell for large combos)
Initial SCell statedeactivated — activated later by MAC CE (fast)
Debug checklist
SCell never added → combo not in UECapability, or gNB combo table missing it. Added but no throughput gain → SCell still deactivated (no MAC CE) or CQI on SCell bad → check SCell coverage/config. RRCReconfiguration failure → UE couldn't apply SCell cfg (SRS/CQI resource clash). Reject at capability → UE band-combo class too low.
Interview Q&A
Q: Why is a newly added SCell deactivated? To save UE power and avoid measuring/decoding a carrier before it's needed; activation via MAC CE is much faster than an RRC add, so the gNB adds early and activates on demand.
Q: What always stays on the PCell? RRC signaling, security, and PUCCH (unless a PUCCH-SCell is configured for large combos).
Q (PW): Which CA combos matter on a 5-band Metro AAU? Low+high pairings (e.g. B8/B28 coverage + B1/B3/B41 capacity) — the RCT per-band power/EVM must pass first, since CA just schedules across carriers that already meet conformance.
Deep Reference Notes
CA bandwidth classes (aggregated RB / #CCs): Class A = 1 CC (≤100 RB); Class B = 2 CC ≤100 RB total; Class C = 2 contiguous CC (100–200 RB) — the common intra-band case. Deployment scenarios: intra-band contiguous, intra-band non-contiguous, and inter-band (e.g. B3+B1). Cross-carrier scheduling: a Carrier Indicator Field (CIF) in the DCI lets the PCell PDCCH schedule an SCell PDSCH — used when the SCell own PDCCH is unreliable (interference). UE capability: supportedBandCombination + per-CC ca-BandwidthClass gate which combos the gNB may configure.

CA02 SCell Activation / Deactivation — MAC Control Element Carrier Aggregation click to expand +

Turning an SCell on/off fast, at L2 — a MAC CE, not RRC · plus the sCellDeactivationTimer for auto-off

Why it exists
RRC add/remove of an SCell is slow (tens of ms) and battery-costly to keep active. So the gNB adds SCells once via RRC (deactivated), then flips them on/off with a 1-byte MAC Control Element in a few ms as traffic demands. An inactivity timer auto-deactivates an idle SCell to save UE power.
Call flow
Activation:
gNB → UE :  MAC CE (Activation/Deactivation), bit[SCellIndex]=1
UE       :  start CQI/SRS on SCell, apply activation delay (~8+ ms)
UE → gNB :  valid CQI on SCell -> gNB schedules PDSCH there
Deactivation:
gNB → UE :  MAC CE bit=0    OR    sCellDeactivationTimer expires
UE       :  stop SReporting/monitoring on that SCell
Key parameters
ParamMeaning
Activation/Deactivation MAC CEbitmap, one bit per SCellIndex (LCID identifies the CE)
Activation delay~8 subframes+ before SCell is usable (CQI valid)
sCellDeactivationTimerauto-deactivate after inactivity (RRC-configured)
Debug checklist
MAC CE sent but SCell not used → activation delay not respected, or UE not reporting CQI on SCell → check SCell RS/coverage. SCell keeps deactivating → sCellDeactivationTimer too short vs bursty traffic. No CE at all → scheduler policy never activates (low load threshold). Throughput lower than expected → SCell active but poor CQI → falls back to PCell scheduling.
Interview Q&A
Q: Why activate via MAC CE, not RRC? MAC CE is L2 and takes a few ms vs tens of ms for RRC — you can react to traffic bursts without re-signaling the whole SCell config.
Q: What happens the instant after activation? There's an activation delay while the UE starts CQI/SRS on the SCell; the gNB can only schedule PDSCH there once valid CQI arrives.
Q (PW): How would you confirm SCell activation on the bench? Look for the Activation/Deactivation MAC CE in the DU/MAC log and the appearance of CQI reports + PDSCH grants on the SCell index.
CA03 Inter-band CA Measurement — A4 event trigger Carrier Aggregation click to expand +

Deciding which SCell to add on another band — driven by the A4 event ("neighbour becomes better than a threshold")

Why it exists
For inter-band CA the gNB needs to know the candidate carrier is actually good enough to add. Unlike handover (A3 = neighbour better than serving), SCell selection uses A4 = neighbour above an absolute threshold — the serving cell isn't degrading, we just want a good extra carrier. Inter-band measurement may need measurement gaps so the UE can tune away and measure the other band.
Call flow
gNB → UE :  RRCReconfiguration (measObject other band,
             reportConfig event A4: threshold, hyst, TTT;
             measGapConfig if inter-freq needs gaps)
UE       :  during gaps, measure candidate band RSRP/RSRQ
UE → gNB :  MeasurementReport (A4: Mn + Ofn + Ocn - Hys > Thresh)
gNB      :  pick SCell -> RRCReconfiguration sCellToAddModList (CA01)
Key parameters
ParamMeaning
Event A4Mn + Ofn + Ocn − Hys > a4-Threshold (neighbour absolute)
Measurement gapsgp0 (6ms/40ms) / gp1 (6ms/80ms) — needed for inter-freq if UE can't measure without retuning
Ofn / Ocnfrequency- and cell-specific offsets
A2 (companion)often used to release SCell when serving gets poor
Debug checklist
No A4 report → threshold too high, offsets wrong, or gaps not configured so UE never measures the other band. SCell added on a weak carrier → A4 threshold too low. Throughput drops during measurement → gaps stealing too many subframes (gp0 vs gp1 trade-off). Inter-band combo unsupported → not in UE capability (check band-combo list).
Interview Q&A
Q: Why A4 for SCell and A3 for handover? A3 is relative (neighbour better than serving → you must move); A4 is absolute (neighbour good enough → worth adding as an extra carrier without leaving the PCell).
Q: When are measurement gaps needed? When the UE can't measure the target frequency while receiving on the serving carrier (no spare RF chain) — the gap lets it retune briefly.
Q (PW): For B3(PCell)+B1(SCell) CA, why might gaps be required? They're different bands; a UE without simultaneous multi-band RX needs a gap to measure B1 RSRP before the gNB adds it as SCell.
CA04 CA ACLR — why the second-carrier run limit is 52 dBc Carrier Aggregation click to expand +

Ties CA back to RCT: when two carriers transmit together, the ACLR limit for the second-run bands relaxes from 55 → 52 dBc

Why it exists
With two carriers active the PA runs closer to its limits and inter-carrier products raise adjacent-channel leakage, so a single-carrier target (PW internal 55 dBc) is unrealistically tight for the second run. The KPI file therefore applies a band-specific override to 52 dBc for the CA/2nd-run cases — visible in the RCT ACLR card's band-override list (b0407, b0307_2nd_run, b082028_2nd_run, b41_1st_run → 52). It's still well above the 3GPP 45 dBc floor.
How it's applied in RCT
# limits_validation_aclr() resolves the band override first:
band_min_limit[ f"{fhgw_band}_{dualband_step}" ]  # e.g. "b0307_second_run" -> 52
# else band_min_limit[fhgw_band]  else global min_limit (55)
aclr_pass_limit = min_limit - tolerance
# each of the 4 offsets must be > limit  (higher dBc = better)
See card FC01T (ACLR Automation Trace) for the full path; this is the CA-specific limit branch.

Debug checklist
Second run fails at 55 but should be 52 → band/step key not matching band_min_limit map → check {fhgw_band}_{dualband_step} string. ACLR worse only with 2 CCs → PA compression / DPD not tracking dual-carrier PAR → check DPD alignment. Asymmetric ACLR between carriers → uneven per-carrier power / CFR settings. Still < 52 → real leakage; inspect adjacent-channel offsets on the EXA.
Interview Q&A
Q: Why relax ACLR to 52 dBc on the second run? Two active carriers push the PA harder and create inter-carrier intermodulation, so leakage rises; 52 is a realistic dual-carrier target still 7 dB above the 3GPP 45 floor.
Q: Where does that 52 come from in code? The band_min_limit override in the KPI file, keyed by {fhgw_band}_{dualband_step}, applied inside limits_validation_aclr.
Q (PW): If B3 passes ACLR single-carrier but fails in B3+B1 CA, what's your first check? DPD convergence for the dual-carrier waveform and whether the correct 52 dBc override is being selected for the second run.
PD01 PDCP Debug — ciphering mismatch, ROHC context, SN wrap Protocol Debug click to expand +

PDCP = ciphering, integrity, header compression (ROHC), SN + reordering · top of the L2 stack, just under RRC/IP

Why it exists / what breaks
PDCP secures and orders each bearer's PDUs. Three classic failure families: ciphering/integrity mismatch (wrong key or algorithm → garbage after decryption / MAC-I failure → the UE can't decode anything), ROHC context desync (compressor/decompressor disagree → headers can't be rebuilt → packets dropped), and SN wrap / HFN desync (the sequence number rolls over and the two ends disagree on the hyper-frame number → COUNT mismatch → deciphering fails).
Where each failure shows up
COUNT = HFN : PDCP-SN            (input to ciphering)
cipher mismatch : SecurityModeComplete ok, then user-plane
                  fails -> decode errors, no throughput
integrity fail  : MAC-I check fails on SRB -> RRC msg discarded

CSI01 CQI — Channel Quality Indicator: meaning, MCS mapping, logs CSI Reporting click to expand +

LAT01 LTE / 5G Latency — components, targets, how 5G hits sub-ms Latency click to expand +
Why it matters
Latency is the round-trip a packet sees. It caps VoLTE mouth-to-ear delay, interactive gaming, TCP throughput (throughput ≈ window / RTT), and is the whole point of URLLC. Two flavours: control-plane (state transition) and user-plane (packet in→out).
Components (user plane)
U-plane latency = UE proc + TTI(1 ms LTE) + HARQ RTT(~8 ms if retx) + gNB proc + scheduling/queuing + propagation + S1/N3 + coreEach HARQ retransmission adds ~8 ms in LTE, so BLER directly inflates latency.
Targets vs reality
MetricTarget / typical
C-plane idle→connected< 50 ms
C-plane dormant→active< 10 ms
U-plane (LTE, ideal)< 5 ms one-way
U-plane (real lab)~11 ms RTT test set, 20–50 ms carrier lab
5G NR URLLC< 1 ms one-way
How 5G cuts it
Higher numerology → shorter slot (0.5/0.25 ms, see PT15), mini-slots (start mid-slot), self-contained slot (data + HARQ-ACK in one slot), and edge UPF placement. In your lab, measure with ping/iperf RTT; a cabled bench typically shows ~10–11 ms RTT.

Q: Why can 5G reach <1 ms when LTE floors near 4–5 ms? Shorter TTI (mini-slot + high SCS), self-contained slots that carry HARQ-ACK in the same slot, and faster processing budgets.
Q: A UE has great CQI but high latency — where do you look? HARQ retransmissions (each ~8 ms in LTE) and scheduling/queuing delay, not the radio strength.

RLF01 Radio Link Failure — N310/T310/N311, re-establishment, T311 RLF click to expand +
Why it matters

Detection & recovery sequence

ROHC01 ROHC Header Compression — the VoLTE header fix ROHC click to expand +
Why it exists
A VoLTE voice packet is only ~30 bytes of AMR payload but carries a 40-byte (IPv4) or 60-byte (IPv6) RTP/UDP/IP header — more overhead than data. ROHC (in the PDCP layer) compresses that header down to 1–3 bytes, roughly doubling voice capacity.
Modes & context
U-mode (unidirectional, no feedback), O-mode (bidirectional optimistic), R-mode (bidirectional reliable). Compression starts with IR packets (full header) that build a context at both ends; after that only changed fields are sent (SN increments, timestamps are inferred).
Profiles (TS 36.323)
ProfileCompressesUse
0x0001RTP/UDP/IPVoLTE voice (biggest win)
0x0002UDP/IP—
0x0004IP—
SIP signalling usually is NOT ROHC-compressed — processing cost outweighs the saving.
Failure handling
If the compressor/decompressor contexts desync (lost IR, HO), decompression fails and packets drop until an IR refresh re-establishes the context — this is the ROHC case in the PDCP debug card (PD01). On HO, PDCP re-establishment resets the ROHC context.
Interview Q&A
Q: Why ROHC for voice but not for a file download? Overhead is a huge fraction of a tiny voice packet but negligible for large data payloads.
Q: Packets drop only after a handover — ROHC angle? ROHC context lost/reset at HO; forcing IR refresh (or disabling ROHC) isolates it from ciphering.

SCFDMA01 SC-FDMA / DFT-s-OFDM — the low-PAPR uplink waveform PHY click to expand +
Why the uplink is different
OFDMA (used on the downlink) sums many subcarriers → a high Peak-to-Average Power Ratio (PAPR). A UE PA would have to back off to stay linear, wasting power and hurting cell-edge coverage. So LTE UL (and NR when configured) uses SC-FDMA / DFT-s-OFDM, which has a single-carrier-like envelope and ~2–3 dB lower PAPR → the UE PA runs closer to saturation, more efficiently.
The one extra step: DFT precoding
OFDMA (DL): symbols --------------------> subcarrier map -> IFFT -> +CP SC-FDMA(UL): symbols -> M-point DFT (spread) -> subcarrier map -> IFFT -> +CPThe added DFT spreads each symbol across all allocated subcarriers before the IFFT, so the time-domain signal behaves like a single carrier. Receiver (eNB) does the inverse (FDE + IDFT) — complexity is pushed to the base station, which is fine.

NR PUSCH supports both: CP-OFDM (default — higher throughput + easier MIMO) and DFT-s-OFDM (transform precoding enabled — for coverage/cell-edge, power-limited UEs). DL is always CP-OFDM. Ties to your link budget: the low-PAPR UL waveform is part of why UL sensitivity/coverage holds up.
Interview Q&A
Q: Why not use OFDMA on the uplink too? Its high PAPR forces UE PA back-off — wasteful and coverage-limiting; DFT-s-OFDM keeps a single-carrier envelope for PA efficiency.
Q: When does NR pick DFT-s-OFDM over CP-OFDM for PUSCH? For coverage/power-limited UEs (transform precoding enabled); otherwise CP-OFDM for peak throughput and MIMO.

PAG01 Paging Procedure — reaching an idle UE Paging click to expand +
Why it exists
An idle UE has no connection, so the network can't just send data. Paging is how the core reaches it — for mobile-terminated calls/data, SI change, or ETWS/CMAS — while the UE mostly sleeps (DRX) to save battery.
DRX, PF and PO
UE sleeps; wakes only at its Paging Occasion (PO) in its Paging Frame (PF): PF: SFN mod T = (T div N) x (UE_ID mod N) UE_ID = IMSI mod 1024 T = min(UE-specific DRX, defaultPagingCycle) ; Ns selects the PO subframeAt the PO the UE checks PDCCH for the P-RNTI; if present it reads the paging message (PCCH) on PDSCH.
Message content & response
pagingRecordList → ue-Identity (S-TMSI preferred, IMSI if needed), cn-Domain (PS/CS), plus systemInfoModification / etws-/cmas-Indication flags (see EB01). If the UE finds its identity, it launches RRC Connection Request → Service Request.

Q: How does a sleeping UE know when to listen? Its PF/PO are derived from its IMSI and the paging cycle, so it wakes only at those occasions to check PDCCH for P-RNTI.
Q: S-TMSI vs IMSI in paging? S-TMSI is used normally (shorter, privacy); IMSI paging is a fallback (e.g. after a network failure / UE unreachable by S-TMSI).

TA vs cell
A Tracking Area is a group of cells; each cell broadcasts its TAC in SIB1, and TAI = PLMN + TAC. The MME gives the UE a TAI list — the UE can roam across all those TAs without signalling, which trades a slightly larger paging area for far less update traffic.

What they test
The basics, fast: data structures, string/dict work, list/dict comprehensions, file I/O, regex, and a clean function. If you can read a file, extract numbers with regex, and return a pass/fail, you clear most first-round Python screens.

# --- a clean function with type hints + docstring ---
def dbm_to_watt(dbm: float) -> float:
    """Convert power in dBm to watts."""

# --- file read + regex extract ---
import re
with open("rct.log") as f:                 # 'with' auto-closes the file
    text = f.read()
aclr = [float(x) for x in re.findall(r"ACLR[:\s]+([\d.]+)\s*dBc", text)]
worst = min(aclr) if aclr else None        # ACLR: higher is better -> worst = min
Interview Q&A
Q: list vs tuple vs set vs dict — when do you use each?
A: list = ordered, mutable sequence (a sweep of results); tuple = immutable record (a fixed (band, freq) pair, usable as a dict key); set = unique membership with O(1) lookups (which preambles were detected); dict = key→value mapping (per-band limits, per-ADC offsets). Pick by whether you need order, mutability, uniqueness, or lookup.
Q: Why use 'with open(...)' instead of open()/close()?
A: The context manager guarantees the file is closed even if an exception is raised mid-parse — no leaked handles. Same reason you wrap instrument/SSH sessions in context managers in test code.
AUTO02 Python — parse a log / result file and decide pass/fail Automation click to expand ▾
The most common "write code" task for a test engineer
Given a log/CSV of measurements, extract the numbers, apply the 3GPP limit (with tolerance and direction), and emit a verdict. This is exactly what an RCT measure function does.
import re, csv

def evaluate_aclr(log_path, limit_dbc=55.0, tol=0.0):
    """Extract ACLR values, return (worst, verdict). ACLR: higher is better."""
    with open(log_path) as f:
        vals = [float(m) for m in re.findall(r"ACLR[:\s]+(-?[\d.]+)", f.read())]
    if not vals:
        return None, "NO DATA"
    worst = min(vals)                          # worst-case adjacent channel
    if worst >= limit_dbc:            verdict = "PASS"
    elif worst >= limit_dbc - tol:   verdict = "PASS (tolerance)"
    else:                             verdict = "FAIL"
    return worst, verdict

# CSV of per-band results -> summary
def summarise(csv_path):
    rows = list(csv.DictReader(open(csv_path)))
    for r in rows:
        p = float(r["power_dbm"])
        r["verdict"] = "PASS" if abs(p - float(r["rated"])) <= 1.5 else "FAIL"
    fails = [r for r in rows if r["verdict"] == "FAIL"]
    print(f"{len(rows)-len(fails)}/{len(rows)} passed")
    return fails
Direction matters
ACLR / sensitivity margin: higher is better → worst = min, pass if >= limit. EVM / power-error / spurious: lower is better → worst = max, pass if <= limit. Get the direction wrong and every verdict inverts — a classic interview trap.
Interview Q&A
Q: Given a log, print the worst ACLR and pass/fail against 55 dBc — how?
A: Read the file, regex-extract the ACLR numbers, take min() (higher-is-better so the worst is the smallest), compare to 55 with any tolerance, return PASS/FAIL. Guard the empty case. That's the evaluate_aclr function above.
Addition — scaling up: a config-driven log-to-Excel parser for time-series RAN analysis
From pass/fail on one value to a time-series view of a whole run. A RAN log tool used for 3G and later 4G stack logs scales the regex idea above into a config-driven parser: one table entry per worksheet with active (build it or not), a list of regexes, the column names, copyToMaster (copy into a master sheet that feeds the charts), count (count occurrences into an overview sheet), forced-value (give an event with no number a fixed value so it can be plotted) and forced-format (keep a captured group as text). Each log becomes an Excel workbook with tables and charts (XlsxWriter); a batch script walks archives and parses every log; binary traces first go through the stack's decoder to produce text.
import re, xlsxwriter

# one entry per worksheet: the parser is driven by data, not by code
SHEETS = {
  "UL BLER": {"active": True, "copyToMaster": True, "count": False,
              "regex": [r"^(\S+ \S+).*\[ULHARQ\] ue=(\d+) bler=([\d.]+)"],
              "columns": ["time", "ue", "bler"]},
  "UE attach": {"active": True, "copyToMaster": True, "count": True,
              "regex": [r"^(\S+ \S+).*\[UECounting\] UE (added|deleted) .*imsi=(\d+)"],
              "columns": ["time", "event", "imsi"],
              "forced-format": {3: "string"}},   # IMSI must stay text in Excel
}

def parse(log_path, out_xlsx):
    rows = {name: [] for name, s in SHEETS.items() if s["active"]}
    pats = {n: [re.compile(r) for r in SHEETS[n]["regex"]] for n in rows}
    with open(log_path, errors="replace") as f:
        for line in f:
            for n, plist in pats.items():
                for p in plist:
                    m = p.search(line)
                    if m: rows[n].append(m.groups())
    wb = xlsxwriter.Workbook(out_xlsx)
    for n, data in rows.items():
        ws = wb.add_worksheet(n[:31]); ws.write_row(0, 0, SHEETS[n]["columns"])
        for i, r in enumerate(data, 1):
            for j, v in enumerate(r):
                if SHEETS[n].get("forced-format", {}).get(j + 1) == "string": ws.write_string(i, j, v)
                else:
                    try: ws.write_number(i, j, float(v))
                    except ValueError: ws.write(i, j, v)
        # add a line chart of the last column vs time (omitted for brevity)
    wb.close()
Why bother? A 15-minute KPI says how often something went wrong; a time-series plot of BLER, UE count, DL/UL rate, per-link power and RTWP shows when, and what moved with it. Correlation across traces is where root causes appear.
"Massaging" captured values into engineering units is part of the job — e.g. converting the timing-advance index into UE distance in metres when the trace does not provide it.
Tips: force IMSI and other long digit strings to text, or Excel turns them into floating-point numbers and loses digits; keep one master sheet as the chart data source; pre-filter lines (only those your regexes could match) to speed up large logs. Limitation: offline parsing is post-mortem only. Live plotting while you run a manual test is better for controlling the scenario — e.g. timing when a UE is added or traffic starts (see EAGLE01 for a live bench timeline, AUTO14 for crash triage).
Interview Q&A
Q: Why make a log parser table-driven instead of hard-coding each regex?
A: Adding a metric becomes a config entry (regex + columns + chart flags) instead of code; non-programmers can extend it, and each worksheet can be switched on or off per investigation.
Q: What breaks when you export IMSIs to Excel as numbers?
A: Excel stores numbers as double precision with 15 significant digits, so a 15-digit IMSI can be shown in scientific notation or rounded; write it as a string.

The framework ruauto uses
pytest is code-first: test functions named test_*, shared setup via fixtures, matrix runs via @parametrize, selection via markers, and CLI options via conftest.py (pytest_addoption). See CLI01 / FWK1 for the RCT specifics.
# conftest.py — a shared fixture + a CLI option
import pytest

def pytest_addoption(parser):
    parser.addoption("--fhgw-band", action="store", default="b0103")

@pytest.fixture(scope="session")
def band(request):
    return request.config.getoption("--fhgw-band")

@pytest.fixture

    sa = connect_exa("10.62.2.135")
    yield sa                        # test runs here
    sa.close()                      # teardown always runs

# test_tx.py
import pytest

@pytest.mark.parametrize("bw,limit", [(5,13.9),(10,16.9),(15,18.7),(20,20.0)])
def test_tx_dynamic_range(analyzer, band, bw, limit):
    measured = analyzer.measure_dynamic_range(band, bw)
    assert measured >= limit, f"{band} {bw}MHz: {measured} < {limit} dB"

@pytest.mark.conformance          # run: pytest -m conformance

    assert analyzer.measure_aclr(band) >= 55.0
Interview Q&A
Q: What is a pytest fixture and why use one?
A: A fixture provides reusable setup/teardown injected into tests by name. The code before yield runs before the test (connect the analyzer), the code after runs as teardown (close it) even on failure. Scope (function/session) controls how often it runs — session-scope to connect the instrument once for the whole run.
Q: How do you run the same test across 4 bandwidths without copy-paste?
A: @pytest.mark.parametrize with a list of (bw, limit) tuples — pytest generates one test case per tuple, each reported separately, so one failing BW doesn't hide the others.

AUTO05 SCPI instrument automation in Python (pyvisa) — EXA/EXM Automation click to expand ▾
Talk to the analyzer from Python
SCPI commands over LAN (VISA/sockets) drive the Keysight EXA/EXM. Set mode → center/span → measurement → trigger → read. See EXP2 for the command set.
import pyvisa

def measure_aclr(ip="10.62.2.135", fc_hz=2140e6, bw_mhz=10):
    rm = pyvisa.ResourceManager("@py")
    sa = rm.open_resource(f"TCPIP0::{ip}::inst0::INSTR")
    sa.timeout = 20000                       # ms
    try:
        sa.write("*RST"); sa.query("*OPC?")  # reset, wait complete
        sa.write(":INSTrument:SELect LTE")   # LTE-FDD mode
        sa.write(f":SENSe:FREQuency:CENTer {fc_hz}")
        sa.write(":CONFigure:ACP")           # ACLR/ACP measurement
        # auto-range so a low-power isolated path is not near the noise floor:
        sa.write(":SENSe:POWer:RF:RANGe:OPTimize IMMediate")
        sa.query("*OPC?")
        vals = sa.query(":FETCh:ACP?").strip().split(",")
        return [float(v) for v in vals]
    finally:
        sa.close(); rm.close()               # always release the session
The real-world gotcha (from an actual fix)
When measuring a per-RFFE isolated (lower-power) signal, the analyzer must auto-range (:SENSe:POWer:RF:RANGe:OPTimize IMMediate) or the reading sits near the noise floor and ACLR reads ~2–3 dB low (51–52 vs 54–55 dBc). Always range before an ACP read. (Real RCT fix in measure_test_Tx_ACLR.)
Interview Q&A
Q: What does *OPC? do and why query it?
A: *OPC? (operation complete) blocks until the instrument finishes the pending command and returns 1. You query it after RST/CONFig/trigger so you don't FETCh a result before the sweep/measurement is actually done — otherwise you read stale or partial data.
AUTO06 Multi-UE automation — ADB, subprocess, parallel threads, iperf Automation click to expand ▾
Drive a fleet of real UEs
Shell out to ADB with subprocess, address each UE by serial, and run actions in parallel with threads for load/throughput. See UE02/UE03/UE09.
import subprocess
from concurrent.futures import ThreadPoolExecutor

def adb(serial, *args):
    """Run an adb command on a specific device, return stdout."""
    cmd = ["adb", "-s", serial, *args]
    return subprocess.run(cmd, capture_output=True, text=True, timeout=60).stdout

def list_devices():
    out = subprocess.run(["adb","devices"], capture_output=True, text=True).stdout
    return [l.split()[0] for l in out.splitlines()[1:] if l.strip().endswith("device")]

def run_iperf(serial, server="10.0.0.1", secs=30):
    adb(serial, "shell", "svc", "data", "enable")          # ensure attached
    out = adb(serial, "shell", f"iperf3 -c {server} -t {secs} -R")  # DL
    return serial, out

# run all UEs in parallel and collect throughput
ues = list_devices()
with ThreadPoolExecutor(max_workers=len(ues) or 1) as pool:
    results = list(pool.map(lambda s: run_iperf(s), ues))
for serial, out in results:
    print(serial, "done")
Interview Q&A
Q: How do you run traffic on 10 UEs at once in Python?
A: Address each UE by its ADB serial (adb -s), then launch the per-UE work concurrently with a ThreadPoolExecutor (threads are fine here because the work is I/O-bound — waiting on adb/iperf, not CPU). Collect per-UE results and aggregate. For CPU-bound work you'd use multiprocessing instead.
Addendum — per-UE pass/fail rules, iperf and attenuator details from an E2E multi-UE job
How an E2E multi-UE job turns logs into a verdict. A CI job that loads a build, runs N simulated UEs with UL + DL traffic and collects logs needs a rule per UE, not just an average:
ClassRule (defaults)Meaning
failedUE never reached CONNECTEDAttach / RACH / RRC problem
idleIdle for more than 20 % of the testReleased too often or never re-established
partialConnected for less than 50 % of the test, or more than 1 dropoutUnstable link
successfulNone of the aboveCounts towards the throughput check
  • Throughput pass/fail compares the average bit rate of successful UEs with the target — and targets are per UE, so scale them when you add UEs.
  • Disconnects caused by the planned power-off / deregistration at the end are not dropouts (this can occasionally under-count real drops right at the end).
  • Classes overlap: failed and partial UEs are usually also idle. Not enough successful UEs = test fails.
  • On a failure, read the generated test_summary.txt first; open the raw UE-sim and DU logs only if the summary does not explain it.
iperf details that bite: UDP with -l 1410 (stay under the tunnel MTU), -B <data-plane addr> on the server so traffic does not leave via the management port, and for simulated UEs run iperf inside the UE namespace (ip netns exec ue1 iperf ...); for real phones push iperf to /data/local/tmp and start it via adb -s <serial> shell.
Programmable attenuator over serial: set <ch> <dB> per antenna port, saa <dB> for all ports, range 0–63 dB, help for the rest — easy to wrap with pyserial in the same thread pool. See AMARI01 for the UE-simulator side.

# 1) dBm <-> mW
def dbm_to_mw(dbm): return 10 ** (dbm / 10)
def mw_to_dbm(mw):  import math; return 10 * math.log10(mw)

# 2) worst-case + margin vs a limit (higher-is-better metric)
def margin(values, limit):
    worst = min(values)
    return worst, worst - limit          # +ve margin = pass

# 3) binary-search a sensitivity threshold (miss-rate <= 1%)
def find_sensitivity(measure, lo=-120.0, hi=-60.0, res=0.5):
    while hi - lo > res:
        mid = (lo + hi) / 2
        if measure(mid) <= 1.0:  lo = mid   # still detecting -> go lower
        else:                    hi = mid   # too weak -> go higher
    return lo

# 4) parse "B1=46.0 B3=44.8" into a dict
def parse_kv(line):
    return {k: float(v) for k, v in (p.split("=") for p in line.split())}

# 5) count occurrences without a library
def counts(items):
    d = {}
    for x in items: d[x] = d.get(x, 0) + 1
    return d

# 6) first duplicate in a stream (set for O(n))
def first_dup(seq):
    seen = set()
    for x in seq:
        if x in seen: return x
        seen.add(x)
    return None
Interview Q&A
Q: Write a function to find the reference sensitivity by binary search.
A: Bracket the power [lo, hi]; test the midpoint; if the miss-detection rate is within limit the UE still decodes so search lower, else search higher; stop when the range is under your resolution. That's find_sensitivity above — O(log range) instead of a linear sweep (and it mirrors the real PRACH/sensitivity search, see PRACHDM01).
Q: Why is a set the right tool for "first duplicate"?
A: Membership testing in a set is O(1) average, so one pass over the stream is O(n). Using a list and 'in' would be O(n) per check → O(n²). Same reasoning behind using a set for detected-preamble bookkeeping.

5 · Step C — the U-shaped power sweep (the clever bit)
BLER-vs-power is U-shaped: ~100% at the saturated top (ADC hits full-scale → clipping → decode fails) and ~100% at the sensitivity floor (signal in the noise), with a clean ~0% valley in between. A naïve "step down until BLER rises" would stop at the wrong edge. So the controller runs three phases:
Phase A  descend from start by COARSE step, skipping the saturated top,
         until BLER settles <= 1%   -> we are now in the clean valley
Phase B  keep COARSE-stepping down through the valley
         until BLER rises above 1%  -> we found the low-power KNEE
Phase C  back off to last-clean power, step at FINE (0.5 dB);
         once BLER >= ~1% switch to ULTRA-FINE (0.1 dB) to pin the exact 5%,
         continue down until BLER >= 99%  (fully into the floor)
mode='sensitivity' -> coarse 5 dB in the flat + 0.1 dB at knee (fast, just pins 5%)
mode='accuracy'    -> uniform 0.5 dB everywhere (dense RSSI-vs-power, no ultra-fine)
mode='both'        -> uniform 0.5 dB + 0.1 dB at knee (default: dense + exact 5%)

Interview Q&A — how a VP / senior lead will probe this
Q: Walk me through what happens end-to-end when the RSSI-accuracy test runs.
A: test_Rx_RSSI_Accuracy declares the sheet/columns/frequencies and returns them; the road-trip driver loops antenna×freq, selects the antenna and restarts L1/L2, and calls configure_test_Rx_RSSI_Accuracy. That computes setup-loss/EIRP/TRP math, reads the RU model to pick the calibration offset, loads the ETM1.1 UL waveform, then sweeps SG power in a U-aware three-phase controller. At each power _measure reads PHY rct_stats once and N samples of RU-CLI RSSI + BLER, averages them, records PHY−CLI, and writes a row. At the end _rssi_acc_report builds the xlsx + BLER/RSSI graphs and interpolates the 5% BLER sensitivity.
Q: Why compare CLI RSSI against PHY RSSI at all — aren't they the same number?
A: No — they come from different subsystems. The CLI get-rssi is what the operator/EMS sees (post-calibration, per-ADC), the PHY rct_stats is L1's internal estimate. If they diverge, either the RU's RSSI calibration/offset is wrong or the reporting path is broken. The test characterises that gap across the full power range, so a calibration error shows up as a consistent PHY−CLI diff.
Q: Why is BLER high at BOTH the top and bottom of the power sweep?
A: At the top the ADC saturates/clips (input above full-scale), so the samples are distorted and decode fails; at the bottom the signal drops into the noise floor and SINR collapses. In between there's a clean ~0% valley. That U-shape is exactly why the sweep first descends to find the clean region before hunting the low-power knee — otherwise you'd mistake the saturated top for the sensitivity edge.
Q: You read the PHY once per power step but the CLI N times — why the asymmetry?
A: The PHY value comes from tailing l1_Debug.log inside the phynode container, which only rewrites every few seconds. The N CLI reads complete in milliseconds, so reading the PHY per sample would just return N identical values plus N wasted docker round-trips. One PHY read per step, mirrored across the sample rows, is correct and much faster.
Q: How do you go from "logical antenna 2" to the right RSSI number in the CLI output?
A: get-rssi prints one line per physical ADC. A per-band mapping table (adc_mappings[fhgw_band][band][antenna_index]) translates the logical antenna to the physical ADC index — on the 5-band AAU, B28 antenna 0 is ADC 4, not ADC 0 — then I regex that line for adc_dbfs and rssi. Wrong mapping = you silently report a different antenna's power.
Q: What's EIRP vs TRP here, and where does the +3/+6 dB come from?
A: EIRP at the RU input = generator power + external_gain (which is −setup_loss, the cable/path loss). TRP adds the splitter correction: the low bands (B8/B28) feed through a 2:1 splitter (+3 dB) and the mid bands (B1/B3)/B41 through a 4:1 (+6 dB), so TRP = EIRP + that correction. It's derived from the band, with a config override.
Q: How would you extend this test to a new band or RU model?
A: Almost no code — add the band's ADC layout to adc_mappings, add the frequencies to the cadence, and populate rssi_model_offsets[model][fhgw_band][band][ant] in fdd_test_setup.json. The sweep, averaging, PHY/CLI reads and report are band-agnostic; only the mapping and calibration tables are data.
Q: If PHY−CLI diff is, say, 3 dB and constant across power, what do you conclude?
A: A constant offset points to a calibration/offset error in the RU's RSSI reporting (or a wrong rssi_model_offsets entry) — not a linearity problem. A diff that grows toward the top would suggest compression/clipping; one that grows at the bottom suggests a noise-floor/SINR issue. Constant → fix the offset table; power-dependent → investigate the analog/ADC front-end.
AUTO09 Self-Healing Traffic Watchdog — why a 24 h stability run lost UL for 15 hours, the per-stream heal loop, its parameters, and the false-restart lesson Advanced click to expand ▾
In plain English
In a 24-hour B3+B7 stability run, Band 7 uplink throughput fell to 0 and stayed there for ~15.7 hours, while downlink kept running. The radio was fine. The test harness had silently lost its UL traffic generator, and nothing noticed. The fix was a watchdog that checks every stream while traffic runs and restarts only the dead one. It records each restart, so it never hides a real RAN problem.
Level 1 — root cause: an iPerf asymmetry
DirectionWhere the sender/receiver runsAfter a radio blip
DLUDP server (receiver) on the phone, bound to the UE IPa server just waits, so it resumes when packets return: DL recovers by itself
ULUDP client (sender) on the phone, bound to the UE IPsendto() fails when the radio drops and the client process exits: UL = 0 forever
The UE re-established (new RNTI) and kept the same IP, so this was never an "IP changed" problem, just a dead sender. Nobody noticed because the test started iPerf once for 24 h and then blocked in a sequential "wait for completion" (DL first), so UL health was never checked while traffic ran.
Level 2 — the design
Replace the blind wait with a loop that runs during the traffic window. Every poll seconds, read each UE × direction's live throughput. If a stream reads ~0 for zero_streak consecutive polls, kill and restart only that UE+direction. The restart builds a fresh iPerf object, which re-resolves the UE IP (runs ip route on the phone), so it would follow an IP change for free. It never fails the test. It returns events for the report.
def monitor_and_heal(ue_list, duration, poll=20, zero_streak=3, max_restarts=10,
                     ramp_grace_polls=3, zero_threshold=1.0, require_seen_alive=True):
    streak, restarts, grace, seen_alive, events = {}, {}, {}, {}, []
    end = time.time() + duration
    while time.time() + poll < end:
        time.sleep(poll)
        for ue in ue_list:
            for d in ('ul', 'dl'):
                key = (ue, d)
                if grace.get(key, 0) > 0:
                    grace[key] -= 1
                    continue
                tpt = read_live_throughput(ue, d)
                if tpt is not None and tpt >= zero_threshold:
                    seen_alive[key], streak[key] = True, 0
                    continue
                if require_seen_alive and not seen_alive.get(key):
                    continue
                streak[key] = streak.get(key, 0) + 1
                if streak[key] < zero_streak or restarts.get(key, 0) >= max_restarts:
                    continue
                events.append(restart_stream(ue, d, remaining=end - time.time()))
                restarts[key] = restarts.get(key, 0) + 1
                streak[key], grace[key] = 0, ramp_grace_polls
    return events

Level 3 — validation: the proof and the new problem it revealed
Smoke run (200 s): the full restart path worked (read → detect → kill → restart → IP re-resolved → report). It also exposed a startup false positive: a stream still ramping read "None" in its first ~60 s and was restarted. require_seen_alive was added for this.
Overnight 12 h run: the headline result. At one point the B7 UE re-established (new RNTI). DL recovered instantly, UL stuck at 0 with UL MCS floored to 9, which is the same failure class as the original. The watchdog detected it and restarted B7 UL, and UL recovered in ~38 s instead of 15.7 h.
But: the watchdog logged 20 restarts in that night and only one was a real stall. The rest were triggered by read failures: the SSH read of the iPerf result file failed during a connectivity glitch, returned None, and the code treated None like a confirmed zero. That burned the restart budget (one stream hit its cap within 46 minutes) and briefly interrupted healthy streams.
Level 4 — the lessons (apply them to any watchdog)
1. Distinguish "I could not read it" from "I read zero". A read failure should skip the poll, not count toward the streak. Only a successful read of ~0 is a stall.
2. Corroborate before acting: a real UL stall also showed UL MCS floored at 9 in the eNB stats. Requiring a second independent signal removes most false positives.
3. Budget and grace: caps prevent storms, but false positives spend the budget you need for the real event.
4. Never hide the RAN: every heal is reported in the test message, for example Self-heal: 1 restart | [time] B7 ul restart#1 ok=True IP same. That is the breadcrumb to go and find why the UE dropped in the eNB logs.
5. Know your KPI layer: the stats tool reported eGTP (~177 Mbps offered) while the dashboard showed PDCP (~167 delivered) (LF20).
6. Test the healer: kill the phone-side UL client mid-run (adb shell pkill -f "iperf -u -c") and confirm a restart within ~poll × zero_streak seconds.
Interview Q&A
Q: In a long test, UL throughput went to 0 and stayed there while DL recovered after a radio blip. Why, and how do you fix it?
A: With iPerf the DL receiver on the phone is a UDP server that simply resumes, but the UL sender is a client process on the phone that exits when sendto() fails during the outage. Nothing restarted it because the test blocked in a sequential wait. Fix: a watchdog that polls each UE+direction, restarts only the dead stream after N consecutive zero reads (re-resolving the UE IP), caps restarts, and reports every event.
Q: Why debounce with a zero-streak and add ramp-grace / seen-alive rules?
A: Throughput naturally dips for a second or two, and a new stream reads nothing while it starts. Without debounce and grace the watchdog restarts healthy streams, disrupting the test and wasting its restart budget.
Q: Your watchdog restarted streams 20 times but only one stall was real. What went wrong?
A: It treated a failed read (SSH/tail error returning None) the same as a confirmed zero. Separate the two: a read error skips the poll, and only a successful ~0 reading counts. Optionally require a corroborating signal such as UL MCS dropping to the floor in the eNB stats.
Q: Why must a self-healing test still report every heal?
A: Healing keeps the test running, but the underlying cause (why the UE dropped) is a potential RAN bug. The logged time, stream and outcome let you correlate with eNB/CWS logs afterwards. Silent healing would hide defects.

    results = {}
    for rsrp_target in levels_dbm:
        set_attenuation_for_rsrp(rsrp_target)
        ok = 0

            ue_power_cycle()

def link_adapt_sweep(att_steps_db, dwell_s=30):
    rows = []

        time.sleep(dwell_s)
        rows.append(dict(att=att, rsrp=ue.rsrp(), **du.snr_cqi_ri_mcs_bler(), **iperf.rates()))

What a healthy link-adaptation trace looks like. As SNR falls, CQI falls, the scheduler steps MCS down, RI drops (4 → 2 → 1 layers), and BLER stays near the scheduler's target (typically around 10 %) because outer-loop link adaptation keeps correcting. Throughput should slope down. A cliff with BLER shooting up means link adaptation is not keeping up, and that is a finding in its own right.
Why "recovers at 0 dB" is part of the pass: 161 of 166 Mbps (about 97 %) proves the cell and UE came back to full rate after being pushed to the edge. A stuck low MCS or rank after the sweep (the same failure class as AUTO09) would otherwise hide.
Why 5 power cycles per level: RACH is statistical. One attach proves nothing. Power-cycling the UE forces a fresh initial access (cell search → PRACH → RAR → RRC setup) every time, and 5 tries per level gives a success-rate percentage.

Why RACH at the cell edge is an uplink problem: the x-axis is downlink RSRP, but access fails when the RU cannot detect the preamble. The UE sets its PRACH power by open-loop power control (target received power + estimated path loss), capped at its maximum of about 23 dBm. Past that point every extra dB of path loss arrives at the RU as a weaker preamble. A receiver with a sensitivity problem reaches its detection limit much earlier, so access dies at a much stronger DL RSRP.
The same fault also stalled B28 TCP: DL TCP needs a steady flow of UL ACKs. When UL is weak, ACKs are lost and DL TCP stalls even though the DL radio is fine. If a DL TCP number looks bad, always check UL health too (and use UDP to separate the two directions, see AUTO12).
Cross-check with conducted RCT: the conducted B28 campaign (FC09D) had already measured a receive-sensitivity shortfall and poor PRACH detection on B28, while B3 passed. The E2E sweep reproduced the same conclusion independently. Do not expect the dB numbers to match one-to-one: an E2E coverage limit also includes UE power control, PRACH detection thresholds and the unit's fault-20 behaviour. Treat the E2E sweep as corroborating evidence and the conducted test as the measurement.
Pitfalls: (1) all four RX/TX ports must be attenuated equally, or the rank and MIMO behaviour is not representative. (2) Give each step enough dwell time for CQI and outer-loop link adaptation to settle before you sample. (3) Report against UE RSRP, not attenuator dB, because the path-loss offset differs per band and per cable set.
Interview Q&A
Q: How do you automate a coverage or cell-edge test in the lab?
A: Put a programmable attenuator between the RU and the UE, run continuous traffic, and step the attenuation. At each step, wait for the link to settle, then log the UE RSRP, the DU SNR/CQI/RI/MCS/BLER and the throughput. Finish by returning to 0 dB and checking that throughput recovers. For access coverage, repeat attach N times per level and record the success rate.
Q: B3 reached -110 dBm RACH coverage but B28 only -85 dBm on the same DU. What do you conclude, and why?
A: The shared parts (DU, EPC, UE type, method) are cleared by the B3 control case, so the problem is on the B28 RRH. RACH at the edge is limited by preamble detection in the RU uplink, so a 25 dB gap points to a B28 receive problem. That matched the unit's fault-20 and the conducted sensitivity finding.
Q: DL TCP throughput stalls at cell edge but DL UDP is fine. Why?
A: TCP depends on UL ACKs. A weak uplink loses ACKs, the TCP window collapses and DL stalls, even though the DL radio link is healthy. Test each direction with UDP to separate the radio from the transport.
Q: What should link adaptation look like as the signal fades?
A: A smooth decline: CQI and MCS step down, rank drops from 4 to 1, and BLER stays near its target while outer-loop adaptation corrects. Then a clean recovery when the signal returns. A cliff edge or a stuck low MCS after recovery is a defect.

How a scenario CSV becomes test cases (a teaching sketch; column names other than the filter keys and pass-% fields are illustrative):
import csv, pytest

def load_scenarios(path, flt):
    with open(path, newline="") as f:
        rows = list(csv.DictReader(f))
    return [r for r in rows if all(r.get(k) == v for k, v in flt.items())]

def pytest_generate_tests(metafunc):
    if "scenario" in metafunc.fixturenames:
        flt = metafunc.config.scenario_filter          # e.g. {"direction": "DL_UL", "protocol": "TCP"}
        rows = load_scenarios("throughput_scenarios.csv", flt)
        if not rows:
            raise pytest.UsageError(f"scenario_filter {flt} matched 0 rows")
        metafunc.parametrize("scenario", rows, ids=[r["name"] for r in rows])

def test_throughput(scenario, traffic, kpi_poller):
    res = traffic.run(scenario)                      # iperf, per direction
    kpis = kpi_poller.summary()                      # PRB, MCS, RI, SNR, CQI, BLER
    assert res.duration_pct >= float(scenario["min_duration_pct"])
    assert res.dl_mbps >= float(scenario["dl_target"]) * float(scenario["dl_pass_pct"]) / 100
Each CSV row becomes its own test ID in the JUnit XML and the report, so one bad scenario does not hide the others.
Level 3 — traps that make benchmark numbers lie
1. A filter that matches nothing is not a pass. A typo such as bandwidth_label=15Mhz selects zero rows. pytest then exits with code 5 ("no tests collected"). If CI treats every non-1 exit as success, you get a green night with no traffic at all. Fail loudly on zero matches (as the sketch does) and make CI treat exit code 5 as a failure.
2. "Duration %" catches a dead traffic generator. If iPerf dies halfway, the average over the remaining samples can still look fine. Requiring the run to last most of its planned time catches it. AUTO09 shows the extreme version: a UL sender that died and stayed dead for 15 hours.
3. TCP vs UDP answer different questions. UDP at a fixed offered rate measures what the radio can carry (loss = datagram error %). TCP measures what an application gets, and it is limited by window size, RTT and UL ACK health (a weak UL stalls DL TCP, see AUTO11). Use UDP to benchmark the RAN, and TCP to benchmark the user experience.
4. Know the KPI layer. The UE-side iPerf number, eNB PDCP throughput and eGTP throughput differ by headers and retransmissions (LF20, AUTO09). Compare like with like across builds.
5. The radio KPIs explain the number. Low DL with RI stuck at 2 means a MIMO or channel problem, not a scheduler problem. Low DL with high PRB use and good MCS means capacity. Good RI/MCS but low PRB use means the scheduler is not being fed (the traffic source or transport). This is why PRB, MCS, RI, SNR, CQI and BLER are logged next to every throughput value.
6. CA needs UE support. An inter-band 2CC run with a UE that lacks the band combination silently falls back to 1CC. Check the UE capability (LF15) and the SCell activation before you blame the RU.
Interview Q&A
Q: Why drive throughput tests from a scenario CSV instead of separate test functions?
A: The logic is identical and only the parameters change. A CSV row per scenario means new cases need no code, a command-line filter picks a subset for CI, and each row still reports as its own test ID. It also keeps targets and pass percentages next to the scenario, where reviewers can see them.
Q: Your nightly benchmark is green but took 30 seconds. What happened?
A: Most likely the scenario filter matched zero rows, pytest collected nothing (exit code 5), and CI treated that as success. Fail on an empty selection and treat exit 5 as a failure.
Q: What pass criteria besides "throughput ≥ X % of target" would you add, and why?
A: Datagram error % for UDP (the offered traffic really got through), and duration % (the traffic ran for its whole window, so a dead iPerf cannot pass on a partial average). Log PRB/MCS/RI/SNR/CQI/BLER as well, to explain any miss.
Q: 2CC on this bench is B3+B3. Why not B3+B28?
A: Inter-band CA needs a UE that supports the CA_3-28 band combination. With the available UE, intra-band B3+B3 (15+15 MHz) was the CA configuration that could be exercised.

Every verdict has a direction. The enum in the source is PASS_RESULT / MARGINAL_RESULT (shown as Pass(Tolerance)) / FAIL_RESULT. A summary of the rules (a sketch, not the framework code):
PASS_RESULT, MARGINAL_RESULT, FAIL_RESULT = "Pass", "Pass(Tolerance)", "Fail"

def verdict(measured, kpi, tol, better):
    if better == "higher":
        if measured >= kpi:        return PASS_RESULT
        if measured >= kpi - tol:  return MARGINAL_RESULT
        return FAIL_RESULT
    if better == "lower":
        if measured <= kpi:        return PASS_RESULT
        if measured <= kpi + tol:  return MARGINAL_RESULT
        return FAIL_RESULT
    lo, hi = kpi
    if lo <= measured <= hi:                 return PASS_RESULT
    if lo - tol <= measured <= hi + tol:     return MARGINAL_RESULT
    return FAIL_RESULT
DirectionTests
higher is betterACLR (dBc), dynamic range
lower is betterEVM %, reference sensitivity and ACS/blocking (RU input power at the BLER crossing), PRACH (input power at 1 % missed detection)
windowoutput power (low/high, or configured − measured within ± x dB), frequency error (± Hz, or ppm of the carrier)

Level 3 — why you must read this setup's files, and a correction
1. The "same" limit differs by setup file. ACLR is 54 dBc with a 1 dB tolerance inline in a 5G FHGW Test-ID, 55 dBc with a 0.8 dB tolerance in the 4G FHGW box file, and 55 dBc with 0 tolerance in the Metro file (FC16, KPI01). EVM is per E-TM in the FHGW 4G file (17.5 % QPSK, 12.5 % for E-TM 3.2, 8 % for 64QAM, 3.5 % for 256QAM, i.e. the 3GPP values), but 3.5 % for every E-TM in the Metro file. Frequency error is 0.05 ppm plus 12 Hz tolerance in one file and 0 Hz tolerance in another. Never quote a limit without naming the setup and the file.
2. Layer precedence explains "I changed the value and nothing happened". The RU pytest documentation describes the merge as setup_configuration/ → cws_sources_<tech>/ → test_inputs_<tech>/ → one test_config singleton, where later layers win. If test_inputs defines the same key, your edit in setup.json is silently overridden. Search all layers for the key before editing. For thresholds there is a similar order: a tc_cadence RRH-Thresholds override, then the KPI file, then a hard-coded fallback (FC16).
3. Groups multiply. One Test-ID in a group with 4 BWs × 3 frequencies × 4 antennas is 48 measurements, and each can have several KPIs. When a report shows "ACLR fail", the Group axes tell you which of the 48. That is the first thing to read, before the value.
4. Rules the framework documentation insists on: always run through the run_*.py wrappers (they load the config layers and the report plugins), tests never import products directly (FWK1 golden rule), and credentials in config should come from ${ENV_…} variables rather than plain text.
5. Correction to M12. The overview box in M12 lists file names such as rct_report.pdf / rct_results.json and Test IDs such as TX_POWER / SENS_B1, plus a DSA JSON example. Those are illustrative, not the real schema. Real Test-IDs are test method names (test_Tx_ACLR, test_Tx_BS_Output_Power, test_Tx_modulation_analysis, test_Rx_Reference_Sensitivity_Level, test_Rx_PRACH, ACS_7_4_1 …). Results go to report.html, the Excel workbook and Elasticsearch. The transceiver field in the real ACLR Test-ID is trx (M12 shows trb).

Q: Someone hands you a test name you have never seen. How do you work out what it does and what makes it pass?
A: Find the Test-ID in the setup's tc_cadence.json: test_type gives the analyzer mode, and 5G tests carry their KPIs inline. For 4G, look up the limit and any band override in the kpi_thresholds file. Find the Group that lists the test (band/BW/frequency/TM) and the Cadence that includes that group. A: Because the modulation-analysis measurement returns several quantities at once. Its KPI block has output power (window), EVM (max %), frequency error (± Hz) and TAE (max ns), and each is judged separately.
Q: ACLR is 54 dBc in one place and 55 dBc in another. Which is right?
A: Both. They come from different setups and files: 54 with 1 dB tolerance inline in a 5G Test-ID, 55 with 0.8 or 0 dB tolerance in 4G threshold files, and 52 for some dual-band overrides. The applicable limit is the one resolved for that setup, band and dual-band step.
Q: What is MARGINAL_RESULT and how is it computed for sensitivity?
A: It is the Pass(Tolerance) verdict. Sensitivity is lower-is-better: pass if the RU input power at the 5 % BLER crossing is ≤ KPI, marginal if ≤ KPI + tolerance (e.g. 1.0 dB), otherwise fail.
Q: You changed a value in setup.json and the test ignored it. Why?
A: The configuration layers merge in order and later layers win. A test_inputs file (or a cadence-level override) probably defines the same key. Search every layer for the key.

Level 3 — what an experienced reviewer notices
1. Stale documentation. The docstrings say 180 s and DL 45 / UL 17, and the test tag says 180s. The Variables that actually run are 600 s and 43.75 / 18.75. The Variables section is the truth. Fix docs in the same change that edits a variable.
2. Implicit coupling through suite variables. Set Suite Variable makes ${cws_b4}, ${ue_b4}, ${rsrp_b4} and others visible to resource keywords without passing them. That is convenient, but a keyword such as Verify_B4B7_Throughput_Results silently depends on a variable set three steps earlier. If you reorder or reuse steps, the failure is "variable not found" far from the cause. For new keywords, prefer explicit [Arguments].
3. Deliberate tolerance. RSRP defaults to N/A before the TRY, and EXCEPT *RSRP* *attribute* glob-matches the error text, so a failed RSRP read only logs a WARN. Throughput is the objective and RSRP is context. The defaults stop the later Excel write from hitting an undefined variable.
4. Collected but not saved. The basic Excel writer records only RSRP. The OAM KPIs (MCS, SNR, RSSI, PRB) from step f are collected but not written. The full writer is Write_B4B7_OAM_KPI_Results_To_Excel, and the comment above the call wrongly claims it writes KPI results. When throughput fails, those KPIs are the first thing you need, so swap the keyword.
5. Configuration through the management plane. The test writes cell parameters via ACS (TR-069) with read-compare-write and a conditional reboot. It never edits files on the radio. That is idempotent: a re-run on an already-configured node skips the reboot. (CM17 shows why editing a file on an AAU often does nothing.)
6. Stability, not a single measurement. The Stability tag, the crash-file snapshot in suite setup and the 600 s window make this a building block for long runs. Pair it with a stream watchdog (AUTO09) and a crash triage pipeline (AUTO14) for 24–72 h campaigns.
Where to look when it breaks: proxy or connection errors → Real UE CI-PreSuite. "No UE found with VoLTE_band4" → the UE pool config. Wrong BW or CA still on → Configure_RU_Bandwidth_And_CA_Settings. Low throughput → RSRP in the summary, then the OAM KPIs.

In plain English
When a program on Linux crashes, the system can save a core file: a snapshot of the process memory at the moment it died, like an aircraft black box. In a 48-hour unattended stability run you do not want someone opening log bundles by hand on Monday morning. This tool does it for you. It watches each new log archive from the run, looks for a core file, reads which thread died from the file name, uses a lookup table to say which component that thread belongs to (DU, CU or PHY), and emails an HTML report. A weekend of traffic becomes a list such as "Saturday 03:12, crash in DU, MAC scheduler thread", which you can hand straight to the right developer team.

Why the file name is enough to find the thread: the kernel names core files using the pattern in /proc/sys/kernel/core_pattern. With a pattern such as core.%e.%p, %e is the name of the thread that crashed (its "comm", at most 15 characters) and %p is the PID. That is why the stack names its threads carefully. MacTxCtlData_C0 is exactly 15 characters. A longer thread name would be cut short and stop matching the table.
After classification, get the stack trace. The report tells you where to look. The backtrace tells you why:
tar -xzf <archive>.tgz <path>/core.MacTxCtlData_C0.12345
file core.MacTxCtlData_C0.12345
gdb <matching-binary-with-symbols> core.MacTxCtlData_C0.12345
(gdb) bt
(gdb) info threads
(gdb) thread apply all bt
The binary must be the exact build that crashed, with debug symbols. file core.* shows which executable produced the core. A mismatched binary gives a backtrace that looks plausible but is wrong.
Level 3 — making the triage trustworthy
1. Mark every archive as checked, not only the ones with a crash. In the documented loop, checked.txt is appended only in the crash branch. An archive with no core is then scanned again on every 5-minute poll and adds another "No Core" row each time. Move the append after the if.
2. grep core is too loose. It also matches corelist.txt, score.log or a directory called core_logs/, which gives false crash alerts. It also returns several lines when one archive holds two cores, and basename of a multi-line string breaks the lookup. Match the naming pattern exactly and loop over each core:
for file in $(ls -rth /data/$SETUP_NAME/$CURRENT_DATE/*.tgz); do
    grep -Fxq "$file" checked.txt && continue
    cores=$(tar -tzf "$file" | grep -E '(^|/)core[.][^/]+$')
    if [ -z "$cores" ]; then
        ./convert_html.sh "$file" "No Core in this file"
    else
        for c in $cores; do
            name=$(basename "$c")
            ./determine_task_pod.sh "$name"
        done
    fi
    echo "$file" >> checked.txt
done
3. Ambiguous task names. recv_data_0 appears under both gnb_du_layer2 and gnb_cu_pdcp, and phy_logger under both PHY processes. A first-match lookup blames whichever section comes first. Break the tie with the archive's origin (which pod's log directory the core came from) or with file core.* (the executable name).
4. One crash, many cores. When one process dies, its peers often abort afterwards (for example a watchdog or an interface peer), leaving several cores within seconds. Sort by timestamp and treat the earliest core as the primary. The rest are usually consequences.
5. It complements, not replaces, the other stability tools. AUTO09 keeps the traffic alive and logs each heal. RBTCAUSE01 attributes RU-side reboots. This tool classifies BBU-side software crashes. A complete 24–72 h report shows all three on one timeline, so a throughput dip can be matched to a crash or reboot.
6. Sanity rules from the tool's own guidance: do a 4-hour run before a 48-hour one, watch the first 2 hours, analyse crashes within 24 hours, and try to reproduce each one in a shorter test.
Interview Q&A
Q: How would you automatically work out which component crashed during a 48-hour stability run?
A: Scan each new log archive for core files. The core file name (from the kernel core_pattern, e.g. core.%e.%p) contains the crashed thread name. Map that name to a component and pod with a table (MacTxCtlData_C0 → gnb_du_layer2 in the DU pod), write an HTML report and email the team. Then open the core in gdb with the matching symbols for the backtrace.
Q: A core file is named core.MacTxCtlData_C0.12345. What do the parts mean?
A: MacTxCtlData_C0 is the name of the thread that crashed (a MAC thread for cell 0 in the DU layer-2 process) and 12345 is the process ID. The name comes from %e in core_pattern, limited to 15 characters.
Q: Your triage reported three crashes within two seconds in DU, CU and PHY. How do you read that?
A: Most likely one primary crash and two consequences (peers aborting or being killed by a watchdog after losing their partner). Take the earliest core as the primary, get its backtrace, and check that the others are secondary before filing three bugs.
Q: The crash report keeps growing with "No Core in this file" rows for the same archives. Why?
A: Archives without a core are never added to checked.txt, so every poll rescans them. Record every processed archive, not only those with a crash.

Reading the core name: core.sig11.<app>.<...> encodes the signal (sig11 = SIGSEGV, sig6 = SIGABRT) and the application. A "(*)" in info sharedlibrary means that library has no debug info — you still get function names from its symbol table, but no line numbers or locals.

Two modes: chronological (the base point is the first point in time; best for one drive), and geographic / "consistent" (sort by latitude then longitude first, so the same place tends to get the same cluster_id on different drives). That makes a morning vs afternoon comparison possible, for example cluster 5 RSRP -85.2 vs -82.1 dBm (+3.1 dB). A sketch of both:
from math import radians, sin, cos, asin, sqrt

def haversine_km(lat1, lon1, lat2, lon2):
    dlat, dlon = radians(lat2 - lat1), radians(lon2 - lon1)
    a = sin(dlat / 2) ** 2 + cos(radians(lat1)) * cos(radians(lat2)) * sin(dlon / 2) ** 2
    return 2 * 6371.0 * asin(sqrt(a))

def cluster(points, threshold_km=0.005, geographic=False):
    order = sorted(range(len(points)), key=lambda i: (points[i].lat, points[i].lon)) if geographic \
            else range(len(points))
    cluster_id, done, next_id = [None] * len(points), set(), 0
    for i in order:
        if i in done:
            continue
        base = points[i]
        for j in order:
            if j not in done and haversine_km(base.lat, base.lon, points[j].lat, points[j].lon) <= threshold_km:
                cluster_id[j] = next_id
                points[j].timestamp, points[j].location = base.timestamp, base.location
                done.add(j)
        next_id += 1
    return cluster_id

Level 3 — the data traps (each one has broken a real drive-test report somewhere)
1. Time zones. NMEA time is always UTC. A KPI tool often logs local time. If one side is off by hours, nothing falls within 3 s, and you get a merged file with KPIs but no positions. Normalise both sides to UTC before merging, and always print how many rows merged (as the sketch does).
2. GGA has no date. The date comes from RMC. A drive across midnight UTC goes back to 00:00:00 and can merge with the wrong day unless date and time are combined.
3. ddmm.mmmm is not decimal degrees. 4807.038 means 48° 07.038', which is 48.1173°. Reading it as 48.07038° puts every point about 5 km away. Also apply the sign for S and W.
4. Talker IDs. Multi-constellation receivers send $GNGGA / $GNRMC (GN = combined GNSS) instead of $GPGGA. A parser or health check that only looks for $GP… finds zero sentences on such a receiver. Match on the last three letters of the sentence type.
5. "Consistent" clustering is only mostly consistent. Cluster IDs are assigned in sorted order. If the afternoon drive has one extra point further south (a detour, a GPS jump), every ID after it shifts by one, and the per-cluster comparison quietly compares different places. More robust options: cluster the combined points of both drives once and then split by drive, or snap points to a fixed grid (for example a geohash cell) so the ID depends only on position.
6. Fix quality and HDOP. Drop or flag points with fix quality 0, or with a high HDOP, before clustering. Otherwise a cold-start jump becomes its own "stationary location".
7. Lab "drive tests". The framework can also simulate movement with attenuators and path-loss models. That is useful for repeatable handover logic tests, but it does not reproduce fading, shadowing or real neighbour interference. Do not report simulated coverage as field coverage (AUTO11 covers attenuator sweeps).
8. Sanitise before sharing. Drive logs contain precise locations, and index names contain project or customer labels. Use neutral names for anything that leaves the team.

A: Time alignment. NMEA is UTC and the KPI tool may log local time, so the two never fall within the merge tolerance. Also check that the receiver had a fix (quality ≥ 1) and that the parser recognises $GN… talker IDs.
Q: Why cluster stationary GPS points, and how do you pick the radius?
A: So that time spent stopped (traffic lights, junctions) does not dominate per-location statistics, and so repeated visits to one spot are grouped. Pick a radius just above GPS accuracy (5 m by default, since receivers are typically accurate to 2–5 m). Larger radii merge distinct locations.
Q: You want to compare RSRP at the same places on two drives. What can go wrong with per-drive cluster IDs?
A: IDs depend on which points exist in each drive, so one extra point can shift the numbering and you end up comparing different places. Cluster the union of both drives once, or use a fixed spatial grid, so an ID means the same location in both.

Level 3 — design choices, pitfalls and coverage gaps
1. Same layers, different top. The Robot libraries are thin: they strip quotes, log the step and call the same Steps classes the pytest RCT code uses. Business logic belongs in Steps; a keyword that grows real logic is a smell.
2. Continue-on-failure is a double-edged tool. It gives a full list of IE failures per run, but a failed precondition (Xn not up, UE without IP) then produces a cascade of secondary failures. Read the first failure first.
3. Expected values from the same capture. Several counter tests compute the expectation from the pcap of the same run (ZT2). It adapts to ping-pong but is blind to a capture gap; keep one absolute sanity check.
4. Fixed sleeps and warn-on-failure injection. Many cases wait 200-700 s and inject faults with warn on failure. The test is slow and can pass without the fault having happened — check pod restart counts or PIDs, and poll for state instead of sleeping.
5. Hard-coded lab facts. SSB/ARFCN values (643968, 646716), pod name patterns (cunode01, dunode02/03, phynode, cpanode) and log paths are embedded in keywords. When a bench differs, tests fail for reasons unrelated to the feature; moving them into setup config is a cheap robustness win.
6. Visibility requirements. RRC-level IE checks need null ciphering (NEA0) and the right Lua dissector; a new message type or port needs the dissector updated before any test can assert it.
Coverage note for the owner: across all ≈3,800 robot files there are no CMAS/ETWS (public warning) tests and no conditional-handover (CHO) tests. The site has theory cards for both (PT13, EB01, EB02, HO06); either those features are verified elsewhere or they are untested here — worth asking the feature owners.

Level 3 — design lessons: verdicts, multi-user safety, contracts

Why the verdict stays blank: the Chapter 8 framework decides pass/fail only when it writes its report (verdict rules as in AUTO18). An early version of the GUI guessed the verdict row by row and disagreed with the framework on 5 of 11 tests in a real run. Lesson: never re-implement the verdict in a wrapper; display the framework's.

The multi-user rule for any instrument tool. A web tool is one process shared by every browser. If it keeps a config file or a module-level dict that request handlers read and write, two users clobber each other: last save wins, a reload shows someone else's DU address, and single-user testing never reproduces it. Hiding it behind a "Connect" button does not fix it.

DesignWhenVerdict
Per-session storageKeep state on the server keyed by session/userWorks, but you own the lifecycle (TTL, cleanup); avoid unless needed
Stateless: browser keeps settings, every request carries themEach action is one-shotRecommended default; removes the bug class
Stateless + target-keyed locked poolServer holds long-lived sessions (SSH, SCPI socket)Pool keyed by the physical target, one lock per target

Config isolation alone does not stop two operators driving the same hardware at once; that is a hardware race. The EXM Controller pattern solves it:

conns: dict[tuple[str, int], TRXConnection] = {}   # key = (host, trx_id)

class TRXConnection:
    def __init__(self, trx_id):
        self._lock = asyncio.Lock()          # one lock per physical TRX
    async def query(self, cmd):
        async with self._lock:               # serialise SCPI write + read
            ...

Two users on the same TRX serialise on one socket instead of interleaving commands and responses; two users on different TRXs run fully in parallel. For long-lived per-user state, key by an identity header rather than an anonymous cookie. A gRPC server-stream written for a single subscriber is the same bug in another form.

AAU-Sense contract: the spectrum tile (SENSE01) talks to the radio-side server over gRPC IntegSenseV1 with six RPCs (StreamPsd, GetStatus, SetAntenna, Start, Stop, SetIqDebug) on a fixed port. Changes are additive only (new fields get new tags; a V2 service is added rather than V1 edited), and StreamPsd supports multiple subscribers from day one. A fake stub emits frames of the same shape, so the GUI works identically against demo or hardware. All browser URLs are relative, so one JS bundle works standalone and embedded.

Level 3 — RAG internals, skill design and security

How a RAG code assistant is built (an RU-team assistant indexed the RU application repo):

  • Index: docs (Markdown chunker), C sources, headers and the FPGA register (CSR) JSON, about 2,011 chunks. Embeddings from all-MiniLM-L6-v2 (384-dim) in ChromaDB, plus a BM25 keyword index. The index records the git commit it was built from, so you know how stale it is.
  • Query classification sets top_k: identifier-like queries (underscores, camelCase, very short) get 15, normal questions 10, broad "explain the architecture" questions 8 (less noise).
  • Hybrid retrieval with Reciprocal Rank Fusion: score = 1/(60 + rankvector) + 1/(60 + rankBM25). A chunk found by both methods outranks one found by either alone. Vector search alone misses exact names like fault_manager; BM25 alone misses paraphrases.
  • Generation: temperature 0.3 (factual), 4-turn conversation memory, and every answer must cite its source chunks.

Skill-design lessons: skills should point into the code and docs, not copy them; when they disagree, the code wins. Every script that writes to hardware runs a dry run first. Keep transport (how to reach the box) in one skill that the others build on.

Security rules (non-negotiable):

  • Never paste tokens, passwords, customer data or production addresses into a prompt.
  • Review AI code for: subprocess(..., shell=True) with user input (command injection), unchecked file paths (traversal), SQL built by string concatenation, pickle.load / yaml.load on untrusted data, exception text leaked to users, and hard-coded secrets.
  • Personal access tokens for Bitbucket / Confluence / Jira: least privilege, an expiry date, never committed; keep them in an environment variable or a file readable only by you (mode 600).
  • Lab credentials in automation: prefer SSH keys. If sshpass is unavoidable use -e (reads SSHPASS from the environment) or -f (a mode-600 file), never -p, which exposes the password in ps, /proc and shell history (see L31).

  • Skip empty sections: an empty table in a customer report looks like a failed test. Absence plus a complete TOC is clearer.
  • Board details from the data, not the operator: the version sheet the framework wrote at run time is the traceable record of which hardware and software were measured.
  • Report, don't re-judge: the verdict belongs to the test framework (AUTO18). A report tool that recomputes pass/fail from rounded numbers will eventually disagree with the log (the same lesson as the GUI verdict in AUTO20).

Pitfalls: mixing Excel files from two different runs of the same band (the glob takes both, so keep in/ clean per campaign); screenshot folders renamed by hand (the generator matches on the Test_Band_ant pattern); and sending the .docx before refreshing fields, which leaves the reviewer with an empty TOC.

In plain English
An M-plane test framework (MPTF) sends O-RAN M-plane API commands — get, edit-config, RPCs — to a real O-RU over NETCONF and checks the replies. It is how you prove "this radio supports the YANG modules and values we need" before integrating it.

A careful assessment of one such framework found that its suites were green without proving much: a lock test that never locked, tests that passed only when the radio failed, dependency markers that silently skipped whole chains, and coverage decided in three different places — all with exit code 0. This card describes the architecture, the anti-patterns (they apply to any pytest suite that drives stateful hardware) and the data-driven design that fixes them. It pairs with AUTO03 (pytest basics) and with the M-plane field notes in ORNC01.
How a test command reaches the radio — old vs proposed
Each legacy layer had hand-written code per YANG module; a schema-driven client has none.
Level 1 — architecture and what a test really checks
  • Back end: a C++ CLI that holds the NETCONF session; built on classes generated from seven YANG bundles (one common, six vendor-specific).
  • Front end: a Python wheel that starts the back end, sends command strings and returns each reply as an XML tree (BeautifulSoup).
  • Suites: one pytest file per vendor (~1000–1100 lines each); eight diverging copies of what is really one suite, only some run in CI.
  • Two command syntaxes coexist: legacy per-module flags (--add --module-o-ran-uplane-conf --rx-array-carriers-name ...) and a schema-generic form (--root module.x .leaf value). The "new syntax" suite still used the legacy form for 37 of its commands.
Almost every test is three lines:
res = ocli.run_command("<command string with hardcoded values>")
assert res.Status == ocli.STATUS_SUCCESS, res.Error
assert res.Data.find('<leaf>', string='<value>') is not None
What that proves
Only that one radio accepts one set of values and echoes them back. It does not prove the radio behaves correctly with them (see ORNC01: an RU can accept a schema-valid u-plane config and still raise fault 15 later). All the real content — frequencies, bitmasks, VLAN ids, names — is data written as code, eight times over.

Interview Q&A
Q: Your M-plane suite is 100% green. Name three ways it could still prove nothing.
A: Tests that assert failure (pass when the radio fails); dependency markers that are no-ops or unsatisfiable so whole chains are skipped; skips and CI -k filters removing tests with exit code 0; tests whose body does not do what the name says; and read-back checks that only prove the value was echoed, not that the radio behaves.
Q: What is wrong with @pytest.mark.dependency(depends=[test_port_get])?
A: pytest-dependency expects test names (strings). Passing a function object means the dependency can never be satisfied, so the test and everything depending on it is silently skipped.
Q: Why is pytest a poor fit for an ordered scenario against one stateful radio?
A: pytest assumes independent tests in any order. Here steps mutate the radio and hand data via globals, so they only work in file order; the suite used none of parametrize/xfail/JUnit. A table of steps plus a small runner that stops at the first failure and reports a reason per row is clearer.
Q: What does a schema-driven NETCONF client buy you over generated per-vendor classes?
A: No per-module or per-vendor code: the RU serves its YANG via get-schema and the client resolves commands against it. Smaller (~18 MB vs ~345 MB), one path to the wire, and it can tell "module not served" from a real error.
Q: What can only real-hardware tests prove, and what only simulators?
A: Real HW: real firmware behaviour, RF on air, recovery after link drops, RET tilt across power cycles. Simulators: malformed protocol, FSM error branches, large scale (24 radios), rare features like NB-IoT guard band — run on every PR.

Level 3 — lessons from running real-hardware CI
  • A gate should assert only what it gates. The pod gate checks Running + all containers Ready and nothing else; "cells down" is information for later tests, not a reason to skip them.
  • Verify the test's read path before blaming the build. The advanced-smoke TX-power check failed on one setup because the test read the wrong configuration item (provisioned power read as -5 dBm against a reported 14.6–17.1 dBm window). The build was fine.
  • Timeouts multiply. A full AISG scan wait of 1100 s that never completes burns ~18 min per test; two such tests and a 120/180 min stage is aborted, leaving every later test "no result". Fail fast on missing preconditions.
  • Separate "no result" from "fail". An aborted stage produces no junit; read the Allure/console output and fix the pipeline before reading test verdicts.
  • Destructive suites need isolation — run recoverability only under a lock you hold, never on a shared rig.
  • Know what each setup can prove. A setup with no live RET skips tilt tests; a radio speaking the "other" transport skips debug-app tests by design. Record this per setup so skips are expected, not mysterious.
  • Recoverability test ideas worth copying: SIGKILL the per-vendor O-RAN daemon mid-bring-up (supervisor respawn, radio re-attaches); SIGKILL a per-connection LRCP daemon (no respawn, radio reconnect restores); drop a call-home session (reconnect inside the supervision window, no fault escalated); reboot a radio (M-plane-disconnect alarm raise → clear, AISG re-init); restart rrhmgr (re-reads its DB rows unchanged); ACS radio inventory matches the BBU exactly after recovery.

Level 3 — what the review actually found
Product defects exposed by looking for gaps:
  • Fault code mis-parse: lrcpsrv treats a response as failed only when the attribute equals 0x81, so a 0x0881 INVALID_PARAM_VALUE reply reads as success. A single negative rig sending the 18 fault codes would have caught it.

  • Latent flake: the O-RAN supervision expiry of 182 s is below the 186 s measured runtime of one RET rig — invisible only because the sim never emits supervision notifications.
  • Gate-script bug: a helper build failure did not fail the suite because the record function was called with arguments in the wrong order, so the fail counter never moved. Test infrastructure needs tests too.
Weak-oracle patterns to avoid:
  • decoding replies by arrival order instead of checking message id, version and length;
  • asserting state only through log substrings (see RUOPSLOG01) instead of reading the database back;
  • frozen payloads (always 4G, 20 MHz, 2 antennas, txPower 230 = 23.0 dBm) — a sweep would have sent at least one NR SET_FREQ;
  • binding a listener to all addresses, so the destination-address contract (loopback port) is never asserted;
  • oracle files that no code loads and hand-written report blurbs that drift from what the rig really runs.
Take-away: "the suite is green" says nothing about the 85 % of OAM message ids it never sends. Publish the coverage table next to the verdict.

RUOPSLOG01 RU-Daemon Logging — the socat/stdout trap, the runit → svlogd chain, the structured line format, levels and log-level controls Automation click to expand ▾
In plain English
The radio-control daemons on a BBU (rrhmgr, ornc for O-RAN radios, lrcpsrv for LRCP radios, uidscan for the AISG bus) run in a Kubernetes pod that is recreated between runs, talking to a radio at the far end of a fibre. There is no debugger. The log is the instrument — and it has four readers: the engineer triaging a field bug, the test rigs that wait for exact log strings, Filebeat/Elasticsearch which parse key=value pairs, and (if you get it wrong) the radio itself.

This card explains how a line gets from a daemon to a file, the one structured line format, the naming rules that make lines machine-readable, and the classic trap: printing to stdout sends bytes down the radio's TCP socket. Useful both for reading logs during triage and for writing test automation that waits on them.
Figure — where a log line goes (and where stdout goes)
One lrcpsrv per radio, one ornc per calling-home O-RU, one uidscan per client; each is exec'd over its connection.
Level 1 — the pipeline and the format
Why stdout is forbidden. socat accepts the radio connection and, with the nofork option, execs the daemon in place:
socat tcp-listen:${PORT},fork exec:"$PROG ...",nofork
The radio's TCP socket becomes the program's stdin and stdout; no relay sits in between. So console logging is built on a stderr sink. rrhmgr is the one exception (nothing execs it over a socket, so it logs on stdout) — do not copy that into a socat-started program.
How it is collected. The runit run script starts with exec 2>&1 (the redirection survives exec, so it covers socat and its child), runit pipes the stream to the paired log service, which runs svlogd into /var/log/sv/<service>/current and forwards to syslog. An empty current file is the first symptom of a daemon that never started.

Per-component reality (know it before you write a grep): rrhmgr and ornc follow the format; lrcpsrv puts the source location first, tags only errors (ERROR:) and does not strip trailing newlines; rrhmgr truncates each message at 1024 bytes including the source location.
For automation writers: wait on the event name (e.g. a ..._SUCCESS / ..._FAILED pair, or an inventory-complete marker) with a timeout, never on free prose or field order. Keep the list of markers in one file so a rename breaks one place, visibly.
Level 3 — rules that prevent painful bugs
  • Never log XML, JSON or hex dumps from rrhmgr — they get cut at 1024 bytes. Log a length and an identifier instead.
  • Never pass a runtime string as the format (format-string bug). Build text separately and log it with "%s".
  • Wire structs are not NUL-terminated. Print a char array from a packed IPC struct with a width matching the field (%.80s, %.240s), or you read past it.
  • No newline in a format string — lrcpsrv does not strip it, so one event becomes two lines and breaks parsers.
  • Flush before _exit() in a forked child: spdlog buffers inside its sinks, so the tail of the log (usually the interesting part) is lost otherwise.
  • Never log a credential or a NETCONF payload that carries one.
  • An event name is a contract. Rigs and dashboards depend on it; renaming or reordering keys fails a test for a reason invisible in the diff. Grep the test tree first.
  • Legacy shapes stay legacy: free prose, Underscore_Joined_Phrases, ticket ids in text exist only because rigs depend on them; do not copy them.
  • Static per-process counters (e.g. a transaction counter) are only safe because there is one lrcpsrv per radio; do not reuse the pattern in a multi-radio process.
Why it matters in practice: a single stray debug print in a socat-started daemon corrupts the radio protocol and produces a symptom (radio drops, parse errors on the radio side) that looks nothing like a logging bug — and the print itself never appears in any log.
Interview Q&A
Q: Why must the ornc and lrcpsrv daemons never write to stdout?
A: socat execs them in place over the accepted radio connection (nofork), so stdin/stdout are the radio's TCP socket. Anything printed is sent to the radio, corrupts the protocol and never reaches a log. Console logging therefore goes to stderr, which runit folds into the log with exec 2>&1.
Q: The /var/log/sv/<service>/current file is empty. What does that tell you?
A: The daemon most likely never started (nothing reached stderr). Check the run script, the socat listener and the supervise status before reading other logs.
Q: How would you make a log line easy for both humans and test rigs?
A: One event per line: level, rrhId= for the radio, an UPPER_SNAKE event name with the outcome in it, lower_snake keys carrying units, flags 0/1, transaction id last, source location at the end. Rigs then wait on the event name, and Elasticsearch parses the pairs.
Q: How do you get more detail from ornc on a running stand?
A: Set ORNC_LOG_LEVEL (for example debug,timestamp) for the container and restart that service; reset to info afterwards. DBG is for traffic-proportional detail.
Q: Why should an automated test not grep for the position of the [file:line] tag?
A: Different builds and components place it differently (end for ornc/rrhmgr, front for lrcpsrv and one rrhmgr build). Anchor on the event name and keys instead.

In plain English
How do you regression-test a 5G PHY on every commit without a radio, a UE or a signal generator? Level 3 — strengths, limits and pitfalls
Why bit-exact vectors work for a PHY: the PHY is deterministic for a given input, so the reference can be compared exactly (or with tight tolerances for IQ). A failing case points to a specific channel and configuration, which a live over-the-air test never does. The weakness is coverage: the vectors only test what someone captured, and real-time behaviour (timing, starvation, fronthaul) is not exercised — timer mode closes part of that gap by driving the real WLS/FAPI interface.

Pitfalls and good practice
  • Per-commit CI uses a reduced UL set for speed; a UL regression can pass CI and fail the nightly full set. Check nightly results before release.
  • Vector submodules must match the PHY version: a FAPI change without regenerated vectors fails every case at once — recognise the pattern before triaging cases one by one.
  • The dissector, PHY and stack must be generated from the same message-definition version; a mismatched plug-in silently mis-decodes fields.
  • A decode that disagrees with the spec is not necessarily wrong: the stack uses a dated FAPI dialect with deviations (see CM34). Trust the generated decoder, then compare with the spec.
  • Licensing: a Wireshark dissector uses Wireshark bindings, so if it is ever distributed outside the company it must be under GPLv2.
  • Always keep the JUnit XML and the per-case compare log as artefacts; "FAIL" without the diff is not actionable.
Interview Q&A
Q: How can you regression-test a PHY without a radio?
A: Use test vectors: per case, the input FAPI messages and UL IQ plus the reference FAPI output and DL IQ. Run the PHY on a server, feed the inputs and compare the output with the reference.
Q: What is the difference between dummy mode and timer mode?
A: Dummy mode feeds the vectors to gnb_app from files. Timer mode uses a test MAC that sends the same content as real FAPI messages over the WLS interface, so the stack interface is exercised too.
Q: Why generate the Wireshark dissector instead of writing it by hand?
A: It is produced from the same macro header that generates the PHY and stack structs, so it cannot drift from the code when messages change.
Q: What C-to-Lua trap did the generator have to handle?
A: In Lua the number 0 is true, unlike C; boolean expressions from the C definitions are converted to explicit numeric comparisons.
Q: Your per-commit CI is green but nightly fails on UL. Why might that be?
A: Per-commit runs a reduced UL vector set; the nightly full set covers more bandwidths, antenna and channel configurations, so it catches regressions the subset missed.

Addendum — measuring what the PHY regression actually exercises (gcov / lcov)
A green regression only tells you the tests passed, not how much of the PHY they touched. The 2G PHY team measured it after moving from the Intel compiler to gcc, with the standard GNU tool chain:
./build.sh -p -g --coverage                 # instrumented build (gcc: -fprofile-arcs -ftest-coverage)
lcov --gcov-tool gcov-12 --directory build --capture --initial -o coverage_base.info   # zero baseline: every line, hit 0
./test.sh                                   # unit + SDK kernel tests + pipeline tests (native AVX-512)
lcov --gcov-tool gcov-12 --directory . --capture -o coverage_test.info
lcov --add-tracefile coverage_base.info --add-tracefile coverage_test.info -o coverage_total.info
genhtml coverage_total.info --output-directory coverage_html
Why the --initial baseline: files that no test ever loads produce no coverage data at all and silently vanish from the report, inflating the percentage. The zero baseline lists every compiled line, so untouched files show up as 0 %.

Result on a 2G PHY code base: 75 % line and 69 % function coverage across about 80 directories — 23 at 0 %, 33 partial, 25 at 100 %. The old fixed gate had been 37 % on an emulated build, which says little; the per-directory view is what drives action. Kernel libraries (CRC, equaliser, Viterbi) and the pipeline tests were 99–100 % covered, while the 0 % areas were the standalone test/control applications and the fronthaul, timing and control framework — code that only runs in an end-to-end pod (call and handover tests, G2FEAT01), not in unit tests. Timer-mode and MATLAB co-simulation tests were left out because they are slow, so a few paths are under-reported.
Lessons: report per directory, sorted from 0 % up, with an owner and a note for each gap; separate "not testable in unit tests" (needs E2E) from "untested"; exclude third-party code explicitly rather than letting it drag the number down; do not chase 100 % on real-time framework code — target the signal-processing and message-handling paths where a regression would hit the air interface.

In plain English
Before you refactor code that runs on a radio, you want a safety net: tests that pass against today's behaviour, so that if a test goes red mid-refactor you know you changed behaviour and can decide whether you meant to. The RU application repository (ru-app) has a host-side test framework with three hand-written lanes that run on any Linux build machine and in CI, without a radio: bash tests for shell scripts, Python validators for JSON/YANG/config files, and compiled C tests (CMocka) for manager-app logic. Anything that needs real FPGA, I2C, PTP or a sysrepo datastore belongs to on-target tests instead.

The rule of the framework is simple and worth copying anywhere: pick the cheapest lane that gives a real verdict, and a suite that produces no results is a failure, never a pass. Related: RUBOOT01 (the managers these tests protect).

Techniques that make tests trustworthy
  • _Static_assert plus must-fail compile targets to pin struct sizes and type rules at build time.
  • Use a real temporary directory (mkdtemp()) instead of mocking sysfs/file I/O — fewer mocks, more real behaviour.
  • -Wl,--wrap=malloc to inject allocation failures and test the error paths.
  • Mutation-test every new test: break the code on purpose and watch the test go red. A test that never fails proves nothing.
Refactor recipe: (1) write tests that pin today's behaviour; (2) make them green on the unmodified code and commit; (3) refactor in small steps; (4) every red case is a behaviour change you must justify or revert.

Don'ts
  • no home-made runner or assert macros — use the harness so results reach JUnit
  • never branch on a "running in CI" environment variable
  • one parametrised case per input, not a loop that collects errors
  • reset global state in every case (setup/teardown); order-dependent tests are flaky tests
  • never run the tests under sudo: root-owned result files break the next run
  • after switching branches, delete the scratch .verbuild* source copies some suites create, or a stale copy fails a check
Why "no results = fail" matters: a bash suite that does echo; exit 0 on a missing tool makes its cases vanish, and a dashboard that only counts failures shows green. Making silence a failure and skips explicit is what turns a CI badge into evidence.

In plain English
You cannot scale-test a gateway that is supposed to serve 1000 small cells and 600 000 UEs with real radios and phones. UniPerf is an in-house load generator that emulates every network element around the device under test (DUT) — eNBs with their UEs, 3G home NodeBs, 2G BSSs, MMEs, SGWs, HSS, PCRF, MSC, SGSN and even an IPSec security gateway — and drives them with scripted call models (attach / detach rates, hold times, handovers, paging …) while a DPDK-style fast path pumps user-plane packets at Gbps rates.
Typical set-up: two UniPerf machines sandwich the DUT (for example the HetNet gateway, HNG). The core-side UniPerf plays MME / MSC / SGSN / PCRF / content server; the access-side UniPerf plays eNBs, HNBs and the converged small cells (CWS). The DUT thinks it is in a live network with hundreds of peers.
LTESIM is the companion Python (ipython) simulator used when you want fine, scriptable control-plane sessions and then hand the resulting flows to UniPerf's fast path for high-rate traffic.

Level 3 — 2G/3G, SON emulation and scale-test pitfalls
2G and 3G scale testing follows the same pattern with extra rules.
  • 2G: always configure an even number of BSS, and make the UE count an integer multiple of the BSS count. Per-role environment variables decide which fast-path flow pools are allocated (GTP-U, RTP, MFPP, GPRS), whether the node is access or core, and the per-node session / node limits (e.g. SGSN role 300 k sessions, BSS role 60 sessions per CWS and up to 320 nodes). Call models: paging (rate, start delay, bulks), attach (calls, RABs per UE, data) and, for SGSN, SRNS relocation.

Pitfalls seen in scale campaigns
  • Start order matters: restart the DUT pair with the right build and config first, then the UniPerf VMs, then core nodes, then access nodes — otherwise eNBs fire S1 Setup at an MME that does not exist yet and back off.
  • The SecGW node must exist before any node that tunnels through it.
  • Canned NAS (enable 0) against a core that enforces integrity gives a wall of attach rejects that looks like a DUT bug.
  • Hundreds of emulated nodes need hundreds of alias IP addresses on the UniPerf host; check the start-up script ran.
  • Interfaces not supported in the 2019-era tool: S10, SGs (CSFB), Sv (SRVCC) and LI X1/X2 — plan other tools for those.
  • Fast-path TCP is SYN-level only; use real servers (iperf) when you need TCP congestion behaviour.
Interview Q&A
Q: Why emulate the core as well as the access side for a gateway scale test?
A: The gateway is a middle box: its load comes from both directions. A real core may not scale or be available, and emulating it lets you control timing, failures and capacity (e.g. 4 MME peers) while the access emulator generates the subscriber load.
Q: What is the difference between NAS enable 0 and 1 in the eNB call model?
A: 0 replays pre-built NAS messages (no real authentication or security, fast). 1 performs real NAS encode/decode with Milenage keys per subscriber so authentication, integrity and ciphering work against a security-enforcing core.
Q: How do LTESIM and UniPerf split the work in a throughput test?
A: LTESIM brings up the control plane (PCRF, MME-S11 sessions, attach) and exports the per-session tunnel info to CSV; UniPerf's fast path installs those flows and generates GTP-U uplink and IP downlink at the set rate (e.g. 1 Gbps).
Q: How many HO calls does a call model with 20 bulks, 1 TPS and 80 nodes generate?
A: Total = bulks x rate x nodes = 20 x 1 x 80 = 1600 handovers.
Q: The SecGW tests show tunnels up for S1-MME but no user plane. Why?
A: Each emulated interface needs its own tunnel; the GTP-U address of the emulated node needs a tunnel too, and the SecGW node must have been added before the other nodes started.
Added: why a DPDK packet generator, its design choices and the packet-size effect
Why a separate DPDK packet generator exists. The Python simulator (LTESIM) is ideal for programmable control-plane cases – edge conditions, failures, odd message orders – but cannot produce a real data-plane load, taken as more than 10 Gbit/s or 14.88 Mpps at minimum frame size. Earlier ad-hoc mixes of tunnel tools, iperf and scripts were hard to reproduce. So LTESIM sets up the calls and hands the user-plane work to a fast-path generator.
Design choices worth knowing when you read its results:
  • Stateless payload. Forwarding cost depends on packet size and rate, not on content, so payload is synthetic; size and rate can be set per access node, test duration globally. Where the gateway matches L3/L4 headers to pick a bearer, the PDN parameters from call setup are used to build matching headers.
  • Separate access-side and core-side instances are fed the TEIDs from LTESIM; the TEID space is pre-carved so a flow can be added or removed in constant time.
  • UDP-encapsulated IPsec on the access side, like real small cells behind NAT.
  • No latency/jitter control; each packet carries an empty fixed-size header reserved for future timestamps. Counters are aggregate per node rather than per bearer.
Measured with one core and a 10G NIC: ~4 Gbit/s at 64-byte packets vs ~8.9 Gbit/s at 1350 bytes. Small packets are limited by packets per second, not bits – always state packet size next to any throughput number, and test both small and large sizes (see DPDKDBG01 for gateway-side numbers).

Level 3 — design lessons and pitfalls
  • One network namespace per UE. Running each phone's tethered traffic in its own namespace lets every UE use the same content-server IP and port plan without routing clashes — the same trick Amarisoft uses for simulated UEs (AMARI01).
  • Start CS and PS calls in parallel, not one phone after another — sequential start-up stretches a 50-phone run by many minutes and hides concurrency bugs in the cell.
  • Check "latched" in a polling loop. One registration check is not enough; phones often need several seconds more. Do it in one place in the code, and update the phone list only after it.
  • Use AT+CFUN=0 → AT+CFUN=1 instead of flight mode on modems that reset when flight mode is toggled; then poll /dev/serial/by-path until every modem is back before the next step.
  • One common cleanup path for every way the script can exit, plus a generic process killer — stray iperf/adb processes were the main cause of the next run failing.
  • Stateless tool = finite tests. The web helper caps iperf at 60 minutes because a force-quit leaves remote iperf servers occupied; let a test finish so it cleans up.
  • Do not auto-reboot on latch failure — a reboot can silently drop the band lock, and the phone then camps on a different band for the rest of the soak.
  • Emergency-call tests only inside a shielded chamber.
Interview Q&A
Q: Why run each real UE's traffic in its own network namespace?
A: So that every UE can use the same content-server address and port scheme without routing conflicts on the controller; each namespace has its own routes and interface for that phone.
Q: Your 40-phone soak shows phones dropping off ADB after an hour. What do you check on the controller?
A: USB autosuspend (must be -1), USB3 vs USB2 ports and hub power, ModemManager/NetworkManager grabbing the modems, and dmesg for USB resets.
Q: What makes an Android phone suitable for automated cell testing?
A: Unlockable bootloader and root, reliable ADB, RAT and band lock that persist across reboot, and scriptable flight-mode/radio control. Without a persistent band lock it may camp on the wrong cell.
Q: Why poll for "latched" instead of checking once?
A: Registration timing varies per phone and per attempt; a single check produces false failures. A polling loop with a timeout gives a deterministic pass/fail.
Q: Why might flight-mode toggling be a bad attach/detach stimulus?
A: On some modems it resets the whole modem, so you test modem recovery instead of the network. AT+CFUN=0/1 switches the radio off and on without the reset.

Level 3 - pitfalls and expert notes
  • Counters are your trace. Compare E2SIM's per-message counters with the xApp log line by line: a Subscription Request counted on E2SIM with no subscription in the xApp means the response was lost or rejected by the RIC subscription manager.
  • Test several E2 nodes early. A known gap was that with multiple simulated eNBs indications were not triggered for all of them; single-node tests hid it. Another was a delay timer on Subscription Delete Request/Response not being honoured.
  • RAN function ids must match. The xApp subscribes to a specific RAN function id (each service model has its own) - if E2SIM registers a different id or revision the subscription fails even though E2 Setup succeeded.
  • containerd, not Docker: on a K8s RIC the kubelet only sees images in containerd's k8s.io namespace; a plain docker load leaves the pod in ImagePullBackOff.
  • Policy-type schemas: create the policy type before any policy; a PUT for an unknown type returns 404, a body that violates the schema 400 - both are good negative tests.

In plain English
Every small cell or vBBU that reaches the core over an untrusted backhaul does so through an IPsec tunnel that ends on a security gateway (often built into the HNG/aggregation gateway). Testing that gateway needs IPsec clients - one per simulated access node, and for scale tests tens of thousands of them. The PW protocol simulator embeds strongSwan (the open-source IKEv2 daemon) so that every simulated eNodeB, HNB or 2G node can bring its own tunnel up before S1/Iuh signalling starts. The same strongSwan can also play the responder (MME, SGSN, MSC, generic SecGW), and a separate scale controller drives a modified strongSwan from Python to create, hold, ping and tear down thousands of tunnels at a chosen rate. This card is the "test side" of IPsec; for debugging a real tunnel on the product see the IPsec debugging card on the Debug page.
Who drives the tunnels
Functional tests: each simulated node owns one tunnel. Scale tests: the Python controller asks the patched strongSwan to make or break thousands of tunnels.

Level 3 - scale testing details and pitfalls
  • Call types: the pw_controller plugin implements 7 ways of initiating tunnels (charon.plugins.pw_controller.call_type, default 1). Type 7 is the recommended one for gateway scale: it supports scheduled ping traffic and fast-path data pumping (rate in Mbit/s, GTP-U ports 2152).
  • Rate maths: in a call model, rate is milliseconds between initiations, so tunnels per second = 1000 / rate. Call models inside one file run in sequence (rate is respected); separate files run in parallel (aggregate rate is not guaranteed).
  • Rekey storms: for soak tests the gateway profile used DPD disabled and ESP lifetime 86400 s, otherwise tens of thousands of tunnels created in a burst all rekey in the same window. If you do test rekey, enable rekey_fuzz in the plugin to spread them.
  • Host limits: raise the interface TX queue length (default 1000) when pumping data; keep keyingtries=1 so failed tunnels are visible instead of silently retried.
  • Responder retransmits: lab strongswan.conf uses retransmit_timeout=10, retransmit_tries=2 - shorter than production defaults, so failures appear quickly.
  • What to measure: tunnels per second accepted, time to N established, CPU of the IKE daemon, ESP throughput with all tunnels pinging, and what fraction re-establishes after a gateway restart. Read failures with the drop counters described in the IPsec debugging card.
Interview Q&A
Q: Why does the simulator set charon.initiator_only=no?
A: So the embedded strongSwan can also answer IKE_SA_INIT. Then core nodes (MME, SGSN, MSC, SecGW) can terminate tunnels on the same host that runs the access-node initiators.
Q: How would you create 10,000 IPsec tunnels against a security gateway?
A: Generate or reuse a 10,000-certificate pack, start the patched strongSwan with the pw_controller plugin, then from Python call make_call(..., num_calls=10000, burst, millisecond) or run a call-model file, and watch get_tunnel_status / get_stats.
Q: What is the difference between ipsec4-prefrag on and force?
A: Both fragment the clear packet before ESP encapsulation; "on" leaves packets with DF set alone (they are dropped or trigger PMTU), "force" fragments them anyway.
Q: Which attribute types carry the P-CSCF address in IKEv2?
A: RFC 7651 defines P_CSCF_IP4_ADDRESS = 20 and P_CSCF_IP6_ADDRESS = 21 in the configuration payload; the simulator defaults to vendor types 16384/16390 unless use_vendor_types=0.
Q: Why disable DPD and lengthen ESP lifetime for a soak test?
A: Thousands of tunnels created together would rekey and DPD-probe together, creating load spikes unrelated to what the test is measuring. Test rekey separately, with fuzz.

Level 2 — running, ordering and verifying a run
The bring-up order is load-bearing. The driver always cycles the bench in this order:
EPC KILL (eNB still up) -> eNB DOWN (scale deployment to 0) -> EPC START
  -> fresh L1BP UP (restart the PHY deployment) -> eNB UP (scale 0 -> 1; verify EPC config + ICC pairing)
  -> UE SIM UP -> DATA PATH (traffic agents last) -> TEST
  • Kill the EPC first. With the eNB still alive the SCTP SHUTDOWN handshake completes. Kill the eNB first and the EPC keeps a zombie association that silently swallows the next eNB INIT — the cell then never comes up and nothing logs a clear error. That is why the driver waits up to 90 s for /proc/net/sctp/assocs to drain and aborts if it does not.
  • The eNB configures its peers only once. At start-up it sends CONFIG/START to its PHY once, and the EPC config is pushed once. A restarted PHY simulator or EPC sim therefore always needs a new eNB.
  • Restart the eNB by scaling, not killing. Scale the deployment 0→1. Killing the process inside the pod bypasses the supervisor and skips the stack-manager teardown.
  • Every eNB gets a fresh L1BP. The PHY simulator keeps its cell state (SFN, hyper-SFN, slot mailboxes) across a new CONFIG and never answers STOP, so reusing it gives odd timing failures.
  • Traffic agents start last — earlier, they break the EPC config sequence.

Level 3 — the traps that make CI lie
Trap 1 — "stale green". "The pod runs image X" does not mean "the eNB under test is X". A sticky private drop-in overrides the baked payload for the life of the container; a deployment re-render reverts the image tag; a same-container restart keeps an older extraction because the tarball is deleted after extracting. Each of these gives a pass for code that never executed. The fix: download the build's own image (temp name, then rename, so a partial download cannot pass), side-load it, retarget the deployment while scaled to 0, then compare the commit in the pod's nbiot-version.txt with the build. Mismatch = fail. There is deliberately no fallback to a cached image: an old image would side-load and then pass its own gate.

Trap 2 — the test that tested nothing. tc6 rewrites repetition values in a legacy OAM Python file, but that file is never pushed to the eNB: the cell is configured over NETCONF from a startup XML that has no repetition leaves. So tc6 runs as tc1 with a longer timeout. Lesson: check the configuration the DUT is actually running, not the file you edited.

Interview Q&A
Q: Why kill the EPC before the eNB when recycling the bench?
A: So the SCTP SHUTDOWN handshake completes while the eNB can still answer. Killing the eNB first leaves a zombie association on the EPC that swallows the next INIT, and the cell fails to come up with no clear error. The driver also waits for /proc/net/sctp/assocs to drain.
Q: The PHY simulator crashed and you restarted it. Why is there still no cell?
A: The eNB sends CONFIG/START to its PHY only once at start-up. A new PHY never receives them, so the eNB must be restarted too (scale 0→1), after the PHY.
Q: What is a "stale green" and how do you prevent it?
A: A pass for code that never ran: sticky drop-ins, re-rendered deployments or old extractions keep an older eNB in the pod. Side-load the build's own image and gate on the commit in the version file inside the pod; no cached-image fallback.
Q: The pod says Running 2/2. Is the eNB up?
A: Not necessarily. After a bring-up failure PID 1 idles to keep the pod exec-able. Check the readiness marker and the stack-manager "skipping NB-IoT bring-up" hard-stop lines.
Q: A CI case for repetitions passes. What would you check before believing it?
A: Whether the repetition setting reached the running cell. Here it did not: the edited file was never pushed and the NETCONF model had no repetition leaves, so the case ran at defaults.

Q: What does a PASS on this simulated bench prove, and what does it not?
A: It proves the L2/L3/NAS/S1AP procedures and the MAC↔PHY FAPI message flow for attach, data and detach. It does not prove PHY signal processing: the simulated PHY is a lossless PDU relay over UDP with no DSP or channel.
Q: A real-time simulator exits silently inside a container. First suspect?
A: It cannot set SCHED_FIFO. Give the container SYS_NICE and an rtprio ulimit. On a PREEMPT_RT host also keep RT throttling (sched_rt_runtime_us 950000) so RT threads cannot starve the box.
Q: Why does the kernel send SCTP ABORT for an association the eNB set up?
A: The eNB runs SCTP in userspace over raw sockets. The kernel SCTP module sees the same packets, knows no such association, and answers "out of the blue" packets with ABORT. Drop those kernel ABORTs.
Q: Every INIT-ACK fails the checksum check, but only in containers. Why?
A: SCTP CRC32c offload on the veth: the checksum is left for hardware that does not exist, so a raw-socket reader sees a bad CRC. Turn off tx-checksum-sctp.
Q: Why must the EPC be configured before the eNB starts?
A: If the eNB's first S1 setup fails, its configuration chain aborts before cell setup, so the cell is never created even after S1 recovers.
PHYSAN01 Catching Memory Bugs and Crashes in PHY CI — AddressSanitizer stage, SIMD over-reads, and making core dumps actually appear Automation click to expand ▾
In plain English
A PHY written in C/C++ with SIMD intrinsics can read one byte past a buffer for months without anyone noticing — until a different memory layout turns it into a crash in the field. Two CI tools catch these problems early. AddressSanitizer (ASAN) is a compiler option that puts guard zones around every allocation and checks every memory access, so an overflow or use-after-free is reported at the exact line, with a stack trace, the first time it happens. Core dumps are the black box for the crashes that still happen: a snapshot of the process memory at the moment it died, which gdb turns into a backtrace.

Both sound simple, and both have a catch. ASAN in a vectorised PHY reports a class of "errors" that are really SIMD over-reads; and on a standard Ubuntu CI host a crash produces no core file at all, because the distribution hands cores to its crash reporter. Related: AUTO14 (core name → component triage), PHYCI01 (PHY test vectors), PHYDBG01.

The CI flow. Making core dumps actually appear. On a stock Ubuntu host /proc/sys/kernel/core_pattern is a pipe to the distribution crash reporter (apport), so a crashing test leaves no core file in the test directory. The CI fix:
# before tests (as root) - remember the original first
orig=$(cat /proc/sys/kernel/core_pattern)
echo "core.%e.%p.%t" | sudo tee /proc/sys/kernel/core_pattern     # e.g. core.enb_app.3960.1771435246

# once per test host, in /etc/security/limits.conf (not per command)
*  soft  core  unlimited
*  hard  core  unlimited

# after tests
find <log dirs> -name "core.*"
file core.enb_app.3960.1771435246            # "execfn:" gives the binary path
gdb -batch -ex "set print asm-demangle on" -ex "thread apply all bt" <binary> <core>

# at job end (safety net, even if log retrieval failed)
echo "$orig" | sudo tee /proc/sys/kernel/core_pattern
The report written next to the logs carries branch, build number and commit with the backtrace, so a crash in a nightly run can be matched to a change. AUTO14 shows the next step: mapping the crashing thread name in the core file name to a component.

"It crashed but there is no core": check ulimit -c (0 = disabled) and cat /proc/sys/kernel/core_pattern (a leading | = piped away) first. In containers, core_pattern is the host's setting.
Level 3 — SIMD over-reads, cost, and pitfalls
The SIMD over-read. AVX/SSE/AVX-512 code loads 16, 32 or 64 bytes at a time. A buffer sized to the exact number of samples, with a tail that is not a multiple of the vector width, is read past its end by the last vector load. In production that usually reads harmless bytes of the next allocation; under ASAN it hits a red zone and is reported as a heap overflow. The team's classifier tags reports whose access size is 16/32/64 bytes as simd-overread: usually benign, still tracked. The clean fix is to pad buffers to the vector width (or use masked loads for the tail), not to suppress the report.

Interview Q&A
Q: ASAN reports a 32-byte heap-buffer-overflow read in an FFT kernel that has run fine in the field for a year. Real bug?
A: Probably a SIMD over-read: an AVX2 load reading past a buffer whose length is not a multiple of 32 bytes. Usually benign today, but layout-dependent. Pad the buffer or handle the tail with masked loads.
Q: halt_on_error=0 or 1 for a CI gate?
A: 1 (and no -fsanitize-recover): the test fails on the first error. 0 collects every error in one run, which is good for a backlog sweep, but the tests still pass, so it is not a gate on its own.
Q: A test crashed on an Ubuntu CI host, but no core file exists. What do you check?
A: ulimit -c (must not be 0; set unlimited in limits.conf) and /proc/sys/kernel/core_pattern — by default it pipes cores to apport. Set a plain pattern like core.%e.%p.%t and restore it after the job.
Q: Why is the ASAN stage nightly rather than per commit?
A: It roughly doubles run time and raises memory use, so per-push CI would slow down every developer. Nightly with a ~3× timeout catches the bugs within a day.
Q: What does ASAN not see in a DPDK-based PHY?
A: Memory from DPDK hugepage pools and other custom allocators, which bypass the instrumented malloc. Those buffers need their own checks.

Level 3 — lab-network rules, pitfalls and design choices
Network rules that must survive any redesign
  • Never NAT SCTP signalling — the 2G A-interface, S1AP and N2 do not survive address translation. Route it.
  • Keep routing in hardware. Stateful firewalling or connection tracking pushes the router to CPU forwarding.
  • User plane stays local. The lab core's UPF targets 15–20 Gbit/s while the whole lab shares ~1 Gbit/s of internet, so a dedicated PDN router terminates the N6 VLAN and serves the content server directly.
  • Lab-only ranges (UE pools, iperf ranges) are never advertised upstream.
  • CI must not pull from the internet mid-run — it competes with everything else on the single uplink.
  • With gateways on the campus router, two machines in the same rack can hairpin through it; whether traffic stays local depends on which switch a patch lead lands on, which silently changes timing and capacity.
Pitfalls
  • Manifest choice: decide whether the nightly takes the latest stable CI manifest or a nightly integration manifest, and pass it explicitly — otherwise two benches test different builds.
  • A matrix cell marked covered is only meaningful once the environment is "ready and tested"; "ready but not tested" cells still need a first green run.
  • Throughput limits differ per bandwidth and server; assertions must be per configuration, and a 0 vs 0 comparison must never pass (see RANCIDBG01).
  • When a UE attaches to the wrong cell, check the attenuator pattern before suspecting the RAN — a missing "all paths high" step leaves a stray path open.

A: Voice AF41 = 34, GPRS AF21 = 18, EGPRS AF31 = 26, signalling EF = 46. They are set via ACS with override on, the vNode is rebooted, and a packet capture on the node must show the markings.
Q: Why must SCTP signalling never pass through NAT in the lab network?
A: SCTP-based A-interface, S1AP and N2 associations break under address translation because the addresses are carried and checked inside the protocol. Route it in hardware without connection tracking.

Level 3 — guard-rails, "stale green" defences and lessons
Guard-rails
  • Runs only inside the time window; a PID lock prevents two nightlies at once.
  • Pre-flight: provisioning VMs reachable, artifact store reachable (3 retries), pool not empty.
  • Only the dedicated provisioning VMs receive new binaries; worker nodes never do.
  • Timeouts: EKS-A provision 90 min, SUSE provision 120 min, each test script 10 min, modify 15 min.
  • The SMO is strictly read-only from the farm (GET of templates only); every SSH, API call and provision is time-stamped in an audit log.
  • Bundles failing the linter are rejected at submit and again at load.
Defences against fake passes
  • Accept only status lines newer than the current trigger — an old "provision succeeded" line from yesterday must not pass tonight.
  • Clear the previous run's results file before starting, or a dead deploy reports yesterday's green.
  • After installing on SUSE, compare the on-disk binary version with the artifact; a difference marks the deploy version_mismatch (it caught real packaging faults).
  • Fail fast on an error body from the modify API; a wrapped payload was once silently ignored by the server and looked like success.
  • Do not infer "modify finished" from a generic "provision in progress" flag — the state machine hid the modify state; poll the dedicated modify-status file for its success marker.
  • Never drop a test silently: skipped tests always carry the real reason.
Failure classification is rule-based: infrastructure, test_bug or code_issue. During beta most failures were test bugs from generated tests (wrong endpoints, invented helpers, bad paths); the pass rate rose from 13 % to 78 % as each fix went into the knowledge files. Interview Q&A
Q: Why tag tests with a life-cycle phase instead of running them in a fixed order?
A: Provisioning time varies a lot (EKS-A vs SUSE, different hardware). A phase tag lets the runner fire each test when the cluster really reaches that state: before create, during or after provision, during or after modify, after delete. No hand-tuned sleeps.
Q: Why build and deploy each developer branch separately instead of a merged test branch?
A: So each result belongs to one change. A merged branch lets one developer's bug fail or mask another's tests, and the morning report can no longer say whose code broke.
Q: Give three ways a nightly can show a false green, and the defence for each.
A: A stale status line from an earlier run: accept only entries newer than the trigger. Leftover results from yesterday: clear artifacts at start. An API that accepted but ignored a payload: fail fast on error bodies and assert the effect on the worker, e.g. HugePages_Total in /proc/meminfo.
Q: How are failures classified and why does it matter?
A: As infrastructure, test_bug or code_issue. Developers then spend time only on code issues. Test bugs go back into the generator's knowledge, and infrastructure faults go to the lab owner.
Q: What safety rules keep an unattended farm from damaging shared systems?
A: A time window and a PID lock, pre-flight checks, binaries installed only on dedicated VMs, per-stage timeouts, read-only access to the SMO, a full audit log, and AI agents that never commit or merge without human approval.

In plain English

When "the cell does not work" the first hour is usually lost finding which layer is dead. iperf traps that make a healthy cell look dead
  • MTU: the bench path MTU is 1400 bytes but iperf's default UDP datagram is 1470, so DL dies after a few datagrams with write failed: Message too long. Use -l 1200.
  • Version skew: handsets run iperf 2.0.5 while the host runs a 2.1-era build whose UDP payload the old end does not recognise — UL arrives as nothing, exactly like a dead cell, unless -C (compatibility) is set. iperf3 3.1 and 3.7 simply refuse each other ("Connection reset by peer").
  • Stopping the server is not stopping the run: a UDP DL client keeps blasting the air with nobody listening. Kill the client too, and only your own roles/ports so you do not kill a colleague's test.
  • Interface moves: some handsets move their data session between two rmnet interfaces a minute or two after leaving airplane mode; a UL client started before the move carries ~0.3 Mbps for the rest of the run. Watch the interface and restart the client on change.
Gates before starting traffic (refuse to start, and say why, if any fails): UE not in airplane mode, UE in service on this bench's PCI, UE has a data-plane address, and the PHY has been configured by the DU (after an OOM restart a PHY sits waiting for config with the cell off air). First fix for a silent UE: airplane ON, wait ~10 s, OFF, wait ~20 s. But never hammer it — about 45 queued airplane toggles once left the core's session for the UE stuck for 22 hours until the shared core was restarted; allow one state change at a time with a settle window.

"Push max" — finding the bench maximum reproducibly: TCP with 1, 4, 8 streams, a fresh 35 s run per rung, read the DU 25 s in, stop when a rung improves by less than 5 %. Save only improvements, and always with the exact command — a number with no command behind it is an anecdote. Level 3 — attenuation sweeps, the channel emulator, Chapter 8 verdicts, lessons
Attenuation sweep recipe (e.g. 0 → 30 dB, 2 dB steps): settle 8 s after each set because the UE filters its own RSRP and lags; dwell ≥ settle + 5 s (30 s default) so each step gets several UE readings and at least one whole 10 s DU counter row; run traffic during the sweep — without traffic the DU cannot see that the UE dropped; stop and restore if the UE drops; plot the per-step median RSRP, SINR, DL/UL Mbps and BLER with min–max whiskers. Attenuator grids differ (0.25 dB on a Mini-Circuits unit, 0.1 dB on a Vaunix brick) and remote writes can take ~10 s, so plan step time = set + settle + 5 s. At the end, read back that the attenuator was restored: a sweep left at 30 dB makes your cell invisible and the UE camps on a foreign one tomorrow.

Two gain knobs on a channel emulator (Propsim): the channel-model gain adj (−80 to +20 dB) is the one to attenuate with; the output-stage gain carries the bench calibration (−95 dB means disconnected) — touching it silently shifts every result afterwards. Treat it as read-only.

Chapter 8 (RCT UL sensitivity) test plan = Signal (test vector in the PHY + generator waveform + optional interferer) · Channel (Propsim model or AWGN; SNR set by the Propsim or by a digital attenuator) · Carrier · Verdict. The verdict is a sensitivity search: find the lowest SNR that still meets the throughput (PUSCH) or detection/false-alarm (PRACH) threshold; pass if it lands inside KPI ± tol. Far better than the KPI is also a fail — it means the SNR or path loss is not what the test assumes. Pre-check before a run: TVs present in that PHY, waveforms loaded on the generator, channels loaded on the Propsim, and a bench lock so a nightly Jenkins job and a manual run never collide.

Real case — recording killed the cell: per-slot PHY recording is written into the PHY's log directory, which is RAM counted against the pod's memory limit. Two full recordings left there OOM-killed the PHY and took the cell off air. Fix: trim rows already copied off the host every 200 MB, step FULL down to SLIM when memory is short.

Bug triage helper: list the PRs per component (PHY, RU manager, stack, fronthaul, PTP) between the last-good and the running build and rank them by area keywords. The ranking tells you what to read first; it proves nothing.
Interview Q&A
Q: Why should a check that could not be read be grey rather than green?
A: Because "not confirmed bad" is not "confirmed good". A dashboard that defaults unknown to green hides exactly the boxes you cannot see; grey forces someone to look.
Q: DU MAC counters say 64 Mbps, iperf says 42 Mbps and the phone says 250 Mbps. Which is right?
A: All three. MAC counts airtime including retransmissions and overhead, iperf counts this run's payload, the phone counts every byte on its interface. To answer "did the cell carry it" use the DU MAC counters.
Q: UL iperf from a handset shows zero but DL is fine. What do you check before blaming the cell?
A: Version compatibility (-C for iperf 2.0.5 vs newer), datagram size vs path MTU (-l 1200), that the client is still on the interface holding the address, and that the UE is on this bench's PCI with a data address.
Q: Why run traffic during an attenuation sweep?
A: An idle UE gives the DU nothing to measure, so a dropped link is invisible; traffic also makes RSRP/SINR/BLER per step meaningful. Settle 8 s per step because the UE filters RSRP.
Q: A Chapter 8 test measured 4 dB better sensitivity than the KPI. Pass?
A: No — outside KPI ± tol in either direction fails. A large "better" margin usually means a wrong SNR calibration or cable loss, so the test is not measuring what it claims.
RUBUILD01 Fast RU Software Builds — compiling M-plane apps against the Petalinux SDK, RPM packaging and golden-rootfs images Automation click to expand ▾
In plain English
The software on an O-RU (the M-plane daemons, drivers, Linux root file system) is normally produced by a full Petalinux (Xilinx Yocto) build: it compiles the kernel, the libraries, every third-party package and the in-house applications, and packs them into one update image. That is safe but slow — about 2 hours from scratch (at least ~10 minutes even with every cache warm), plus ~10 minutes to copy the image to the radio, install it and reboot. And 99 % of every image is unchanged from the last one.

When you only touched one M-plane application, you do not need any of that. You can compile your code directly against the Petalinux SDK (the cross-compiler and target sysroot) with plain make in seconds, copy the binary to the board and debug it. Going one step further, the in-house code can be shipped as RPM packages installed into a known-good "golden" root file system, so a new update image is "golden rootfs + these RPM versions" instead of a full rebuild.

Why a validation engineer cares: it changes what identifies the build you tested. With RPMs the answer is the manifest of package versions (each with its git hash), not just an image name. For how an update package is installed on the RU see CM36 (software update redesign) and CM04; for driving the M-plane apps by hand see ORUMAN01.

Level 1 — SDK builds, RPMs and why they are faster
  • Petalinux SDK = the cross toolchain plus a target sysroot for the RU's ARM cores (Cortex-A72/A53, aarch64). You source its environment script once per shell; after that $CC, $CFLAGS and the sysroot point at the target, and ordinary makefiles build target binaries.
  • The fast build of the in-house tree produces a small rootfs/usr tree: bin/ with the M-plane daemons (fault, firmware, PM, radio, sync, network, watchdog, supervision, file, log, LED, operations, user-management managers and helpers for DHCP/VLAN scan/EEPROM) and lib/ with their shared libraries (messaging, config, JSON parser, GPIO, I2C semaphore, hwmon, SFP info ...). Copy that tree onto a lab board and you are testing the new code.
  • Package management. Enabling the package-management image feature in petalinux-config -c rootfs puts dnf/rpm on the target, so in-house packages can be installed and removed without reflashing. RPM scriptlets (pre/post-install scripts) can enable systemd units and adjust configuration during install.
  • Visible warnings. Inside the full Petalinux build compiler warnings scroll past unseen; a plain make build shows every warning, which is how latent bugs get caught before the RCT run.

Validation checklist for an RPM-built image
  • Record the manifest (golden rootfs id + every RPM name-version-release) with each RCT result, not only the image filename.
  • On the RU, rpm -qa | sort must match the manifest; a hand-copied binary will not appear there — ask whether the DUT was patched by copy.
  • After installing or removing a package, confirm the scriptlets did their job: services enabled and running, config files in place, no leftover unit after removal.
  • Upgrade path test: old image → new RPM set → reboot; and downgrade by RPM, checking that the daemons restart cleanly.

Design consequences and pitfalls
  • No intermediate images stored. Only the manifest (artifact links + RPM versions) is kept; the image can be re-created from it. If the golden rootfs or an artifact is deleted from the store, old builds can no longer be reproduced — retention matters.
  • ABI drift. An app compiled against an SDK sysroot that differs from the golden rootfs libraries can link fine and crash on the board (missing symbol, different struct layout). Build with the SDK that matches the golden rootfs version.
  • QEMU is for logic, not timing. Business logic and parsing can be debugged in QEMU aarch64; anything touching FPGA registers, I2C, GPIO or real-time behaviour still needs hardware.
  • Kernel, u-boot and FPGA bitstreams keep separate pipelines; an RPM-only update cannot change them, so a fix in those areas still needs a full image.
  • Migration is gradual: code moves to the new repository step by step while unmoved code keeps the old pipeline, so for a while a build is a mix — another reason the manifest must travel with test results.

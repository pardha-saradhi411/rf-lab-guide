AUTO01 Python essentials for RF test interviews Automation click to expand ▾
What they test
The basics, fast: data structures, string/dict work, list/dict comprehensions, file I/O, regex, and a clean function. If you can read a file, extract numbers with regex, and return a pass/fail, you clear most first-round Python screens.
# --- the four structures ---
bands   = ["B1", "B3", "B8", "B28"]        # list  (ordered, mutable)
rated   = {"B1": 46.0, "B8": 44.8}          # dict  (key -> value)
seen    = set()                              # set   (unique, fast membership)
point   = ("B1", 2140)                       # tuple (immutable)

# --- comprehensions (know these cold) ---
dbm     = [43, 46, 44.8, 40]
watts   = [round(10**((p-30)/10), 2) for p in dbm]     # list comp
passing = {b: p for b, p in rated.items() if p >= 45}  # dict comp
uniq    = {b for b in bands}                            # set comp

# --- a clean function with type hints + docstring ---
def dbm_to_watt(dbm: float) -> float:
    """Convert power in dBm to watts."""
    return 10 ** ((dbm - 30) / 10)

# --- file read + regex extract ---
import re
with open("rct.log") as f:                 # 'with' auto-closes the file
    text = f.read()
aclr = [float(x) for x in re.findall(r"ACLR[:\s]+([\d.]+)\s*dBc", text)]
worst = min(aclr) if aclr else None        # ACLR: higher is better -> worst = min
Interview Q&A
Q: list vs tuple vs set vs dict — when do you use each?
A: list = ordered, mutable sequence (a sweep of results); tuple = immutable record (a fixed (band, freq) pair, usable as a dict key); set = unique membership with O(1) lookups (which preambles were detected); dict = key→value mapping (per-band limits, per-ADC offsets). Pick by whether you need order, mutability, uniqueness, or lookup.
Q: Why use 'with open(...)' instead of open()/close()?
A: The context manager guarantees the file is closed even if an exception is raised mid-parse — no leaked handles. Same reason you wrap instrument/SSH sessions in context managers in test code.
AUTO02 Python — parse a log / result file and decide pass/fail Automation click to expand ▾
The most common "write code" task for a test engineer
Given a log/CSV of measurements, extract the numbers, apply the 3GPP limit (with tolerance and direction), and emit a verdict. This is exactly what an RCT measure function does.
import re, csv

def evaluate_aclr(log_path, limit_dbc=55.0, tol=0.0):
    """Extract ACLR values, return (worst, verdict). ACLR: higher is better."""
    with open(log_path) as f:
        vals = [float(m) for m in re.findall(r"ACLR[:\s]+(-?[\d.]+)", f.read())]
    if not vals:
        return None, "NO DATA"
    worst = min(vals)                          # worst-case adjacent channel
    if worst >= limit_dbc:            verdict = "PASS"
    elif worst >= limit_dbc - tol:   verdict = "PASS (tolerance)"
    else:                             verdict = "FAIL"
    return worst, verdict

# CSV of per-band results -> summary
def summarise(csv_path):
    rows = list(csv.DictReader(open(csv_path)))
    for r in rows:
        p = float(r["power_dbm"])
        r["verdict"] = "PASS" if abs(p - float(r["rated"])) <= 1.5 else "FAIL"
    fails = [r for r in rows if r["verdict"] == "FAIL"]
    print(f"{len(rows)-len(fails)}/{len(rows)} passed")
    return fails
Direction matters
ACLR / sensitivity margin: higher is better → worst = min, pass if >= limit. EVM / power-error / spurious: lower is better → worst = max, pass if <= limit. Get the direction wrong and every verdict inverts — a classic interview trap.
Interview Q&A
Q: Given a log, print the worst ACLR and pass/fail against 55 dBc — how?
A: Read the file, regex-extract the ACLR numbers, take min() (higher-is-better so the worst is the smallest), compare to 55 with any tolerance, return PASS/FAIL. Guard the empty case. That's the evaluate_aclr function above.
AUTO03 pytest for RCT — fixtures, parametrize, markers, conftest Automation click to expand ▾
The framework ruauto uses
pytest is code-first: test functions named test_*, shared setup via fixtures, matrix runs via @parametrize, selection via markers, and CLI options via conftest.py (pytest_addoption). See CLI01 / FWK1 for the RCT specifics.
# conftest.py — a shared fixture + a CLI option
import pytest

def pytest_addoption(parser):
    parser.addoption("--fhgw-band", action="store", default="b0103")

@pytest.fixture(scope="session")
def band(request):
    return request.config.getoption("--fhgw-band")

@pytest.fixture
def analyzer():                     # setup / teardown around each test
    sa = connect_exa("10.62.2.135")
    yield sa                        # test runs here
    sa.close()                      # teardown always runs

# test_tx.py
import pytest

@pytest.mark.parametrize("bw,limit", [(5,13.9),(10,16.9),(15,18.7),(20,20.0)])
def test_tx_dynamic_range(analyzer, band, bw, limit):
    measured = analyzer.measure_dynamic_range(band, bw)
    assert measured >= limit, f"{band} {bw}MHz: {measured} < {limit} dB"

@pytest.mark.conformance          # run: pytest -m conformance
def test_tx_aclr(analyzer, band):
    assert analyzer.measure_aclr(band) >= 55.0
Interview Q&A
Q: What is a pytest fixture and why use one?
A: A fixture provides reusable setup/teardown injected into tests by name. The code before yield runs before the test (connect the analyzer), the code after runs as teardown (close it) even on failure. Scope (function/session) controls how often it runs — session-scope to connect the instrument once for the whole run.
Q: How do you run the same test across 4 bandwidths without copy-paste?
A: @pytest.mark.parametrize with a list of (bw, limit) tuples — pytest generates one test case per tuple, each reported separately, so one failing BW doesn't hide the others.

Interview Q&A
Q: Robot Framework vs pytest — when would you pick Robot?
A: Robot is keyword-driven and reads almost like English, so it suits large mixed-skill teams sharing reusable keyword libraries and gives rich HTML reports out of the box (my Mavenir work). pytest is code-first and better when tests need real Python logic (the ruauto RCT suites). Both can drive the same UEs/instruments via libraries.
Q: How do you make a data-driven test in Robot?
A: Use [Template] on the test case pointing at a keyword; each row of arguments below it becomes one iteration — e.g. an attach/detach cycle repeated N times, or the same measurement across bands.
AUTO05 SCPI instrument automation in Python (pyvisa) — EXA/EXM Automation click to expand ▾
Talk to the analyzer from Python
SCPI commands over LAN (VISA/sockets) drive the Keysight EXA/EXM. Set mode → center/span → measurement → trigger → read. See EXP2 for the command set.
import pyvisa

def measure_aclr(ip="10.62.2.135", fc_hz=2140e6, bw_mhz=10):
    rm = pyvisa.ResourceManager("@py")
    sa = rm.open_resource(f"TCPIP0::{ip}::inst0::INSTR")
    sa.timeout = 20000                       # ms
    try:
        sa.write("*RST"); sa.query("*OPC?")  # reset, wait complete
        sa.write(":INSTrument:SELect LTE")   # LTE-FDD mode
        sa.write(f":SENSe:FREQuency:CENTer {fc_hz}")
        sa.write(":CONFigure:ACP")           # ACLR/ACP measurement
        # auto-range so a low-power isolated path is not near the noise floor:
        sa.write(":SENSe:POWer:RF:RANGe:OPTimize IMMediate")
        sa.query("*OPC?")
        vals = sa.query(":FETCh:ACP?").strip().split(",")
        return [float(v) for v in vals]
    finally:
        sa.close(); rm.close()               # always release the session
The real-world gotcha (from an actual fix)
When measuring a per-RFFE isolated (lower-power) signal, the analyzer must auto-range (:SENSe:POWer:RF:RANGe:OPTimize IMMediate) or the reading sits near the noise floor and ACLR reads ~2–3 dB low (51–52 vs 54–55 dBc). Always range before an ACP read. (Real RCT fix in measure_test_Tx_ACLR.)
Interview Q&A
Q: What does *OPC? do and why query it?
A: *OPC? (operation complete) blocks until the instrument finishes the pending command and returns 1. You query it after RST/CONFig/trigger so you don't FETCh a result before the sweep/measurement is actually done — otherwise you read stale or partial data.
AUTO06 Multi-UE automation — ADB, subprocess, parallel threads, iperf Automation click to expand ▾
Drive a fleet of real UEs
Shell out to ADB with subprocess, address each UE by serial, and run actions in parallel with threads for load/throughput. See UE02/UE03/UE09.
import subprocess
from concurrent.futures import ThreadPoolExecutor

def adb(serial, *args):
    """Run an adb command on a specific device, return stdout."""
    cmd = ["adb", "-s", serial, *args]
    return subprocess.run(cmd, capture_output=True, text=True, timeout=60).stdout

def list_devices():
    out = subprocess.run(["adb","devices"], capture_output=True, text=True).stdout
    return [l.split()[0] for l in out.splitlines()[1:] if l.strip().endswith("device")]

def run_iperf(serial, server="10.0.0.1", secs=30):
    adb(serial, "shell", "svc", "data", "enable")          # ensure attached
    out = adb(serial, "shell", f"iperf3 -c {server} -t {secs} -R")  # DL
    return serial, out

# run all UEs in parallel and collect throughput
ues = list_devices()
with ThreadPoolExecutor(max_workers=len(ues) or 1) as pool:
    results = list(pool.map(lambda s: run_iperf(s), ues))
for serial, out in results:
    print(serial, "done")
Interview Q&A
Q: How do you run traffic on 10 UEs at once in Python?
A: Address each UE by its ADB serial (adb -s), then launch the per-UE work concurrently with a ThreadPoolExecutor (threads are fine here because the work is I/O-bound — waiting on adb/iperf, not CPU). Collect per-UE results and aggregate. For CPU-bound work you'd use multiprocessing instead.
AUTO07 Interview coding drills — small functions with solutions Automation click to expand ▾
Try each from memory first, then check
The kinds of "write a function" they hand an RF/test engineer — short, domain-flavoured, and quick to reason about.
# 1) dBm <-> mW
def dbm_to_mw(dbm): return 10 ** (dbm / 10)
def mw_to_dbm(mw):  import math; return 10 * math.log10(mw)

# 2) worst-case + margin vs a limit (higher-is-better metric)
def margin(values, limit):
    worst = min(values)
    return worst, worst - limit          # +ve margin = pass

# 3) binary-search a sensitivity threshold (miss-rate <= 1%)
def find_sensitivity(measure, lo=-120.0, hi=-60.0, res=0.5):
    while hi - lo > res:
        mid = (lo + hi) / 2
        if measure(mid) <= 1.0:  lo = mid   # still detecting -> go lower
        else:                    hi = mid   # too weak -> go higher
    return lo

# 4) parse "B1=46.0 B3=44.8" into a dict
def parse_kv(line):
    return {k: float(v) for k, v in (p.split("=") for p in line.split())}

# 5) count occurrences without a library
def counts(items):
    d = {}
    for x in items: d[x] = d.get(x, 0) + 1
    return d

# 6) first duplicate in a stream (set for O(n))
def first_dup(seq):
    seen = set()
    for x in seq:
        if x in seen: return x
        seen.add(x)
    return None
Interview Q&A
Q: Write a function to find the reference sensitivity by binary search.
A: Bracket the power [lo, hi]; test the midpoint; if the miss-detection rate is within limit the UE still decodes so search lower, else search higher; stop when the range is under your resolution. That's find_sensitivity above — O(log range) instead of a linear sweep (and it mirrors the real PRACH/sensitivity search, see PRACHDM01).
Q: Why is a set the right tool for "first duplicate"?
A: Membership testing in a set is O(1) average, so one pass over the stream is O(n). Using a list and 'in' would be O(n) per check → O(n²). Same reasoning behind using a set for detected-preamble bookkeeping.

How to use this card
This is a feature walkthrough, not a snippet — a step-by-step trace of the real ruauto RSSI-accuracy test (GRDEV-8461), following every method call to what it executes and where control goes next. Read it top-to-bottom once; then in the interview you can narrate "the test does X, which calls Y, which SSHes into the RU and runs get-rssi, parses it like this…". This is the template — the same shape (declare → road-trip iterates → configure runs the sweep → two independent readouts → average → report) applies to Sensitivity, ACLR, Dynamic Range, PA-protection. Ask me to trace any of those next.
1 · What the feature proves (say this first)
"RSSI accuracy validates that the RU's own reported received-power agrees with reality across the whole input range, per antenna / band / RU-model. I inject a known LTE UL signal at power P from the signal generator, then read RSSI from two independent places — the RU's get-rssi CLI (dBm + dBFS, the operator-facing number) and the PHY / L1 rct_stats (the internal number) — average N samples at each power, and record the difference PHY−CLI. A per-model offset calibrates the CLI readout. As a by-product, sweeping power from saturation down to the noise floor gives me the BLER-vs-power curve, so I also extract the 5% BLER sensitivity point. No pass/fail coloring — it's a calibration/characterisation test producing raw averages + diff."

3 · Step A — test_Rx_RSSI_Accuracy() only DECLARES (the naming convention)
In ruauto every test is split in two by name: test_X declares (defines the report column headers, the supported frequencies via _get_tc_freq, the RB set, and calls xlxfile.prepare_report() to create the sheet), then returns (supported_freq, supported_rb). The heavy lifting lives in the sibling configure_test_X. The road-trip driver reads what test_X returned, loops over antenna × frequency, does per-antenna hardware setup (antenna select rctEaxc1=rctEaxc2=ant# + L1/L2 restart), and calls configure_test_X once per (antenna, freq). Knowing this split is the fastest way to show you understand the framework, not just your one test.
4 · Step B — configure_test_Rx_RSSI_Accuracy() sets up the math + waveform

Every knob (rssi_acc_samples, step sizes, floor_pwr, the offset table) is config-driven from fdd_test_setup.json/cws[0], so the same code runs on every band and RU model — nothing is hard-coded per band except the derived splitter correction. The offset is per-ADC (indexed model → fhgw_band → band → antenna) because each antenna's RSSI path calibrates slightly differently.
5 · Step C — the U-shaped power sweep (the clever bit)
BLER-vs-power is U-shaped: ~100% at the saturated top (ADC hits full-scale → clipping → decode fails) and ~100% at the sensitivity floor (signal in the noise), with a clean ~0% valley in between. A naïve "step down until BLER rises" would stop at the wrong edge. So the controller runs three phases:
Phase A  descend from start by COARSE step, skipping the saturated top,
         until BLER settles <= 1%   -> we are now in the clean valley
Phase B  keep COARSE-stepping down through the valley
         until BLER rises above 1%  -> we found the low-power KNEE
Phase C  back off to last-clean power, step at FINE (0.5 dB);
         once BLER >= ~1% switch to ULTRA-FINE (0.1 dB) to pin the exact 5%,
         continue down until BLER >= 99%  (fully into the floor)
mode='sensitivity' -> coarse 5 dB in the flat + 0.1 dB at knee (fast, just pins 5%)
mode='accuracy'    -> uniform 0.5 dB everywhere (dense RSSI-vs-power, no ultra-fine)
mode='both'        -> uniform 0.5 dB + 0.1 dB at knee (default: dense + exact 5%)
This gives dense data where it matters (the knee) without wasting time taking 0.1 dB steps across the flat valley — a real speed/coverage trade the interviewer will appreciate you naming.

Two subtle design choices worth calling out: (1) PHY is read once per power step, not per sample — the L1 debug file only refreshes every few seconds while the N CLI reads finish in milliseconds, so per-sample PHY reads would return N identical values plus N wasted docker round-trips. (2) The offset is added to the CLI reading (RU-perspective calibration), so diff = PHY − CLI is what you're characterising.
7 · Step E — the RU-CLI path: get_rssi_from_rrh() + extract_adc_values()
This is the part that surprises non-RU people — reading RSSI means driving the radio's shell over SSH+telnet:
get_rssi_from_rrh():
  if not verify_fh_connection():        # radio dropped off fronthaul?
      handle_radio_lost(); drop stale ssh session      # recover/power-cycle, then reconnect
  ssh 'pwd'  -> detect where the shell landed:
      'localhost' (BBU) or '#' (FHGW shell)  -> not in cli-manager yet:
          /usr/bin/cli-manager &
          telnet localhost 8888 ; login root/root  -> prompt becomes '>'
      already '>'                             -> already in cli-manager
  send 'get-rssi'  ; wait for '>'  ; return the raw lines

extract_adc_values(lines, antenna_index):
  data_lines = [l for l in lines if 'ADC_INDEX_' in l]
  adc_index  = adc_mappings[fhgw_band][band][antenna_index]   # logical ant -> physical ADC
  line       = data_lines[adc_index]
  re.search(r'adc_dbfs:([-\d.]+) dBFS,rssi:([-\d.]+) dBm', line) -> (rssi_dBm, dBFS)
The adc_mappings table matters: a logical antenna is not ADC N. On the 5-band AAU (b082028), for example, B28 antenna 0 reads physical ADC 4, antenna 1 → ADC 5. Getting that mapping wrong reads the wrong antenna's power — a real bug class. The session is also self-healing: if the radio fell off the fronthaul the read triggers the same recovery path as the sensitivity test instead of hanging on a dead prompt.

9 · Step G — the report: _rssi_acc_report()
At run end, results (keyed by band/antenna/ulf/bw) become an openpyxl workbook: a summary of sensitivity @5% BLER per combo, one big table (per-sample rows + an AVG row), and two matplotlib charts — BLER vs EIRP (with the 5% line) and RSSI dBFS: CLI vs PHY. The 5% point is a linear interpolation between the two samples that straddle 5% on the low-power side:
_rssi_acc_sens_5pct(rows):   # rows sorted by eirp
  find i where bler[i-1] > 5 >= bler[i]           # straddle the 5% line
  frac  = (5 - bler[i-1]) / (bler[i] - bler[i-1]) # linear interp fraction
  return eirp[i-1] + frac * (eirp[i] - eirp[i-1]) # EIRP @ exactly 5% BLER
The whole report is best-effort / never raises into the road-trip — a broken matplotlib or a missing lib logs a warning and the test still passes its data through. Defensive by design so a reporting hiccup never fails a validated run.
Interview Q&A — how a VP / senior lead will probe this
Q: Walk me through what happens end-to-end when the RSSI-accuracy test runs.
A: test_Rx_RSSI_Accuracy declares the sheet/columns/frequencies and returns them; the road-trip driver loops antenna×freq, selects the antenna and restarts L1/L2, and calls configure_test_Rx_RSSI_Accuracy. That computes setup-loss/EIRP/TRP math, reads the RU model to pick the calibration offset, loads the ETM1.1 UL waveform, then sweeps SG power in a U-aware three-phase controller. At each power _measure reads PHY rct_stats once and N samples of RU-CLI RSSI + BLER, averages them, records PHY−CLI, and writes a row. At the end _rssi_acc_report builds the xlsx + BLER/RSSI graphs and interpolates the 5% BLER sensitivity.
Q: Why compare CLI RSSI against PHY RSSI at all — aren't they the same number?
A: No — they come from different subsystems. The CLI get-rssi is what the operator/EMS sees (post-calibration, per-ADC), the PHY rct_stats is L1's internal estimate. If they diverge, either the RU's RSSI calibration/offset is wrong or the reporting path is broken. The test characterises that gap across the full power range, so a calibration error shows up as a consistent PHY−CLI diff.
Q: Why is BLER high at BOTH the top and bottom of the power sweep?
A: At the top the ADC saturates/clips (input above full-scale), so the samples are distorted and decode fails; at the bottom the signal drops into the noise floor and SINR collapses. In between there's a clean ~0% valley. That U-shape is exactly why the sweep first descends to find the clean region before hunting the low-power knee — otherwise you'd mistake the saturated top for the sensitivity edge.
Q: You read the PHY once per power step but the CLI N times — why the asymmetry?
A: The PHY value comes from tailing l1_Debug.log inside the phynode container, which only rewrites every few seconds. The N CLI reads complete in milliseconds, so reading the PHY per sample would just return N identical values plus N wasted docker round-trips. One PHY read per step, mirrored across the sample rows, is correct and much faster.
Q: How do you go from "logical antenna 2" to the right RSSI number in the CLI output?
A: get-rssi prints one line per physical ADC. A per-band mapping table (adc_mappings[fhgw_band][band][antenna_index]) translates the logical antenna to the physical ADC index — on the 5-band AAU, B28 antenna 0 is ADC 4, not ADC 0 — then I regex that line for adc_dbfs and rssi. Wrong mapping = you silently report a different antenna's power.
Q: What's EIRP vs TRP here, and where does the +3/+6 dB come from?
A: EIRP at the RU input = generator power + external_gain (which is −setup_loss, the cable/path loss). TRP adds the splitter correction: the low bands (B8/B28) feed through a 2:1 splitter (+3 dB) and the mid bands (B1/B3)/B41 through a 4:1 (+6 dB), so TRP = EIRP + that correction. It's derived from the band, with a config override.
Q: How would you extend this test to a new band or RU model?
A: Almost no code — add the band's ADC layout to adc_mappings, add the frequencies to the cadence, and populate rssi_model_offsets[model][fhgw_band][band][ant] in fdd_test_setup.json. The sweep, averaging, PHY/CLI reads and report are band-agnostic; only the mapping and calibration tables are data.
Q: If PHY−CLI diff is, say, 3 dB and constant across power, what do you conclude?
A: A constant offset points to a calibration/offset error in the RU's RSSI reporting (or a wrong rssi_model_offsets entry) — not a linearity problem. A diff that grows toward the top would suggest compression/clipping; one that grows at the bottom suggests a noise-floor/SINR issue. Constant → fix the offset table; power-dependent → investigate the analog/ADC front-end.

What they test

# --- file read + regex extract ---
import re
with open("rct.log") as f:                 # 'with' auto-closes the file
    text = f.read()
aclr = [float(x) for x in re.findall(r"ACLR[:\s]+([\d.]+)\s*dBc", text)]
worst = min(aclr) if aclr else None        # ACLR: higher is better -> worst = min
Interview Q&A
Q: list vs tuple vs set vs dict — when do you use each?
A: list = ordered, mutable sequence (a sweep of results); tuple = immutable record (a fixed (band, freq) pair, usable as a dict key); set = unique membership with O(1) lookups (which preambles were detected); dict = key→value mapping (per-band limits, per-ADC offsets). Pick by whether you need order, mutability, uniqueness, or lookup.
Q: Why use 'with open(...)' instead of open()/close()?
A: The context manager guarantees the file is closed even if an exception is raised mid-parse — no leaked handles. Same reason you wrap instrument/SSH sessions in context managers in test code.
AUTO02 Python — parse a log / result file and decide pass/fail Automation click to expand ▾
The most common "write code" task for a test engineer
Given a log/CSV of measurements, extract the numbers, apply the 3GPP limit (with tolerance and direction), and emit a verdict. This is exactly what an RCT measure function does.
import re, csv

def evaluate_aclr(log_path, limit_dbc=55.0, tol=0.0):
    """Extract ACLR values, return (worst, verdict). ACLR: higher is better."""
    with open(log_path) as f:
        vals = [float(m) for m in re.findall(r"ACLR[:\s]+(-?[\d.]+)", f.read())]
    if not vals:
        return None, "NO DATA"
    worst = min(vals)                          # worst-case adjacent channel
    if worst >= limit_dbc:            verdict = "PASS"
    elif worst >= limit_dbc - tol:   verdict = "PASS (tolerance)"
    else:                             verdict = "FAIL"
    return worst, verdict

# CSV of per-band results -> summary
def summarise(csv_path):
    rows = list(csv.DictReader(open(csv_path)))
    for r in rows:
        p = float(r["power_dbm"])
        r["verdict"] = "PASS" if abs(p - float(r["rated"])) <= 1.5 else "FAIL"
    fails = [r for r in rows if r["verdict"] == "FAIL"]
    print(f"{len(rows)-len(fails)}/{len(rows)} passed")
    return fails
Direction matters
ACLR / sensitivity margin: higher is better → worst = min, pass if >= limit. EVM / power-error / spurious: lower is better → worst = max, pass if <= limit. Get the direction wrong and every verdict inverts — a classic interview trap.
Interview Q&A
Q: Given a log, print the worst ACLR and pass/fail against 55 dBc — how?
A: Read the file, regex-extract the ACLR numbers, take min() (higher-is-better so the worst is the smallest), compare to 55 with any tolerance, return PASS/FAIL. Guard the empty case. That's the evaluate_aclr function above.
AUTO03 pytest for RCT — fixtures, parametrize, markers, conftest Automation click to expand ▾
The framework ruauto uses
pytest is code-first: test functions named test_*, shared setup via fixtures, matrix runs via @parametrize, selection via markers, and CLI options via conftest.py (pytest_addoption). See CLI01 / FWK1 for the RCT specifics.
# conftest.py — a shared fixture + a CLI option
import pytest

def pytest_addoption(parser):
    parser.addoption("--fhgw-band", action="store", default="b0103")

@pytest.fixture(scope="session")
def band(request):
    return request.config.getoption("--fhgw-band")

@pytest.fixture

    sa = connect_exa("10.62.2.135")
    yield sa                        # test runs here
    sa.close()                      # teardown always runs

# test_tx.py
import pytest

@pytest.mark.parametrize("bw,limit", [(5,13.9),(10,16.9),(15,18.7),(20,20.0)])
def test_tx_dynamic_range(analyzer, band, bw, limit):
    measured = analyzer.measure_dynamic_range(band, bw)
    assert measured >= limit, f"{band} {bw}MHz: {measured} < {limit} dB"

@pytest.mark.conformance          # run: pytest -m conformance
def test_tx_aclr(analyzer, band):
    assert analyzer.measure_aclr(band) >= 55.0
Interview Q&A
Q: What is a pytest fixture and why use one?
A: A fixture provides reusable setup/teardown injected into tests by name. The code before yield runs before the test (connect the analyzer), the code after runs as teardown (close it) even on failure. Scope (function/session) controls how often it runs — session-scope to connect the instrument once for the whole run.
Q: How do you run the same test across 4 bandwidths without copy-paste?
A: @pytest.mark.parametrize with a list of (bw, limit) tuples — pytest generates one test case per tuple, each reported separately, so one failing BW doesn't hide the others.

AUTO05 SCPI instrument automation in Python (pyvisa) — EXA/EXM Automation click to expand ▾
Talk to the analyzer from Python
SCPI commands over LAN (VISA/sockets) drive the Keysight EXA/EXM. Set mode → center/span → measurement → trigger → read. See EXP2 for the command set.
import pyvisa

def measure_aclr(ip="10.62.2.135", fc_hz=2140e6, bw_mhz=10):
    rm = pyvisa.ResourceManager("@py")
    sa = rm.open_resource(f"TCPIP0::{ip}::inst0::INSTR")
    sa.timeout = 20000                       # ms
    try:
        sa.write("*RST"); sa.query("*OPC?")  # reset, wait complete
        sa.write(":INSTrument:SELect LTE")   # LTE-FDD mode
        sa.write(f":SENSe:FREQuency:CENTer {fc_hz}")
        sa.write(":CONFigure:ACP")           # ACLR/ACP measurement
        # auto-range so a low-power isolated path is not near the noise floor:
        sa.write(":SENSe:POWer:RF:RANGe:OPTimize IMMediate")
        sa.query("*OPC?")
        vals = sa.query(":FETCh:ACP?").strip().split(",")
        return [float(v) for v in vals]
    finally:
        sa.close(); rm.close()               # always release the session
The real-world gotcha (from an actual fix)
When measuring a per-RFFE isolated (lower-power) signal, the analyzer must auto-range (:SENSe:POWer:RF:RANGe:OPTimize IMMediate) or the reading sits near the noise floor and ACLR reads ~2–3 dB low (51–52 vs 54–55 dBc). Always range before an ACP read. (Real RCT fix in measure_test_Tx_ACLR.)
Interview Q&A
Q: What does *OPC? do and why query it?
A: *OPC? (operation complete) blocks until the instrument finishes the pending command and returns 1. You query it after RST/CONFig/trigger so you don't FETCh a result before the sweep/measurement is actually done — otherwise you read stale or partial data.
AUTO06 Multi-UE automation — ADB, subprocess, parallel threads, iperf Automation click to expand ▾
Drive a fleet of real UEs
Shell out to ADB with subprocess, address each UE by serial, and run actions in parallel with threads for load/throughput. See UE02/UE03/UE09.
import subprocess
from concurrent.futures import ThreadPoolExecutor

def adb(serial, *args):
    """Run an adb command on a specific device, return stdout."""
    cmd = ["adb", "-s", serial, *args]
    return subprocess.run(cmd, capture_output=True, text=True, timeout=60).stdout

def list_devices():
    out = subprocess.run(["adb","devices"], capture_output=True, text=True).stdout
    return [l.split()[0] for l in out.splitlines()[1:] if l.strip().endswith("device")]

def run_iperf(serial, server="10.0.0.1", secs=30):
    adb(serial, "shell", "svc", "data", "enable")          # ensure attached
    out = adb(serial, "shell", f"iperf3 -c {server} -t {secs} -R")  # DL
    return serial, out

# run all UEs in parallel and collect throughput
ues = list_devices()
with ThreadPoolExecutor(max_workers=len(ues) or 1) as pool:
    results = list(pool.map(lambda s: run_iperf(s), ues))
for serial, out in results:
    print(serial, "done")
Interview Q&A
Q: How do you run traffic on 10 UEs at once in Python?
A: Address each UE by its ADB serial (adb -s), then launch the per-UE work concurrently with a ThreadPoolExecutor (threads are fine here because the work is I/O-bound — waiting on adb/iperf, not CPU). Collect per-UE results and aggregate. For CPU-bound work you'd use multiprocessing instead.

The kinds of "write a function" they hand an RF/test engineer — short, domain-flavoured, and quick to reason about.
# 1) dBm <-> mW
def dbm_to_mw(dbm): return 10 ** (dbm / 10)
def mw_to_dbm(mw):  import math; return 10 * math.log10(mw)

# 2) worst-case + margin vs a limit (higher-is-better metric)
def margin(values, limit):
    worst = min(values)
    return worst, worst - limit          # +ve margin = pass

# 3) binary-search a sensitivity threshold (miss-rate <= 1%)
def find_sensitivity(measure, lo=-120.0, hi=-60.0, res=0.5):
    while hi - lo > res:
        mid = (lo + hi) / 2
        if measure(mid) <= 1.0:  lo = mid   # still detecting -> go lower
        else:                    hi = mid   # too weak -> go higher
    return lo

# 4) parse "B1=46.0 B3=44.8" into a dict
def parse_kv(line):
    return {k: float(v) for k, v in (p.split("=") for p in line.split())}

# 5) count occurrences without a library
def counts(items):
    d = {}
    for x in items: d[x] = d.get(x, 0) + 1
    return d

# 6) first duplicate in a stream (set for O(n))
def first_dup(seq):
    seen = set()
    for x in seq:
        if x in seen: return x
        seen.add(x)
    return None
Interview Q&A
Q: Write a function to find the reference sensitivity by binary search.
A: Bracket the power [lo, hi]; test the midpoint; if the miss-detection rate is within limit the UE still decodes so search lower, else search higher; stop when the range is under your resolution. That's find_sensitivity above — O(log range) instead of a linear sweep (and it mirrors the real PRACH/sensitivity search, see PRACHDM01).
Q: Why is a set the right tool for "first duplicate"?
A: Membership testing in a set is O(1) average, so one pass over the stream is O(n). Using a list and 'in' would be O(n) per check → O(n²). Same reasoning behind using a set for detected-preamble bookkeeping.

1 · What the feature proves (say this first)
"RSSI accuracy validates that the RU's own reported received-power agrees with reality across the whole input range, per antenna / band / RU-model. I inject a known LTE UL signal at power P from the signal generator, then read RSSI from two independent places — the RU's get-rssi CLI (dBm + dBFS, the operator-facing number) and the PHY / L1 rct_stats (the internal number) — average N samples at each power, and record the difference PHY−CLI. A per-model offset calibrates the CLI readout. As a by-product, sweeping power from saturation down to the noise floor gives me the BLER-vs-power curve, so I also extract the 5% BLER sensitivity point. No pass/fail coloring — it's a calibration/characterisation test producing raw averages + diff."

3 · Step A — test_Rx_RSSI_Accuracy() only DECLARES (the naming convention)

5 · Step C — the U-shaped power sweep (the clever bit)
BLER-vs-power is U-shaped: ~100% at the saturated top (ADC hits full-scale → clipping → decode fails) and ~100% at the sensitivity floor (signal in the noise), with a clean ~0% valley in between. A naïve "step down until BLER rises" would stop at the wrong edge. So the controller runs three phases:
Phase A  descend from start by COARSE step, skipping the saturated top,
         until BLER settles <= 1%   -> we are now in the clean valley
Phase B  keep COARSE-stepping down through the valley
         until BLER rises above 1%  -> we found the low-power KNEE
Phase C  back off to last-clean power, step at FINE (0.5 dB);
         once BLER >= ~1% switch to ULTRA-FINE (0.1 dB) to pin the exact 5%,
         continue down until BLER >= 99%  (fully into the floor)
mode='sensitivity' -> coarse 5 dB in the flat + 0.1 dB at knee (fast, just pins 5%)
mode='accuracy'    -> uniform 0.5 dB everywhere (dense RSSI-vs-power, no ultra-fine)
mode='both'        -> uniform 0.5 dB + 0.1 dB at knee (default: dense + exact 5%)
This gives dense data where it matters (the knee) without wasting time taking 0.1 dB steps across the flat valley — a real speed/coverage trade the interviewer will appreciate you naming.

7 · Step E — the RU-CLI path: get_rssi_from_rrh() + extract_adc_values()

extract_adc_values(lines, antenna_index):
  data_lines = [l for l in lines if 'ADC_INDEX_' in l]
  adc_index  = adc_mappings[fhgw_band][band][antenna_index]   # logical ant -> physical ADC
  line       = data_lines[adc_index]
  re.search(r'adc_dbfs:([-\d.]+) dBFS,rssi:([-\d.]+) dBm', line) -> (rssi_dBm, dBFS)
The adc_mappings table matters: a logical antenna is not ADC N. On the 5-band AAU (b082028), for example, B28 antenna 0 reads physical ADC 4, antenna 1 → ADC 5. Getting that mapping wrong reads the wrong antenna's power — a real bug class. The session is also self-healing: if the radio fell off the fronthaul the read triggers the same recovery path as the sensitivity test instead of hanging on a dead prompt.

  frac  = (5 - bler[i-1]) / (bler[i] - bler[i-1]) # linear interp fraction
  return eirp[i-1] + frac * (eirp[i] - eirp[i-1]) # EIRP @ exactly 5% BLER
The whole report is best-effort / never raises into the road-trip — a broken matplotlib or a missing lib logs a warning and the test still passes its data through. Defensive by design so a reporting hiccup never fails a validated run.
Interview Q&A — how a VP / senior lead will probe this
Q: Walk me through what happens end-to-end when the RSSI-accuracy test runs.
A: test_Rx_RSSI_Accuracy declares the sheet/columns/frequencies and returns them; the road-trip driver loops antenna×freq, selects the antenna and restarts L1/L2, and calls configure_test_Rx_RSSI_Accuracy. That computes setup-loss/EIRP/TRP math, reads the RU model to pick the calibration offset, loads the ETM1.1 UL waveform, then sweeps SG power in a U-aware three-phase controller. At each power _measure reads PHY rct_stats once and N samples of RU-CLI RSSI + BLER, averages them, records PHY−CLI, and writes a row. At the end _rssi_acc_report builds the xlsx + BLER/RSSI graphs and interpolates the 5% BLER sensitivity.
Q: Why compare CLI RSSI against PHY RSSI at all — aren't they the same number?
A: No — they come from different subsystems. The CLI get-rssi is what the operator/EMS sees (post-calibration, per-ADC), the PHY rct_stats is L1's internal estimate. If they diverge, either the RU's RSSI calibration/offset is wrong or the reporting path is broken. The test characterises that gap across the full power range, so a calibration error shows up as a consistent PHY−CLI diff.
Q: Why is BLER high at BOTH the top and bottom of the power sweep?
A: At the top the ADC saturates/clips (input above full-scale), so the samples are distorted and decode fails; at the bottom the signal drops into the noise floor and SINR collapses. In between there's a clean ~0% valley. That U-shape is exactly why the sweep first descends to find the clean region before hunting the low-power knee — otherwise you'd mistake the saturated top for the sensitivity edge.
Q: You read the PHY once per power step but the CLI N times — why the asymmetry?
A: The PHY value comes from tailing l1_Debug.log inside the phynode container, which only rewrites every few seconds. The N CLI reads complete in milliseconds, so reading the PHY per sample would just return N identical values plus N wasted docker round-trips. One PHY read per step, mirrored across the sample rows, is correct and much faster.
Q: How do you go from "logical antenna 2" to the right RSSI number in the CLI output?
A: get-rssi prints one line per physical ADC. A per-band mapping table (adc_mappings[fhgw_band][band][antenna_index]) translates the logical antenna to the physical ADC index — on the 5-band AAU, B28 antenna 0 is ADC 4, not ADC 0 — then I regex that line for adc_dbfs and rssi. Wrong mapping = you silently report a different antenna's power.
Q: What's EIRP vs TRP here, and where does the +3/+6 dB come from?
A: EIRP at the RU input = generator power + external_gain (which is −setup_loss, the cable/path loss). TRP adds the splitter correction: the low bands (B8/B28) feed through a 2:1 splitter (+3 dB) and the mid bands (B1/B3)/B41 through a 4:1 (+6 dB), so TRP = EIRP + that correction. It's derived from the band, with a config override.
Q: How would you extend this test to a new band or RU model?
A: Almost no code — add the band's ADC layout to adc_mappings, add the frequencies to the cadence, and populate rssi_model_offsets[model][fhgw_band][band][ant] in fdd_test_setup.json. The sweep, averaging, PHY/CLI reads and report are band-agnostic; only the mapping and calibration tables are data.
Q: If PHY−CLI diff is, say, 3 dB and constant across power, what do you conclude?
A: A constant offset points to a calibration/offset error in the RU's RSSI reporting (or a wrong rssi_model_offsets entry) — not a linearity problem. A diff that grows toward the top would suggest compression/clipping; one that grows at the bottom suggests a noise-floor/SINR issue. Constant → fix the offset table; power-dependent → investigate the analog/ADC front-end.
AUTO09 Self-Healing Traffic Watchdog — why a 24 h stability run lost UL for 15 hours, the per-stream heal loop, its parameters, and the false-restart lesson Advanced click to expand ▾
In plain English
In a 24-hour B3+B7 stability run, Band 7 uplink throughput fell to 0 and stayed there for ~15.7 hours, while downlink kept running. The radio was fine. The test harness had silently lost its UL traffic generator, and nothing noticed. The fix was a watchdog that checks every stream while traffic runs and restarts only the dead one. It records each restart, so it never hides a real RAN problem.
Level 1 — root cause: an iPerf asymmetry
DirectionWhere the sender/receiver runsAfter a radio blip
DLUDP server (receiver) on the phone, bound to the UE IPa server just waits, so it resumes when packets return: DL recovers by itself
ULUDP client (sender) on the phone, bound to the UE IPsendto() fails when the radio drops and the client process exits: UL = 0 forever
The UE re-established (new RNTI) and kept the same IP, so this was never an "IP changed" problem, just a dead sender. Nobody noticed because the test started iPerf once for 24 h and then blocked in a sequential "wait for completion" (DL first), so UL health was never checked while traffic ran.
Level 2 — the design
Replace the blind wait with a loop that runs during the traffic window. Every poll seconds, read each UE × direction's live throughput. If a stream reads ~0 for zero_streak consecutive polls, kill and restart only that UE+direction. The restart builds a fresh iPerf object, which re-resolves the UE IP (runs ip route on the phone), so it would follow an IP change for free. It never fails the test. It returns events for the report.
def monitor_and_heal(ue_list, duration, poll=20, zero_streak=3, max_restarts=10,
                     ramp_grace_polls=3, zero_threshold=1.0, require_seen_alive=True):
    streak, restarts, grace, seen_alive, events = {}, {}, {}, {}, []
    end = time.time() + duration
    while time.time() + poll < end:
        time.sleep(poll)
        for ue in ue_list:
            for d in ('ul', 'dl'):
                key = (ue, d)
                if grace.get(key, 0) > 0:
                    grace[key] -= 1
                    continue
                tpt = read_live_throughput(ue, d)
                if tpt is not None and tpt >= zero_threshold:
                    seen_alive[key], streak[key] = True, 0
                    continue
                if require_seen_alive and not seen_alive.get(key):
                    continue
                streak[key] = streak.get(key, 0) + 1
                if streak[key] < zero_streak or restarts.get(key, 0) >= max_restarts:
                    continue
                events.append(restart_stream(ue, d, remaining=end - time.time()))
                restarts[key] = restarts.get(key, 0) + 1
                streak[key], grace[key] = 0, ramp_grace_polls
    return events

Level 3 — validation: the proof and the new problem it revealed
Smoke run (200 s): the full restart path worked (read → detect → kill → restart → IP re-resolved → report). It also exposed a startup false positive: a stream still ramping read "None" in its first ~60 s and was restarted. require_seen_alive was added for this.
Overnight 12 h run: the headline result. At one point the B7 UE re-established (new RNTI). DL recovered instantly, UL stuck at 0 with UL MCS floored to 9, which is the same failure class as the original. The watchdog detected it and restarted B7 UL, and UL recovered in ~38 s instead of 15.7 h.
But: the watchdog logged 20 restarts in that night and only one was a real stall. The rest were triggered by read failures: the SSH read of the iPerf result file failed during a connectivity glitch, returned None, and the code treated None like a confirmed zero. That burned the restart budget (one stream hit its cap within 46 minutes) and briefly interrupted healthy streams.
Level 4 — the lessons (apply them to any watchdog)
1. Distinguish "I could not read it" from "I read zero". A read failure should skip the poll, not count toward the streak. Only a successful read of ~0 is a stall.
2. Corroborate before acting: a real UL stall also showed UL MCS floored at 9 in the eNB stats. Requiring a second independent signal removes most false positives.
3. Budget and grace: caps prevent storms, but false positives spend the budget you need for the real event.
4. Never hide the RAN: every heal is reported in the test message, for example Self-heal: 1 restart | [time] B7 ul restart#1 ok=True IP same. That is the breadcrumb to go and find why the UE dropped in the eNB logs.
5. Know your KPI layer: the stats tool reported eGTP (~177 Mbps offered) while the dashboard showed PDCP (~167 delivered) (LF20).
6. Test the healer: kill the phone-side UL client mid-run (adb shell pkill -f "iperf -u -c") and confirm a restart within ~poll × zero_streak seconds.
Interview Q&A
Q: In a long test, UL throughput went to 0 and stayed there while DL recovered after a radio blip. Why, and how do you fix it?
A: With iPerf the DL receiver on the phone is a UDP server that simply resumes, but the UL sender is a client process on the phone that exits when sendto() fails during the outage. Nothing restarted it because the test blocked in a sequential wait. Fix: a watchdog that polls each UE+direction, restarts only the dead stream after N consecutive zero reads (re-resolving the UE IP), caps restarts, and reports every event.
Q: Why debounce with a zero-streak and add ramp-grace / seen-alive rules?
A: Throughput naturally dips for a second or two, and a new stream reads nothing while it starts. Without debounce and grace the watchdog restarts healthy streams, disrupting the test and wasting its restart budget.
Q: Your watchdog restarted streams 20 times but only one stall was real. What went wrong?
A: It treated a failed read (SSH/tail error returning None) the same as a confirmed zero. Separate the two: a read error skips the poll, and only a successful ~0 reading counts. Optionally require a corroborating signal such as UL MCS dropping to the floor in the eNB stats.
Q: Why must a self-healing test still report every heal?
A: Healing keeps the test running, but the underlying cause (why the UE dropped) is a potential RAN bug. The logged time, stream and outcome let you correlate with eNB/CWS logs afterwards. Silent healing would hide defects.

Level 3 — reading the fails correctly
1. "The alarm did not raise" is not automatically a product bug. All 3 fails (CMN_012, CMN_015, CMN_018) were the same symptom: no alarm after injection. Two very different things produce that symptom: the RU did not report a real fault, or the injection never created the fault. The review concluded that the injection methods needed software review, and they were not raised as product defects. This is why step 3 of the sketch matters. Read the cause back (the hwmon value, the interface state, the I2C register) before you blame the RU.
2. The CMN_010 fix. FREERUN first failed because the test disabled a fixed interface name. The two RRHs hang off different NIC ports (for example ens3f1np1 for b3 and ens3f2np2 for b28). If you disable the wrong port, the RU under test never loses PTP, so freerun never comes. The fix was to auto-detect the PTP interface per RRH. The same auto-detection of PTP interface and OAM profile is what makes --rrh both reusable across bands and units.
3. Flips on re-run. CMN_016 and CMN_036 failed first and passed on re-run. Track such flips separately. They are either timing margins in the test or intermittent RU behaviour, and both need an owner.
4. Always clean up. A sync TC that stops in the middle with the PTP port still down will break every later TC on that bench. The re-enable, clear check and stack recovery must run in a finally / teardown path. The same applies to thermal limits and NETCONF configs.

What a healthy link-adaptation trace looks like. As SNR falls, CQI falls, the scheduler steps MCS down, RI drops (4 → 2 → 1 layers), and BLER stays near the scheduler's target (typically around 10 %) because outer-loop link adaptation keeps correcting. Throughput should slope down. A cliff with BLER shooting up means link adaptation is not keeping up, and that is a finding in its own right.
Why "recovers at 0 dB" is part of the pass: 161 of 166 Mbps (about 97 %) proves the cell and UE came back to full rate after being pushed to the edge. A stuck low MCS or rank after the sweep (the same failure class as AUTO09) would otherwise hide.
Why 5 power cycles per level: RACH is statistical. One attach proves nothing. Power-cycling the UE forces a fresh initial access (cell search → PRACH → RAR → RRC setup) every time, and 5 tries per level gives a success-rate percentage.
Level 3 — the B28 case, and the physics behind a 25 dB gap
Control case: the same DU, UE type, method and bench gave B3 a -110 dBm limit. That clears the DU, the EPC and the automation. The difference had to be on the B28 side.
Why RACH at the cell edge is an uplink problem: the x-axis is downlink RSRP, but access fails when the RU cannot detect the preamble. The UE sets its PRACH power by open-loop power control (target received power + estimated path loss), capped at its maximum of about 23 dBm. Past that point every extra dB of path loss arrives at the RU as a weaker preamble. A receiver with a sensitivity problem reaches its detection limit much earlier, so access dies at a much stronger DL RSRP.
The same fault also stalled B28 TCP: DL TCP needs a steady flow of UL ACKs. When UL is weak, ACKs are lost and DL TCP stalls even though the DL radio is fine. If a DL TCP number looks bad, always check UL health too (and use UDP to separate the two directions, see AUTO12).
Cross-check with conducted RCT: the conducted B28 campaign (FC09D) had already measured a receive-sensitivity shortfall and poor PRACH detection on B28, while B3 passed. The E2E sweep reproduced the same conclusion independently. Do not expect the dB numbers to match one-to-one: an E2E coverage limit also includes UE power control, PRACH detection thresholds and the unit's fault-20 behaviour. Treat the E2E sweep as corroborating evidence and the conducted test as the measurement.
Pitfalls: (1) all four RX/TX ports must be attenuated equally, or the rank and MIMO behaviour is not representative. (2) Give each step enough dwell time for CQI and outer-loop link adaptation to settle before you sample. (3) Report against UE RSRP, not attenuator dB, because the path-loss offset differs per band and per cable set.

Q: How do you automate a coverage or cell-edge test in the lab?
A: Put a programmable attenuator between the RU and the UE, run continuous traffic, and step the attenuation. At each step, wait for the link to settle, then log the UE RSRP, the DU SNR/CQI/RI/MCS/BLER and the throughput. Finish by returning to 0 dB and checking that throughput recovers. A: The shared parts (DU, EPC, UE type, method) are cleared by the B3 control case, so the problem is on the B28 RRH. A: TCP depends on UL ACKs. A weak uplink loses ACKs, the TCP window collapses and DL stalls, even though the DL radio link is healthy. Test each direction with UDP to separate the radio from the transport.

How a scenario CSV becomes test cases (a teaching sketch; column names other than the filter keys and pass-% fields are illustrative):
import csv, pytest

def load_scenarios(path, flt):
    with open(path, newline="") as f:
        rows = list(csv.DictReader(f))
    return [r for r in rows if all(r.get(k) == v for k, v in flt.items())]

def pytest_generate_tests(metafunc):
    if "scenario" in metafunc.fixturenames:
        flt = metafunc.config.scenario_filter          # e.g. {"direction": "DL_UL", "protocol": "TCP"}
        rows = load_scenarios("throughput_scenarios.csv", flt)
        if not rows:
            raise pytest.UsageError(f"scenario_filter {flt} matched 0 rows")
        metafunc.parametrize("scenario", rows, ids=[r["name"] for r in rows])

def test_throughput(scenario, traffic, kpi_poller):
    res = traffic.run(scenario)                      # iperf, per direction
    kpis = kpi_poller.summary()                      # PRB, MCS, RI, SNR, CQI, BLER
    assert res.duration_pct >= float(scenario["min_duration_pct"])
    assert res.dl_mbps >= float(scenario["dl_target"]) * float(scenario["dl_pass_pct"]) / 100
Each CSV row becomes its own test ID in the JUnit XML and the report, so one bad scenario does not hide the others.
Level 3 — traps that make benchmark numbers lie
1. A filter that matches nothing is not a pass. A typo such as bandwidth_label=15Mhz selects zero rows. pytest then exits with code 5 ("no tests collected"). If CI treats every non-1 exit as success, you get a green night with no traffic at all. Fail loudly on zero matches (as the sketch does) and make CI treat exit code 5 as a failure.
2. "Duration %" catches a dead traffic generator. If iPerf dies halfway, the average over the remaining samples can still look fine. Requiring the run to last most of its planned time catches it. AUTO09 shows the extreme version: a UL sender that died and stayed dead for 15 hours.
3. TCP vs UDP answer different questions. UDP at a fixed offered rate measures what the radio can carry (loss = datagram error %). TCP measures what an application gets, and it is limited by window size, RTT and UL ACK health (a weak UL stalls DL TCP, see AUTO11). Use UDP to benchmark the RAN, and TCP to benchmark the user experience.
4. Know the KPI layer. The UE-side iPerf number, eNB PDCP throughput and eGTP throughput differ by headers and retransmissions (LF20, AUTO09). Compare like with like across builds.
5. The radio KPIs explain the number. Low DL with RI stuck at 2 means a MIMO or channel problem, not a scheduler problem. Low DL with high PRB use and good MCS means capacity. Good RI/MCS but low PRB use means the scheduler is not being fed (the traffic source or transport). This is why PRB, MCS, RI, SNR, CQI and BLER are logged next to every throughput value.
6. CA needs UE support. An inter-band 2CC run with a UE that lacks the band combination silently falls back to 1CC. Check the UE capability (LF15) and the SCell activation before you blame the RU.
Interview Q&A
Q: Why drive throughput tests from a scenario CSV instead of separate test functions?
A: The logic is identical and only the parameters change. A CSV row per scenario means new cases need no code, a command-line filter picks a subset for CI, and each row still reports as its own test ID. It also keeps targets and pass percentages next to the scenario, where reviewers can see them.
Q: Your nightly benchmark is green but took 30 seconds. What happened?
A: Most likely the scenario filter matched zero rows, pytest collected nothing (exit code 5), and CI treated that as success. Fail on an empty selection and treat exit 5 as a failure.
Q: What pass criteria besides "throughput ≥ X % of target" would you add, and why?
A: Datagram error % for UDP (the offered traffic really got through), and duration % (the traffic ran for its whole window, so a dead iPerf cannot pass on a partial average). Log PRB/MCS/RI/SNR/CQI/BLER as well, to explain any miss.

A: Inter-band CA needs a UE that supports the CA_3-28 band combination. With the available UE, intra-band B3+B3 (15+15 MHz) was the CA configuration that could be exercised.

Every verdict has a direction. The enum in the source is PASS_RESULT / MARGINAL_RESULT (shown as Pass(Tolerance)) / FAIL_RESULT. A summary of the rules (a sketch, not the framework code):
PASS_RESULT, MARGINAL_RESULT, FAIL_RESULT = "Pass", "Pass(Tolerance)", "Fail"

def verdict(measured, kpi, tol, better):
    if better == "higher":
        if measured >= kpi:        return PASS_RESULT
        if measured >= kpi - tol:  return MARGINAL_RESULT
        return FAIL_RESULT
    if better == "lower":
        if measured <= kpi:        return PASS_RESULT
        if measured <= kpi + tol:  return MARGINAL_RESULT
        return FAIL_RESULT
    lo, hi = kpi
    if lo <= measured <= hi:                 return PASS_RESULT
    if lo - tol <= measured <= hi + tol:     return MARGINAL_RESULT
    return FAIL_RESULT
DirectionTests
higher is betterACLR (dBc), dynamic range
lower is betterEVM %, reference sensitivity and ACS/blocking (RU input power at the BLER crossing), PRACH (input power at 1 % missed detection)
windowoutput power (low/high, or configured − measured within ± x dB), frequency error (± Hz, or ppm of the carrier)
FWK1 adds the fourth outcome: Not Tested counts as a Fail in the fail rate, and an empty verdict list also records a Fail.
Level 3 — why you must read this setup's files, and a correction
1. The "same" limit differs by setup file. ACLR is 54 dBc with a 1 dB tolerance inline in a 5G FHGW Test-ID, 55 dBc with a 0.8 dB tolerance in the 4G FHGW box file, and 55 dBc with 0 tolerance in the Metro file (FC16, KPI01). EVM is per E-TM in the FHGW 4G file (17.5 % QPSK, 12.5 % for E-TM 3.2, 8 % for 64QAM, 3.5 % for 256QAM, i.e. the 3GPP values), but 3.5 % for every E-TM in the Metro file. Frequency error is 0.05 ppm plus 12 Hz tolerance in one file and 0 Hz tolerance in another. Never quote a limit without naming the setup and the file.
2. Layer precedence explains "I changed the value and nothing happened". The RU pytest documentation describes the merge as setup_configuration/ → cws_sources_<tech>/ → test_inputs_<tech>/ → one test_config singleton, where later layers win. If test_inputs defines the same key, your edit in setup.json is silently overridden. Search all layers for the key before editing. For thresholds there is a similar order: a tc_cadence RRH-Thresholds override, then the KPI file, then a hard-coded fallback (FC16).
3. Groups multiply. One Test-ID in a group with 4 BWs × 3 frequencies × 4 antennas is 48 measurements, and each can have several KPIs. When a report shows "ACLR fail", the Group axes tell you which of the 48. That is the first thing to read, before the value.
4. Rules the framework documentation insists on: always run through the run_*.py wrappers (they load the config layers and the report plugins), tests never import products directly (FWK1 golden rule), and credentials in config should come from ${ENV_…} variables rather than plain text.
5. Correction to M12. The overview box in M12 lists file names such as rct_report.pdf / rct_results.json and Test IDs such as TX_POWER / SENS_B1, plus a DSA JSON example. Those are illustrative, not the real schema. Real Test-IDs are test method names (test_Tx_ACLR, test_Tx_BS_Output_Power, test_Tx_modulation_analysis, test_Rx_Reference_Sensitivity_Level, test_Rx_PRACH, ACS_7_4_1 …). Results go to report.html, the Excel workbook and Elasticsearch. The transceiver field in the real ACLR Test-ID is trx (M12 shows trb).
Interview Q&A
Q: Someone hands you a test name you have never seen. How do you work out what it does and what makes it pass?
A: Find the Test-ID in the setup's tc_cadence.json: test_type gives the analyzer mode, and 5G tests carry their KPIs inline. For 4G, look up the limit and any band override in the kpi_thresholds file. Find the Group that lists the test (band/BW/frequency/TM) and the Cadence that includes that group. Then apply cable loss and the verdict direction.
Q: Why can one 5G Test-ID produce several verdicts?
A: Because the modulation-analysis measurement returns several quantities at once. Its KPI block has output power (window), EVM (max %), frequency error (± Hz) and TAE (max ns), and each is judged separately.
Q: ACLR is 54 dBc in one place and 55 dBc in another. Which is right?
A: Both. They come from different setups and files: 54 with 1 dB tolerance inline in a 5G Test-ID, 55 with 0.8 or 0 dB tolerance in 4G threshold files, and 52 for some dual-band overrides. The applicable limit is the one resolved for that setup, band and dual-band step.
Q: What is MARGINAL_RESULT and how is it computed for sensitivity?
A: It is the Pass(Tolerance) verdict. Sensitivity is lower-is-better: pass if the RU input power at the 5 % BLER crossing is ≤ KPI, marginal if ≤ KPI + tolerance (e.g. 1.0 dB), otherwise fail.
Q: You changed a value in setup.json and the test ignored it. Why?
A: The configuration layers merge in order and later layers win. A test_inputs file (or a cadence-level override) probably defines the same key. Search every layer for the key.

Level 3 — what an experienced reviewer notices
1. Stale documentation. The docstrings say 180 s and DL 45 / UL 17, and the test tag says 180s. The Variables that actually run are 600 s and 43.75 / 18.75. The Variables section is the truth. Fix docs in the same change that edits a variable.
2. Implicit coupling through suite variables. Set Suite Variable makes ${cws_b4}, ${ue_b4}, ${rsrp_b4} and others visible to resource keywords without passing them. That is convenient, but a keyword such as Verify_B4B7_Throughput_Results silently depends on a variable set three steps earlier. If you reorder or reuse steps, the failure is "variable not found" far from the cause. For new keywords, prefer explicit [Arguments].
3. Deliberate tolerance. RSRP defaults to N/A before the TRY, and EXCEPT *RSRP* *attribute* glob-matches the error text, so a failed RSRP read only logs a WARN. Throughput is the objective and RSRP is context. The defaults stop the later Excel write from hitting an undefined variable.
4. Collected but not saved. The basic Excel writer records only RSRP. The OAM KPIs (MCS, SNR, RSSI, PRB) from step f are collected but not written. The full writer is Write_B4B7_OAM_KPI_Results_To_Excel, and the comment above the call wrongly claims it writes KPI results. When throughput fails, those KPIs are the first thing you need, so swap the keyword.
5. Configuration through the management plane. The test writes cell parameters via ACS (TR-069) with read-compare-write and a conditional reboot. It never edits files on the radio. That is idempotent: a re-run on an already-configured node skips the reboot. (CM17 shows why editing a file on an AAU often does nothing.)
6. Stability, not a single measurement. The Stability tag, the crash-file snapshot in suite setup and the 600 s window make this a building block for long runs. Pair it with a stream watchdog (AUTO09) and a crash triage pipeline (AUTO14) for 24–72 h campaigns.
Where to look when it breaks: proxy or connection errors → Real UE CI-PreSuite. "No UE found with VoLTE_band4" → the UE pool config. Wrong BW or CA still on → Configure_RU_Bandwidth_And_CA_Settings. Low throughput → RSRP in the summary, then the OAM KPIs.

Why the file name is enough to find the thread: the kernel names core files using the pattern in /proc/sys/kernel/core_pattern. With a pattern such as core.%e.%p, %e is the name of the thread that crashed (its "comm", at most 15 characters) and %p is the PID. That is why the stack names its threads carefully. MacTxCtlData_C0 is exactly 15 characters. A longer thread name would be cut short and stop matching the table.
After classification, get the stack trace. The report tells you where to look. The backtrace tells you why:
tar -xzf <archive>.tgz <path>/core.MacTxCtlData_C0.12345

gdb <matching-binary-with-symbols> core.MacTxCtlData_C0.12345
(gdb) bt
(gdb) info threads
(gdb) thread apply all bt
The binary must be the exact build that crashed, with debug symbols. file core.* shows which executable produced the core. A mismatched binary gives a backtrace that looks plausible but is wrong.
Level 3 — making the triage trustworthy
1. Mark every archive as checked, not only the ones with a crash. In the documented loop, checked.txt is appended only in the crash branch. An archive with no core is then scanned again on every 5-minute poll and adds another "No Core" row each time. Move the append after the if.
2. grep core is too loose. It also matches corelist.txt, score.log or a directory called core_logs/, which gives false crash alerts. It also returns several lines when one archive holds two cores, and basename of a multi-line string breaks the lookup. Match the naming pattern exactly and loop over each core:
for file in $(ls -rth /data/$SETUP_NAME/$CURRENT_DATE/*.tgz); do
    grep -Fxq "$file" checked.txt && continue
    cores=$(tar -tzf "$file" | grep -E '(^|/)core[.][^/]+$')
    if [ -z "$cores" ]; then
        ./convert_html.sh "$file" "No Core in this file"
    else
        for c in $cores; do
            name=$(basename "$c")
            ./determine_task_pod.sh "$name"
        done
    fi
    echo "$file" >> checked.txt
done
3. Ambiguous task names. recv_data_0 appears under both gnb_du_layer2 and gnb_cu_pdcp, and phy_logger under both PHY processes. A first-match lookup blames whichever section comes first. Break the tie with the archive's origin (which pod's log directory the core came from) or with file core.* (the executable name).
4. One crash, many cores. When one process dies, its peers often abort afterwards (for example a watchdog or an interface peer), leaving several cores within seconds. Sort by timestamp and treat the earliest core as the primary. The rest are usually consequences.
5. It complements, not replaces, the other stability tools. AUTO09 keeps the traffic alive and logs each heal. RBTCAUSE01 attributes RU-side reboots. This tool classifies BBU-side software crashes. A complete 24–72 h report shows all three on one timeline, so a throughput dip can be matched to a crash or reboot.
6. Sanity rules from the tool's own guidance: do a 4-hour run before a 48-hour one, watch the first 2 hours, analyse crashes within 24 hours, and try to reproduce each one in a shorter test.

Stationary clustering: cars stop at traffic lights, and 60 samples at one spot would dominate any average. Points within a radius are grouped and given the first point's timestamp and location. The search covers the whole dataset, so a loop route that returns to its start joins the original cluster. The cost is O(n²), which is fine for 600–1800 points (a 30-minute drive).

Two modes: chronological (the base point is the first point in time; best for one drive), and geographic / "consistent" (sort by latitude then longitude first, so the same place tends to get the same cluster_id on different drives). That makes a morning vs afternoon comparison possible, for example cluster 5 RSRP -85.2 vs -82.1 dBm (+3.1 dB). A sketch of both:
from math import radians, sin, cos, asin, sqrt

def haversine_km(lat1, lon1, lat2, lon2):
    dlat, dlon = radians(lat2 - lat1), radians(lon2 - lon1)
    a = sin(dlat / 2) ** 2 + cos(radians(lat1)) * cos(radians(lat2)) * sin(dlon / 2) ** 2
    return 2 * 6371.0 * asin(sqrt(a))

def cluster(points, threshold_km=0.005, geographic=False):
    order = sorted(range(len(points)), key=lambda i: (points[i].lat, points[i].lon)) if geographic \
            else range(len(points))
    cluster_id, done, next_id = [None] * len(points), set(), 0
    for i in order:
        if i in done:
            continue
        base = points[i]
        for j in order:
            if j not in done and haversine_km(base.lat, base.lon, points[j].lat, points[j].lon) <= threshold_km:
                cluster_id[j] = next_id
                points[j].timestamp, points[j].location = base.timestamp, base.location
                done.add(j)
        next_id += 1
    return cluster_id

Level 3 — the data traps (each one has broken a real drive-test report somewhere)
1. Time zones. NMEA time is always UTC. A KPI tool often logs local time. If one side is off by hours, nothing falls within 3 s, and you get a merged file with KPIs but no positions. Normalise both sides to UTC before merging, and always print how many rows merged (as the sketch does).
2. GGA has no date. The date comes from RMC. A drive across midnight UTC goes back to 00:00:00 and can merge with the wrong day unless date and time are combined.
3. ddmm.mmmm is not decimal degrees. 4807.038 means 48° 07.038', which is 48.1173°. Reading it as 48.07038° puts every point about 5 km away. Also apply the sign for S and W.
4. Talker IDs. Multi-constellation receivers send $GNGGA / $GNRMC (GN = combined GNSS) instead of $GPGGA. A parser or health check that only looks for $GP… finds zero sentences on such a receiver. Match on the last three letters of the sentence type.
5. "Consistent" clustering is only mostly consistent. Cluster IDs are assigned in sorted order. If the afternoon drive has one extra point further south (a detour, a GPS jump), every ID after it shifts by one, and the per-cluster comparison quietly compares different places. More robust options: cluster the combined points of both drives once and then split by drive, or snap points to a fixed grid (for example a geohash cell) so the ID depends only on position.
6. Fix quality and HDOP. Drop or flag points with fix quality 0, or with a high HDOP, before clustering. Otherwise a cold-start jump becomes its own "stationary location".
7. Lab "drive tests". The framework can also simulate movement with attenuators and path-loss models. That is useful for repeatable handover logic tests, but it does not reproduce fading, shadowing or real neighbour interference. Do not report simulated coverage as field coverage (AUTO11 covers attenuator sweeps).
8. Sanitise before sharing. Drive logs contain precise locations, and index names contain project or customer labels. Use neutral names for anything that leaves the team.
Interview Q&A
Q: How do you attach a GPS position to every KPI sample in a drive test?
A: Log NMEA from the GPS receiver and KPIs from the RAN or UE in parallel. Parse GGA for position, VTG/RMC for speed and date, convert everything to UTC, then do a nearest-time join with a tolerance (3 s here). Check how many rows merged, and upload to Elasticsearch with a geo_point field for map views.
Q: A merged drive-test file has all the KPIs but empty latitude and longitude. What is the first thing you check?
A: Time alignment. NMEA is UTC and the KPI tool may log local time, so the two never fall within the merge tolerance. Also check that the receiver had a fix (quality ≥ 1) and that the parser recognises $GN… talker IDs.
Q: Why cluster stationary GPS points, and how do you pick the radius?
A: So that time spent stopped (traffic lights, junctions) does not dominate per-location statistics, and so repeated visits to one spot are grouped. Pick a radius just above GPS accuracy (5 m by default, since receivers are typically accurate to 2–5 m). Larger radii merge distinct locations.
Q: You want to compare RSRP at the same places on two drives. What can go wrong with per-drive cluster IDs?
A: IDs depend on which points exist in each drive, so one extra point can shift the numbering and you end up comparing different places. Cluster the union of both drives once, or use a fixed spatial grid, so an ID means the same location in both.

Level 3 — design choices, pitfalls and coverage gaps
1. Same layers, different top. The Robot libraries are thin: they strip quotes, log the step and call the same Steps classes the pytest RCT code uses. Business logic belongs in Steps; a keyword that grows real logic is a smell.
2. Continue-on-failure is a double-edged tool. It gives a full list of IE failures per run, but a failed precondition (Xn not up, UE without IP) then produces a cascade of secondary failures. Read the first failure first.
3. Expected values from the same capture. Several counter tests compute the expectation from the pcap of the same run (ZT2). It adapts to ping-pong but is blind to a capture gap; keep one absolute sanity check.
4. Fixed sleeps and warn-on-failure injection. Many cases wait 200-700 s and inject faults with warn on failure. The test is slow and can pass without the fault having happened — check pod restart counts or PIDs, and poll for state instead of sleeping.
5. Hard-coded lab facts. SSB/ARFCN values (643968, 646716), pod name patterns (cunode01, dunode02/03, phynode, cpanode) and log paths are embedded in keywords. When a bench differs, tests fail for reasons unrelated to the feature; moving them into setup config is a cheap robustness win.
6. Visibility requirements. RRC-level IE checks need null ciphering (NEA0) and the right Lua dissector; a new message type or port needs the dissector updated before any test can assert it.
Coverage note for the owner: across all ≈3,800 robot files there are no CMAS/ETWS (public warning) tests and no conditional-handover (CHO) tests.

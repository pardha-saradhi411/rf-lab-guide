PT01 MAC Layer — scheduling, HARQ, multiplexing: the traffic controller of the air interface Intermediate click to expand ▾
What MAC does — plain English
MAC (Medium Access Control) is the traffic police between the PHY layer and the RLC layer. It decides: which UE gets which resource blocks in this 1ms subframe, how much power, which MCS. Everything you measure in RCT (throughput, BLER, scheduling) is MAC's job.

MAC sits at Layer 2 — above PHY (Layer 1) and below RLC (Layer 2 also, higher sub-layer)

HARQRetransmission with soft combining — reuses failed packets to improve decodingBLER measurement in your sensitivity test
MultiplexingCombines data from multiple RLC bearers into one MAC PDUMultiple bearers = default+SRB+DRB in same transport block

HARQ deep dive — why BLER ≤ 5% is the sensitivity threshold
HARQ = Hybrid ARQ = combines Automatic Repeat reQuest with soft combining.

Process:
1. gNB sends transport block (TB) → UE decodes → if fail: sends NACK
2. gNB retransmits SAME data (chase combining) or incremental redundancy (IR)
3. UE soft-combines both attempts → higher chance of decoding
4. Max 4 HARQ rounds (LTE) → if still fail = BLER counted

Your sensitivity test measures BLER: at the sensitivity threshold, ~5% of TBs fail after all HARQ rounds. This is A1-3 FRC (QPSK 1/3 rate) — the minimum coding rate 3GPP defines for sensitivity.

8 HARQ processes in LTE: allows 8 TBs in flight simultaneously (pipelined). Round-trip delay = 8ms. B41 TDD has different HARQ timing due to slot structure.

Interview Q&A
Q: BLER is 20% at −65 dBm. The sensitivity limit is −68 dBm. What's happening?
A: At −65 dBm (3dB above the limit), BLER should be near 0%. 20% BLER at this power indicates: LNA degraded, cable fault, DSA mismatch, or HARQ is disabled/misconfigured. Check: sensitivity test at −50 dBm first — if BLER still fails, UL path is broken.
Q: What is NDI in the MAC header?
A: New Data Indicator — 1-bit toggle. Flips for a new TB. Stays same for HARQ retransmission. The receiver uses NDI to know: 'is this new data (start fresh combine buffer) or a retx (soft combine with previous)?'. Incorrect NDI = UE discards retx, can't combine = BLER jumps.
PT02 RLC Layer — TM/UM/AM modes: how data reliability is guaranteed above MAC Intermediate click to expand ▾
What RLC does — plain English
RLC (Radio Link Control) sits above MAC and below PDCP. It handles segmentation (big packets → small pieces that fit in one TTI) and reassembly (pieces → original packet). It also provides reliability (AM mode retransmits failed RLC PDUs).
Three RLC modes — when each is used
ModeFull nameError correctionUsed forVoLTE relevance
TMTransparent ModeNone — just passes dataBCCH, CCCH, PCCH (broadcast/paging)SIBs, paging messages
UMUnacknowledged ModeNo retx, but sequence numberedDTCH real-time (VoIP), MCCHVoLTE voice bearer — latency > reliability
AMAcknowledged ModeARQ retransmissionDTCH data bearersVoLTE IMS signaling SRB
AM mode ARQ — how it differs from HARQ
HARQ is at MAC layer — fast, hardware, 4 rounds, 8ms round trip.
RLC ARQ is at RLC layer — slower, software, many rounds, ~50ms round trip.

They work together: HARQ is the first line of defense (fast). If HARQ fails → MAC delivers corrupted TB to RLC → RLC AM detects via CRC → RLC ARQ retransmits → PDCP gets clean data eventually.

STATUS PDU: RLC AM receiver sends STATUS PDU listing which SNs were missing. Transmitter retransmits only those. Efficient — not retransmitting everything.
Segmentation and reassembly — why it matters for RCT
IP packet = up to 1500 bytes. One MAC TB at 10MHz QPSK = ~300 bytes.
RLC segments the IP packet across multiple TTIs → each gets an RLC PDU with SN.
Receiver reassembles when all segments received.

In your tests: FRC A1-3 (QPSK 1/3) sends one TB per TTI of fixed size. The RLC layer is essentially transparent in this test — MAC drives everything. RLC AM ARQ would only be visible in data throughput tests.
Interview Q&A
Q: VoLTE voice quality degrades but RTP stream shows no packet loss. What RLC mode is voice?
A: VoLTE voice uses RLC UM mode — no retransmission. Packet loss at RLC level directly becomes voice quality loss. The issue is at L1/L2 (BLER, HARQ), not RLC. Check: PDCP discard timer, HARQ BLER in that sector, and UL power control for the UE.
Q: Why does RLC exist if HARQ already handles retransmissions?
A: HARQ is limited to 4 rounds over 8ms — leaves residual BLER ~1%. For best-effort data (file download), 1% BLER over time compounds to significant loss. RLC AM ARQ handles the residual failures. HARQ = fast and hardware; RLC ARQ = reliable and software.

ROHC — why 60-byte headers matter for VoLTE
VoLTE RTP packet: 20 bytes payload (voice sample) + 12 RTP + 8 UDP + 20 IPv4 = 60 bytes overhead.
Without ROHC: 60-byte header + 20-byte data = 75% overhead → TERRIBLE efficiency
With ROHC: 3-4 byte header + 20-byte data = ~17% overhead → acceptable

ROHC works by: establishing context (first few packets send full header), then sending only fields that change (sequence number, timestamp). Static fields (IP addresses, ports) compressed to 0 bits after context established.

PDCP in EN-DC (LTE+NR dual connectivity)
In EN-DC, PDCP runs on the MN (Master Node = LTE eNB) for SRBs.
For DRBs (data): PDCP can split — send half the data over LTE and half over NR.
This is why PDCP has duplicate detection: same SN might arrive from both legs.

Handover during EN-DC: PDCP SN continuity maintained. UE doesn't need to retransmit from PDCP perspective — RLC handles retransmissions per leg.
Interview Q&A
Q: Why is integrity protection only for SRBs and not DRBs?
A: Adding 4-byte MAC-I to every user data packet would add significant overhead to high-speed DRBs (e.g., 100Mbps DRB = 50MB/s × 4 bytes = 200KB/s overhead, plus processing load). SRBs carry RRC/NAS signaling which must not be tampered with — the overhead is acceptable. User data integrity is protected at higher layers (TLS/HTTPS).
Q: PDCP sequence number wraps around. What happens?
A: 12-bit SN = 4096 values, 18-bit = 262144. The receiver handles wrap-around using a window. For 12-bit: window = 2^11 = 2048. As long as out-of-order doesn't exceed half the window, reassembly works. In 5G NR with 18-bit SN, wrap-around is much rarer.

Interview Q&A
Q: UE is stuck in RRC_CONNECTED but has no data throughput. Protocol layer issue?
A: Check: 1) DRB is established (RRCConnectionReconfiguration with DRB-ToAddMod). 2) Bearer is mapped to correct S1/NG tunnel (eNB-to-SGW/UPF). 3) UE sent RRCConnectionReconfigurationComplete. 4) Check PDCP ciphering mismatch — if UE and eNB use different keys, data silently dropped.
Q: What is SRB1 vs SRB2?
A: SRB1 (Signaling Radio Bearer 1): carries RRC messages AND NAS in RRC message container. Created FIRST in RRC setup — needed for all signaling. SRB2: carries NAS messages ONLY, more protected. Created after security activation. You cannot send NAS directly on SRB1 after SRB2 is set up.

AKA (Authentication and Key Agreement):

Interview Q&A
Q: What is the difference between S1AP and NAS?
A: S1AP (S1 Application Protocol) is between eNB and MME — carries NAS as a transparent container plus S1AP procedures (bearer setup, handover, paging). NAS is end-to-end between UE and MME — eNB doesn't parse NAS, just forwards it. S1AP is per-eNB/per-UE context; NAS is per-UE/per-MME context.
Q: UE authentication keeps failing in lab. What do you check?
A: 1. SIM/USIM Ki matches what's programmed in HSS. 2. OPc vs OP — network uses one, SIM configured for other. 3. SQN (Sequence Number) out of sync — HSS SQN too far ahead of USIM counter. 4. Algorithm mismatch — UE supports MILENAGE but HSS using TUAK. 5. Check NAS logs: look for EMM Cause IE in Attach Reject.
PT06 HARQ — Hybrid ARQ: the retransmission mechanism behind your BLER measurements Advanced click to expand ▾
HARQ fundamentals — why hybrid?
ARQ (Automatic Repeat reQuest): if decode fails, send NACK, retransmit. Simple but wastes the failed attempt.
Hybrid ARQ: when decode fails, STORE the soft bits from the failed attempt. On retransmission, COMBINE soft bits → get better SNR effectively → decode from less power.

Two combining strategies:
• Chase Combining (CC): retransmit identical bits. Receiver combines. +3dB per retx.
• Incremental Redundancy (IR): retransmit different parity bits (higher code rate). Receiver combines all received versions → gets full mother code rate. More efficient than CC. LTE uses IR by default.

HARQ in TDD (B41) — variable timing
TDD HARQ timing depends on the UL/DL subframe configuration.
Not every subframe can carry feedback — only UL subframes.
Config 2 (DSUUD): DL subframes 0,1,5,6,7,8,9 → feedback in subframes 2,3

Impact on your testing: B41 HARQ process count and timing depends on tdd-config. If tdd-config in tc_cadence doesn't match BBU config → ACK/NACK timing mismatch → BLER appears worse than actual.
RV (Redundancy Version) sequence
LTE/NR uses 4 RVs: RV0 → RV2 → RV3 → RV1
RV0: systematic bits + first set of parity
RV2: different parity bits (adds new information for IR combining)
RV3: more parity
RV1: remaining parity

NDI (New Data Indicator): 1-bit toggle in DCI. Flip = new TB (reset soft buffer). Same = HARQ retransmission (accumulate soft buffer).
In your logs: look for ndi=0,rv=2 → retransmission in progress
BLER measurement — what it actually counts
BLER = Block Error Rate = (TBs failed after all HARQ rounds) / (total TBs sent)

Your sensitivity test uses FRC A1-3 (QPSK, R=1/3):
• At strong signal: BLER ≈ 0% — all TBs decoded on first attempt
• At sensitivity: BLER ≈ 5% — ~5% of TBs fail all 4 HARQ rounds
• Below sensitivity: BLER > 5% — UE cannot decode reliably

3GPP defines: A1-3 sensitivity = power where BLER ≤ 5% with 95% confidence
Interview Q&A
Q: BLER is 0% at your sensitivity test point. Is this a pass?
A: Check the power level. If BLER=0% AT the sensitivity limit power → PASS (better than spec). If 0% but you haven't decreased to the limit yet → keep decreasing power until BLER hits 5%, that's the actual sensitivity point. Your automated test does a 3-stage search specifically to find this point.
Q: What is HARQ process 0 vs process 7?
A: 8 HARQ processes run independently in parallel — like 8 separate ARQ instances. Process number identifies which soft combine buffer to use. Process 0's buffer is separate from process 7's. A TB arriving in subframe N uses the same process ID as its potential retransmission in N+8. If the IDs don't match → UE resets buffer → can't combine → BLER increases.
Reference Detail (ShareTechNote)
FDD HARQ: 8 processes. DL is asynchronous — the process ID + redundancy version are signalled in the PDCCH/DCI, so any process can be used in any order. UL is synchronous — the same process recurs every 8 subframes (ID inferred from timing). DL→UL feedback rides the PHICH (NACK → non-adaptive UL retransmission if no new DCI 0). RVs: adaptive (RV in DCI) or non-adaptive (predefined RV sequence, TS 36.321).
TDD HARQ timing is not the fixed n+4 of FDD — one UL subframe can acknowledge several DL subframes. Config 2 example: UL subframe 2 carries HARQ-ACK for DL subframes {4,5,6,8} of the previous frame plus 9. Bundling = any NACK in the set → retransmit all; multiplexing = retransmit only the NACKed ones (RRC-selected, affects PUCCH format). Special subframe = DwPTS / GP / UpPTS.

Reference Detail (ShareTechNote) — 5G NR HARQ
5G NR HARQ vs LTE: up to 16 processes (RRC-configurable, default 8) — more processes hide the longer round-trip at high SCS. Both DL and UL are asynchronous (LTE UL was synchronous), so the DCI carries the HARQ process number in each direction. Interview Q&A
Q: Your RCT passes all tests. But field team reports low throughput in that sector. What do you investigate?
A: Lab pass ≠ field pass. Intra- vs inter-frequency — why the measurement-gap detail matters
Intra-frequency: neighbour is on the same ARFCN → UE measures it continuously while receiving data (no gaps).

What SRVCC does
A VoLTE call is an IMS packet call on LTE. When the UE moves to the edge of LTE coverage, SRVCC hands the active voice call over to the CS domain (3G/2G) without dropping it. “Single radio” = the UE transmits on only one RAT at a time. Interview Q&A
Q: What triggers SRVCC and which interface carries the PS-to-CS request?
A: A B2 measurement event (serving LTE below threshold-1 while the target UTRAN/GERAN cell is above threshold-2) makes the eNB send S1AP HandoverRequired with an SRVCC indication. Q: Why is eSRVCC better than basic SRVCC?
A: eSRVCC anchors the media at the ATCF/ATGW in the visited network, so at handover only the access leg is switched and the end-to-end media path barely changes — cutting the voice interruption from hundreds of ms to tens of ms.

Interview Q&A
Q: A UE reads a SIB before it has a connection — which channels does the SIB travel on, top to bottom?
A: Logical BCCH → transport DL-SCH → physical PDSCH, and the PDSCH carrying that SIB is scheduled by a DCI on PDCCH (SI-RNTI). Only the MIB uses the BCCH→BCH→PBCH path; all other system information (SIBs) rides the shared channel PDSCH.
Q: What is the difference between a control channel and a shared channel?

Interview Q&A
Q: Why did NR drop PCFICH and PHICH?
A: PCFICH signalled the LTE control-region size (CFI) every subframe — NR instead fixes the control resources via RRC-configured CORESETs, so no per-slot indicator is needed. A: SIB1 is on the shared channel PDSCH. The MIB (in PBCH within the SSB) points to CORESET#0 / SearchSpace#0; the UE monitors that for a PDCCH scrambled with SI-RNTI, which grants the PDSCH carrying SIB1.

What a control channel does
It carries the signalling that runs the air interface — scheduling grants (who transmits where), feedback (did it decode? how good is the channel?), and broadcast timing — never the user payload itself.
PDCCH + DCI (downlink control)
PDCCH carries DCI (Downlink Control Information) = the grants. In NR it lives in a CORESET (a set of RBs/symbols) monitored via a Search Space (Type0=SIB, Type0A/1/2=paging/RA, Type3=group, plus UE-specific). Blind-decoded at aggregation levels 1/2/4/8/16 CCEs (bigger = more robust, for cell-edge UEs).

Interview Q&A
Q: Your DL data decodes fine but the eNB keeps retransmitting — which control channel is involved and what likely failed?
A: The DL HARQ-ACK the UE sends on PUCCH (or piggybacked on PUSCH). If the eNB does not receive the ACK it assumes NACK and retransmits — so the problem is UL PUCCH reliability/coverage or a mis-decoded UCI, not the PDSCH itself. Check PUCCH SINR / format and UL power control.
Q: What is a CORESET and why did NR introduce it?
A: A CORESET (Control Resource Set) is the block of resource blocks and OFDM symbols where PDCCH can be transmitted, configured by RRC. NR uses it (with search spaces) instead of LTE fixed control region + PCFICH, giving flexible, beam-friendly, bandwidth-part-specific control placement.

Q: What is the difference between DL-SCH and PDSCH?

Interview Q&A
Q: Contention-based vs contention-free RACH — when is each used?
A: Contention-based is for initial access when the network does not know the UE yet: the UE picks a random preamble, so collisions are possible and are resolved at Msg4. Interview Q&A
Q: Why page across a whole Tracking Area list instead of the last known cell?
A: An idle UE reselects cells autonomously and does not tell the network each move, so the network only knows the TA-list granularity. Q: Difference between DRX and eDRX?
A: DRX cycles are short (hundreds of ms to a few seconds) for normal phones balancing latency and battery. eDRX extends the cycle to seconds/minutes/hours for IoT devices that tolerate high latency, drastically cutting power at the cost of reachability delay.

Why beams exist
At FR2 and with massive-MIMO arrays, energy is focused into narrow beams for gain. The system must find and keep the best beam pair (gNB Tx beam ↔ UE Rx beam), and recover quickly when it breaks (UE turns, blockage). Relevant to your n41 beamforming carrier.

5G QoS flow → DRB mapping (SDAP)
A PDU session carries multiple QoS Flows (each a QFI). SDAP (the top user-plane layer, 5G-only) maps QFI ↔ DRB, and can mark packets so the UE learns the mapping automatically — reflective QoS. The UPF enforces per-flow rules received from the SMF over N4 (PFCP).

Interview Q&A
Q: LTE uses QCI per bearer — what is the 5G equivalent and what is different?
A: 5G uses 5QI per QoS Flow (QFI), not per bearer. A: A 5G feature where the UE derives the uplink QoS-flow-to-DRB mapping by observing the QFI marking on downlink packets, instead of being explicitly configured — reducing signalling for short-lived flows.

Q: Why did NR remove the always-on CRS, and what replaced its two jobs?
A: CRS was on all the time regardless of traffic, causing constant interference and power draw. NR removed it for a lean/energy-saving carrier. Its demodulation job is done by on-demand, UE-specific DMRS; its measurement job (RSRP/RSRQ/SINR) is done on the SSB (SS-RSRP) and CSI-RS.
Q: On your n41 carrier, what does the field RSRP value come from?
A: NR SS-RSRP — the per-SSB-beam RSRP measured on the SSB (PSS/SSS/PBCH). Because SSB is beam-swept, each beam has its own SS-RSRP, which is also what beam management (BM01) reports.
SEC01 Mobile Network Security — AKA, key hierarchy, ciphering & integrity, SUCI (33.401 / 33.501) Advanced click to expand ▾
What has to be protected
Four goals: mutual authentication (UE ↔ network), confidentiality (ciphering), integrity (tamper/replay detection), and — new in 5G — identity privacy. Security runs on two planes: NAS (UE ↔ core: MME/AMF) and AS (UE ↔ RAN: eNB/gNB, in PDCP).
AKA — Authentication & Key Agreement
Challenge-response on the shared secret K held in the USIM and in the HSS/AuC (LTE) or UDM/ARPF (5G). The network sends RAND + AUTN; the USIM verifies AUTN (that is how the UE authenticates the network — defeats fake base stations), computes RES; the network checks RES. Both sides then derive the same session keys. 5G variants: 5G-AKA and EAP-AKA'.

Interview Q&A
Q: In the AKA procedure, what does AUTN do and why does it matter?
A: AUTN is the authentication token the network sends with RAND; the USIM checks it against its sequence number and MAC to confirm the challenge really came from the genuine home network. That is what makes AKA mutual — the UE authenticates the network, not just the other way around, so a rogue/false base station cannot complete authentication.
Q: Where is ciphering actually applied in the LTE/5G stack?
A: On the access stratum it is done in the PDCP layer (RRC signalling on SRBs and user data on DRBs); on the non-access stratum the NAS layer ciphers and integrity-protects its own messages between the UE and the MME/AMF. So a packet can be double-protected: NAS security end-to-core, plus AS security over the radio.
Q: What problem does SUCI solve that LTE had?
A: LTE could send the permanent IMSI over the air in the clear (e.g. on first attach or identity request), letting IMSI-catchers track subscribers. 5G encrypts the permanent identity (SUPI) into a SUCI using the home network public key, so only the home network can recover it — closing the identity-privacy hole.

Interview Q&A
Q: What is RSTD and which method uses it?
A: RSTD (Reference Signal Time Difference) is the difference in arrival time at the UE between the PRS of a neighbour cell and a reference cell. OTDOA (DL-TDOA) uses a set of RSTD measurements to place the UE on intersecting hyperbolas. It depends on tight inter-cell synchronisation.
Q: Why is multi-RTT more robust than OTDOA?
A: OTDOA relies on cells being precisely time-synchronised, so any inter-cell timing offset becomes a position error. Multi-RTT measures the round-trip time between the UE and each gNB; the round trip cancels the common clock bias, so it tolerates imperfect network sync and typically gives metre-level accuracy.

RIM01 TDD Cross-Link Interference & Remote Interference Management (RIM) — the n41 field problem Advanced click to expand ▾
The TDD-only interference problem
In TDD every cell shares the same UL/DL time pattern. Two things can break that: remote interference — a distant cell's DL reaches a victim during its UL symbols (via atmospheric ducting over 100s of km) and desensitizes the UL; and cross-link interference (CLI) — gNB↔gNB / UE↔UE when neighbouring cells run opposite directions in the same slot (flexible/dynamic TDD). Neither exists in FDD.
Atmospheric ducting — the mechanism
A temperature inversion forms a duct that carries a far cell's DL far beyond its normal range. It arrives late — during the victim's UL — and shows up as a rising, sloped UL interference floor strongest near the DL→UL switch (eating into the guard period), fading toward the end of the UL region. Classic on 2.6 GHz TD-LTE/NR in China and India.
RIM — the 3GPP mechanism (38.300 / 38.174, RIM-RS in 38.211)
victim gNB detects the characteristic sloped UL interference
victim transmits a RIM Reference Signal (RIM-RS)
aggressor (far) gNB detects its own RIM-RS returning via the duct
→ aggressor now KNOWS it is causing remote interference
aggressor mitigates: back off DL symbols near the switch,
enlarge guard period, adjust power / restrict last DL symbols
The RIM-RS also lets the aggressor gauge how many symbols are affected.
Cross-link interference (CLI) & flexible TDD
With dynamic/flexible TDD, adjacent cells may transmit in opposite directions in the same slot → gNB-to-gNB and UE-to-UE interference. CLI measurements: SRS-RSRP and CLI-RSSI. Mitigation: coordinated/semi-static TDD patterns, power control, and scheduler coordination.
Why this matters for your n41 carrier
n41 (2.6 GHz TDD) is exactly the band/technology where remote interference and ducting appear in the field. Your guard-period / TAE alignment and UL sensitivity tests set the victim's resilience baseline — a radio with poor UL sensitivity or sloppy switch timing suffers remote interference far worse.
Interview Q&A
Q: Why is remote interference a TDD problem and not an FDD problem?
A: In FDD, transmit and receive are on separate frequencies with a duplexer, so a distant cell's downlink can never land in your uplink band. In TDD, all cells use the same frequency and only separate UL/DL by time; if a far cell's downlink is ducted so it arrives during your uplink symbols, it falls exactly on your receive band and time — hence remote interference is unique to TDD.
Q: What is a RIM-RS and how does it fix the problem?
A: A RIM Reference Signal is a special signal the victim gNB transmits when it detects the sloped remote-interference pattern. Because the propagation duct is reciprocal, the aggressor gNB hundreds of km away detects that RIM-RS, learns it is the source, and applies mitigation — backing off the downlink symbols near the DL→UL switch and enlarging the guard period so its energy no longer reaches the victim's uplink.

FLEX01 S1-Flex & NG-Flex — MME / AMF pooling (redundancy & load balancing) Advanced click to expand ▾
What it is — one RAN node, a pool of core nodes
S1-Flex (LTE) and NG-Flex (5G) let a single eNB/gNB connect to many core nodes (a pool of MMEs / a set of AMFs) instead of a rigid one-to-one link. Two wins: redundancy (a core node can fail and UEs stay served) and load balancing (spread UEs across the pool). (Note: this is S1-Flex — the S2a/S2b/S2c interfaces are for non-3GPP/WLAN access, unrelated.)
S1-Flex — LTE (MME pooling)
An eNB is configured with an MME pool serving a pool area. The eNB's NNSF (NAS Node Selection Function) chooses which MME to route a UE to. A connected UE is tied to its MME by the GUMMEI (Globally Unique MME Identity) carried in the S-TMSI; the eNB reads it and routes NAS to the right MME. Weight factors (per MME capacity) bias the selection so bigger MMEs take more load. If an MME fails, its UEs re-establish and NNSF picks another MME in the pool.
NG-Flex — 5G (AMF pooling)
Same idea in 5G: a gNB connects to an AMF Set (within an AMF Region). The UE's serving AMF is identified by the GUAMI (Globally Unique AMF Identity) inside the 5G-S-TMSI; the gNB routes NGAP to that AMF. The AMF Set supports AMF selection, load re-balancing, and AMF re-allocation (an AMF can hand a UE to a peer). Backed by NRF-based discovery in the SBA.

Why it matters
No single point of failure in the core-facing link, graceful load spreading, scaling (add core nodes to a pool without re-homing every cell), geographic pooling, and maintenance offload (drain one MME/AMF, its UEs move to peers). Interview Q&A
Q: What does the NNSF do in S1-Flex?
A: The NAS Node Selection Function in the eNB decides which MME in the pool a UE's NAS signalling goes to. For a returning UE it uses the GUMMEI in the S-TMSI to route back to the same MME; for a new UE it picks one using the configured weight factors (capacity-based load balancing).
Q: GUMMEI vs GUAMI?
A: GUMMEI (LTE) globally identifies an MME (PLMN + MME Group ID + MME Code); GUAMI (5G) globally identifies an AMF (PLMN + AMF Region + AMF Set + AMF Pointer). Both are embedded in the UE's temporary identity (S-TMSI / 5G-S-TMSI) so the RAN can route signalling to the correct pooled core node.
Q: How does pooling give redundancy?
A: Because the eNB/gNB is connected to several MMEs/AMFs, losing one doesn't isolate the cell — its UEs re-establish and the NNSF/AMF-selection routes them to a surviving node in the pool. You can also deliberately drain a node (for maintenance) and its UEs migrate to peers.

ROHC01 ROHC Header Compression — the VoLTE header fix ROHC click to expand +
Why it exists
A VoLTE voice packet is only ~30 bytes of AMR payload but carries a 40-byte (IPv4) or 60-byte (IPv6) RTP/UDP/IP header — more overhead than data. ROHC (in the PDCP layer) compresses that header down to 1–3 bytes, roughly doubling voice capacity.

U-mode (unidirectional, no feedback), O-mode (bidirectional optimistic), R-mode (bidirectional reliable). Compression starts with IR packets (full header) that build a context at both ends; after that only changed fields are sent (SN increments, timestamps are inferred).

SCFDMA01 SC-FDMA / DFT-s-OFDM — the low-PAPR uplink waveform PHY click to expand +
Why the uplink is different
OFDMA (used on the downlink) sums many subcarriers → a high Peak-to-Average Power Ratio (PAPR). A UE PA would have to back off to stay linear, wasting power and hurting cell-edge coverage. So LTE UL (and NR when configured) uses SC-FDMA / DFT-s-OFDM, which has a single-carrier-like envelope and ~2–3 dB lower PAPR → the UE PA runs closer to saturation, more efficiently.
The one extra step: DFT precoding
OFDMA (DL): symbols --------------------> subcarrier map -> IFFT -> +CP SC-FDMA(UL): symbols -> M-point DFT (spread) -> subcarrier map -> IFFT -> +CPThe added DFT spreads each symbol across all allocated subcarriers before the IFFT, so the time-domain signal behaves like a single carrier. Receiver (eNB) does the inverse (FDE + IDFT) — complexity is pushed to the base station, which is fine.

NR PUSCH supports both: CP-OFDM (default — higher throughput + easier MIMO) and DFT-s-OFDM (transform precoding enabled — for coverage/cell-edge, power-limited UEs). DL is always CP-OFDM. Ties to your link budget: the low-PAPR UL waveform is part of why UL sensitivity/coverage holds up.

Q: When does NR pick DFT-s-OFDM over CP-OFDM for PUSCH? For coverage/power-limited UEs (transform precoding enabled); otherwise CP-OFDM for peak throughput and MIMO.

OPT01 PCI Planning — 504/1008 range, mod-3/6/30 rules, reuse distance, collision vs confusion & spotting it in a drive test Protocol click to expand ▾
In plain English
Every LTE or NR cell broadcasts a short label, the Physical Cell Identity (PCI). The phone uses it to find the cell, lock to its reference signals and tell the network "I can hear PCI 137 at −90 dBm". There are only 504 labels in LTE and 1008 in NR, so they must be reused, like house numbers repeated in different streets. PCI planning makes sure two neighbours never share a number (a collision), no cell has two neighbours with the same number (a confusion), and neighbours do not even share the same remainder when the PCI is divided by 3, 6 or 30, because that remainder picks which reference-signal pattern the cell uses.
Three sectors per site share one SSS group; facing sectors must differ in PCI mod 3
Common scheme: site k gets PCIs 3k, 3k+1, 3k+2. Co-sited sectors are then automatically different in mod 3; facing sectors of neighbouring sites still need checking.

Level 2 — planning rules, audit and how to spot problems in a drive test
Planning rules (operator templates vary):
1. Never reuse a PCI in cells whose coverage overlaps, and never among the neighbours of any one cell.
2. Co-sited sectors and strong neighbours: different mod 3; also try for different mod 6 (single-port) and mod 30.
3. Reuse a PCI only after several tiers of cells. Rules of thumb seen in practice: urban macro ≥ 6–8 cells apart, urban micro ≥ 4–6, suburban ≥ 8–12, rural ≥ 10–15. Validate with the planning tool's predicted overlap, not just distance.
4. Allocate by site: one N_ID(1) per 3-sector site, N_ID(2) = sector. Rotate the N_ID(2) order between sites so facing sectors differ.
5. Reserve ranges: keep blocks for small cells, indoor, future sector splits and cross-border coordination. Do not burn the whole range on day one.
6. Account for antenna pattern, tilt and terrain: an overshooting cell (OPT03 topic) makes a "distant" reuse effectively adjacent.

Level 3 — case studies and expert notes
Case A — mod-3 clash (illustrative, re-worked). Two facing sectors used PCI 35 and 38. Both are mod 3 = 2 (35 = 3·11 + 2, 38 = 3·12 + 2). In the overlap the serving SINR sat near −2 dB although RSRP was fine. Re-assigning 38 → 40 (mod 3 = 1) removed the RS-on-RS collision and SINR and throughput recovered. Note: a circulating study note uses PCIs 35 and 36 for this example, which are not in the same mod-3 group (35 mod 3 = 2, 36 mod 3 = 0). Always do the arithmetic. At high load the benefit of mod-3 separation shrinks, because data REs interfere anyway.

Case B — a same-PCI cluster. An urban cluster had several cells on one PCI after a batch of new sites was integrated with a copied template. HO failure was about 18 %. After re-planning, HO failure fell to about 3.5 % and throughput rose about 22 %. Lesson: never copy PCI (or any radio parameter) blindly between sites.

Case C — three cells, one PCI. Cells A, B and C, all on the same PCI, overlapped in one area: serving SINR ≈ −3 dB, RSRQ ≈ −14 dB, RLF ≈ 6.8 %, HOSR ≈ 72 %. Fix: A and C moved to new PCIs, tilt adjusted, power cut 2–3 dB on the overlapping cell, neighbour lists refreshed. Result: SINR ≈ +5.6 dB, RLF down about 74 %, HOSR ≈ 93 %, throughput about doubled. This is a collision/confusion case (and some overshoot), not pilot pollution.

Expert notes. (1) NR has no always-on CRS, so the LTE-style mod-3 "load-independent" penalty is smaller; the PSS and PBCH DMRS (mod 4) still matter where SSBs of neighbours are time-aligned. (2) In DSS (DSS01) the NR carrier rate-matches around the LTE CRS, whose shift follows the LTE PCI: both RATs' PCI plans interact. (3) PCI mod 3 alignment is sometimes deliberately equal in some vendors' features (CRS interference cancellation, or synchronised shifting strategies). Follow the operator template when it says so. (4) After a sector split (3 → 6 sectors) the new sectors need PCIs that satisfy all neighbours; that is why reserved ranges exist.
Interview Q&A
Q: How many PCIs are there in LTE and NR, and how are they built?
A: LTE: 504 = 168 SSS groups × 3 PSS sequences. NR: 1008 = 336 × 3. In both, PCI = 3·N_ID(1) + N_ID(2).
Q: Why must neighbouring cells have different PCI mod 3?
A: Mod 3 selects the PSS sequence and, in LTE with 2 or 4 CRS ports, the CRS frequency shift. Equal values put the reference signals on the same REs, so RSRQ, SINR and channel estimation degrade even at low load.
Q: What does PCI mod 30 affect?
A: The UL DMRS / PUCCH base-sequence group. Neighbours with equal mod 30 have correlated UL reference signals, which hurts UL channel estimation.
Q: Explain PCI collision versus confusion, and how the network detects them.
A: Collision: two overlapping cells share a PCI. Confusion: one cell has two neighbours with the same PCI, so the HO target is ambiguous. ANR detects both when a UE reports a CGI different from the one stored for that PCI; SON or the operator then re-assigns.
Q: A drive test shows RSRP −80 dBm but SINR −2 dB. How would you check if PCI is involved?
A: Look at the scanner's top-N list. The same PCI from two CGIs means collision. A strong neighbour with the same mod 3 means an RS collision. If neither applies, suspect overshoot, pilot pollution or external interference.
PC01 Uplink Power Control (LTE/NR) — open loop P0 + α·PL, closed-loop TPC, PHR & ICIC/eICIC Protocol click to expand ▾
In plain English
A phone right next to the mast and a phone at the cell edge both have to be heard by the base station at about the same level. If both shouted at full power, the near one would drown everybody and the far one would still struggle. Uplink power control is the volume knob: the phone first estimates how much signal is lost on the way (path loss) and sets its power from a formula the network broadcast (open loop). The base station then listens and sends small "louder / quieter" corrections (TPC commands, closed loop). The phone reports how much power it still has spare (power headroom) so the scheduler does not ask for more than it can give.

Level 2 — fractional PC, PHR and what to look for in logs
Why α < 1? With full compensation (α = 1) every UE arrives at the same power per RB, so the edge UE transmits near P_CMAX and splashes interference into neighbour cells. With α = 0.8, a UE with 10 dB more path loss raises its power by only 8 dB. The edge UE gets a slightly lower SINR, the neighbour cells see less interference (lower IoT), and the cell-average UL throughput is usually higher. The operator pairs α with P0: a lower α needs a higher P0_nominal.

Worked example (LTE, α = 0.8, P0 = −90 dBm/RB, 10 RB, Δ_TF = 0, f = 0):
PL = 120 dB → P = −90 + 10 + 96 = 16 dBm.
PL = 130 dB → P = −90 + 10 + 104 = 24 dBm → capped at 23 dBm. The UE is power-limited: the scheduler must reduce RBs (halving to 5 RB saves 3 dB) or lower the MCS.

Power headroom report (PHR). A MAC CE with PH = P_CMAX − (power the UE would need for the current grant). Positive = spare power, negative = power-limited. LTE reports PH in 1 dB steps from −23 to +40 dB. Triggers: periodicPHR-Timer, a path-loss change larger than dl-PathlossChange (1/3/6 dB) after prohibitPHR-Timer, and activation of a serving cell. The scheduler uses PHR to size UL grants (NB12 covers PHR/BSR at protocol level).

PRACH power: preambleReceivedTargetPower + PL, ramped by powerRampingStep on each retry, capped at P_CMAX (see PRA01/CF01).

What to check in UE / eNB logs: UE TX power vs PHR over the route; TPC command histogram (a stream of +1/+3 means the UE never reaches target); UL SINR per UE vs its target; cell IoT/RSSI per PRB (a rising UL noise floor across the band means too much UL power in the neighbourhood, or external interference).

Level 3 — ICIC / eICIC and lab links
Inter-cell interference coordination. UL power control is one half of interference management; the other is coordination between cells.
• ICIC (LTE Rel-8): fractional frequency reuse (reuse-1 in the cell centre, a reuse-3-style edge band) and soft frequency reuse (edge sub-band at higher power). Over X2 the eNBs exchange RNTP (DL: which PRBs I will transmit at high power), HII (UL: which PRBs my edge UEs will use) and OI (UL: I am seeing high interference on these PRBs). The receiving scheduler can then avoid those PRBs or lower power on them.
• eICIC (Rel-10, HetNet): the macro sends ABS (almost-blank subframes carrying only CRS, sync, PBCH and essential signalling; a 40-bit pattern for FDD). The pico extends its footprint with a cell range expansion (CRE) bias (values such as 3–9 dB are common, up to about 15 dB in some systems) and schedules its edge UEs in the macro's ABS.
• FeICIC (Rel-11) adds UE-side CRS interference cancellation; CoMP (joint transmission, coordinated scheduling/beamforming) is the follow-on.
• In NR, the same ideas appear as scheduler coordination, CLI management for TDD and beam-domain coordination.

Lab links for an RCT engineer. (1) In a conducted lab, a UE a few metres from the RU with little attenuation sits at low PL, so it transmits very low power and PHR is large. Adding attenuation raises the UE power along the formula; a flat UE power with rising attenuation means the UE hit P_CMAX. (2) A UL sensitivity or UL throughput shortfall with PHR negative is a coverage/UE limit, not necessarily a radio receiver defect. With PHR positive and low UL SINR, look at the receiver (noise figure, gain settings, PIM, external interference). (3) Too high a P0_nominal on one cell shows up as a rising UL noise floor on its neighbours in RSSI-per-PRB traces.
Interview Q&A
Q: Write the PUSCH power-control formula and explain each term.
A: P = min{P_CMAX, P0 + 10·log10(2^μ·M_RB) + α·PL + Δ_TF + f(i)}. P0 is the target per RB, the bandwidth term keeps power per RB constant, α·PL is the fractional path-loss compensation, Δ_TF is the MCS offset and f(i) is the accumulated closed-loop TPC. The result is capped at P_CMAX.
Q: Why is α less than 1 in many networks?
A: Fractional compensation lets edge UEs transmit a little less than full compensation would require. That limits UL interference (IoT) in neighbour cells and usually raises average cell throughput, at a small edge-SINR cost. PUCCH always uses α = 1.
Q: What are the TPC step values?
A: Accumulated mode is {−1, 0, +1, +3} dB. Absolute mode is {−4, −1, +1, +4} dB. LTE DCI 3A uses 1-bit ±1 dB.
Q: What is PHR and how is it used?
A: Power headroom = P_CMAX minus the power the UE would need for the current allocation, reported in a MAC CE periodically or when path loss changes. Negative PHR means the UE is power-limited, so the scheduler reduces RBs or MCS instead of asking for power the UE does not have.
Q: UL BLER is high only at the cell edge while DL is fine. What do you check?
A: PHR and UE TX power (is it at P_CMAX?), P0/α settings, TPC behaviour, UL interference (IoT per PRB), UL sensitivity of the receiver, and whether the DL power makes the cell bigger than its UL can support.

Q: CSSR is low on one cell. How do you break it down?
A: Split it by stage (RRC vs E-RAB/PDU), by hour and by cause code. Then check coverage/UL limits, interference, admission/congestion counters, RACH performance, core rejects and hardware alarms. Confirm with a drive-test L3 trace at the failure locations.
Q: What is the difference between a setup failure and a drop?
A: A setup failure means the connection never completed (accessibility). A drop is an abnormal release of a connection that was established successfully (retainability). The formula (attempts − successes)/attempts is setup failure rate, not drop rate.
Q: How do you plan a drive-test route for a new cluster?
A: Use the site database and maps. Cross every sector footprint and every handover border, cover main roads plus some side streets, keep the route continuous, drive both directions for HO checks, and keep a steady 20–40 km/h in town with logging only after GNSS lock.
Q: After changing a tilt, how do you validate it?
A: Re-drive the same route with the same setup and compare it with the baseline. Then watch the cell's and its neighbours' KPIs for several days to confirm the improvement and that no neighbour degraded. Keep a rollback plan.
Q: Throughput is low at a point where RSRP is −78 dBm. What next?
A: Check SINR and CQI first: poor SINR means interference. If SINR is good, check PRB utilisation and user count (load), then MIMO rank and CA status, then backhaul and core. RSRP alone does not predict throughput.

NT1 IMS Registration & SIP Call Flow — IMS PDN, P-CSCF discovery, REGISTER/401/200, INVITE→183→PRACK→UPDATE→180→200→ACK, BYE Protocol click to expand ▾
In plain English
Before a phone can make a VoLTE call it has to check in at the IMS reception desk. It first opens a separate data pipe just for IMS (the IMS PDN), learns the address of the receptionist (the P-CSCF), then says "I am here" with REGISTER. The network does not believe it yet, so it answers 401 with a puzzle only the real SIM can solve. The phone solves it, registers again, and gets 200 OK. A call is then a polite negotiation: "I would like to talk, here are the codecs I speak" (INVITE + SDP offer), "fine, use this one" (183 + SDP answer), and the far phone only starts ringing once both sides have reserved a guaranteed voice lane (the QCI 1 bearer). PT10 gives the IMS architecture and a short flow; this card is the message-by-message version with the headers, the bearer interplay and the failure signatures.

Registration step by step. (1) REGISTER to the P-CSCF with the IMPI in the Authorization header (empty response), the IMPU in To/From, a Contact with the UE IP, and Security-Client listing IPsec algorithms and ports. (2) The P-CSCF forwards to the I-CSCF, which queries the HSS (Diameter Cx UAR/UAA) to choose the S-CSCF. (3) The S-CSCF fetches an authentication vector (MAR/MAA) and answers 401 Unauthorized with WWW-Authenticate: the nonce is RAND and AUTN encoded together; CK and IK ride along to the P-CSCF, which removes them and uses them to set up IPsec with the UE. (4) The ISIM checks AUTN (proves the network is genuine, and that the sequence number is fresh), computes RES; the UE sends the second REGISTER over the new IPsec security associations with the digest response derived from RES (digest-AKA). (5) 200 OK returns Service-Route (the S-CSCF path for later requests), P-Associated-URI (all implicitly registered IMPUs, e.g. the tel URI) and the granted Expires. (6) The UE sends SUBSCRIBE to its own registration state (Event: reg), gets 200 OK and a NOTIFY with reginfo XML, answered by 200 OK. Level 2 — the call, header by header
INVITE. Request-URI = the B-party (tel or SIP URI); P-Preferred-Identity = the A-party IMPU; Supported/Require: 100rel and precondition; an SDP offer with the audio line (RTP port, payload types for AMR-WB, AMR and often EVS, plus telephone-event for DTMF), a b=AS bandwidth line, and precondition attributes: a=curr:qos local none and a=des:qos mandatory local sendrecv. In words: "I have no voice bearer yet, and I insist on one before the call proceeds." The P-CSCF answers 100 Trying immediately.
183 Session Progress with the SDP answer. The B-side picks the codec and returns its own IP/port and precondition state. The 183 carries Require: 100rel and an RSeq number, so it is a reliable provisional response: the A-side must acknowledge it with PRACK (RAck header) and gets 200 OK (PRACK). Without 100rel a lost 183 would never be resent and the SDP answer would be lost.
The voice bearer is triggered here, not at 200 OK. When the P-CSCF sees the SDP offer/answer pair it sends a Diameter Rx AAR to the PCRF with the media components (IP 5-tuple, bandwidth). The PCRF pushes a PCC rule to the PGW over Gx; the PGW sends Create Bearer Request; the MME sends E-RAB Setup Request with QCI 1, GBR/MBR in the tens of kbit/s and a TFT that matches the RTP flow. The eNB admits the GBR bearer and adds a DRB (normally RLC UM, often with ROHC) in RRC Reconfiguration. This is the moment the RAN is asked for voice capacity.
UPDATE. Once the A-side sees its own QCI 1 bearer up it sends UPDATE with a=curr:qos local sendrecv ("my side is reserved") and gets 200 OK (UPDATE). When the B-side also has its bearer, both preconditions are met and B starts alerting: 180 Ringing. When the user answers: 200 OK (INVITE), then ACK from A. RTP (20 ms speech frames) and RTCP now flow on QCI 1; SIP signalling stays on the QCI 5 default bearer of the IMS PDN.
Release. BYE → 200 OK. The P-CSCF sends an Rx session-termination to the PCRF, which removes the QCI 1 bearer (Delete Bearer → E-RAB Release). A missing bearer release after BYE is a classic resource-leak defect.
Mobile-terminated side. If UE-B is idle, the INVITE arriving on its QCI 5 bearer causes DL data notification → paging → service request → the INVITE is delivered; B answers with the 183. The same PRACK/UPDATE dance follows from the other direction.
Where to see it. On the eNB/S1-U side SIP is inside GTP-U and usually inside ESP (IPsec between UE and P-CSCF), so you often see only encrypted packets; what the RAN does see is the E-RAB Setup for QCI 5 and QCI 1 and the RRC reconfigurations. For the SIP itself use the UE diagnostic log or an IMS-side trace (Wireshark filters sip, sip.Method == "INVITE", sip.Status-Code == 401).

Transport detail that bites: SIP messages with large SDP and many headers can exceed the path MTU. The SIP rules say a request within 200 bytes of the path MTU (or over 1300 bytes when the MTU is unknown) must use TCP, so VoLTE UEs often send INVITE over TCP and small messages over UDP. A filter that only looks at UDP port 5060 misses half the call, and a secure port (e.g. inside IPsec) hides it completely.
Registration timing: the UE asks for a long Expires, the S-CSCF may grant a shorter one, and the UE re-registers before it runs out (typically at about half the time, or 600 s before expiry for long values). A handover does not require re-registration because the UE IP address on the IMS PDN does not change.
RAN view of a "call setup failure": the SIP failure is often only the symptom. Line up the UE log with the eNB trace: a QCI 1 E-RAB rejected for radio-resources-not-available, an RLF between 183 and 200 OK, or a missing RRC Reconfiguration Complete explains most failures before the SIP timers expire. VoLTE drop causes (RTP inactivity, bearer loss, SRVCC) are in NB13; the PDCP/ROHC side in ROHC01; QCI values in QS01; the 5G variant (VoNR / EPS fallback) in PT22.
Interview Q&A
Q: Why does the first REGISTER always get a 401 — is that a failure?
A: No. It is the normal digest-AKA challenge. The S-CSCF sends RAND and AUTN in the nonce; the ISIM verifies the network and computes RES; the second REGISTER carries the response and gets 200 OK. A failure is a second 401 or a 403 after the response.
Q: At which SIP message is the QCI 1 bearer created and why there?
A: Around the 183 Session Progress, when the P-CSCF has seen both the SDP offer and answer and knows the media 5-tuple and bandwidth. It sends Rx to the PCRF, which triggers the dedicated bearer. Preconditions make the far end wait with ringing until both sides have their bearer.
Q: What are PRACK and UPDATE for in VoLTE?
A: PRACK acknowledges a reliable provisional response (the 183 with RSeq), so the SDP answer cannot be silently lost. UPDATE tells the far end mid-setup that the local QoS precondition is now met, so B can start ringing (180) knowing voice will work.
Q: Which bearer carries SIP and which carries RTP?
A: SIP runs on the default bearer of the IMS PDN (QCI 5, non-GBR, high priority). RTP/RTCP voice runs on a dedicated QCI 1 GBR bearer created per call and removed after BYE.
Q: A VoLTE call fails with 580 Precondition Failure. Where do you look on the RAN side?
A: At the QCI 1 E-RAB Setup: did the eNB admit it, or put it in the failed list (admission control, GBR licence, ARP)? Was the RRC Reconfiguration completed? If the RAN accepted it, look at the PCRF/Rx/Gx side.

Level 3 — pitfalls and real behaviour
  • Combined attach accepted as EPS-only. Everything looks fine for data, but CSFB calls fail. Check the EPS attach result and EMM cause in Attach Accept, and whether the SGs association to the MSC is up.
  • Missing Detach Accept is not a defect when the switch-off bit is set. Automation that asserts "Detach Accept received" must read the bit first.
  • Implicit detach. If a UE misses its periodic TAU, the MME starts the mobile reachable timer (by default T3412 + 4 min), then an implicit detach timer, and deletes the context without telling anyone. The UE's next TAU or Service Request is rejected with #9 (UE identity cannot be derived) or #10 (implicitly detached) and it must attach again. After a core restart this causes a storm of rejects and full attaches, a pattern typical of S1 reset storms.
  • Mobility vs periodic registration in 5G: both reuse the Registration Request, so KPIs that count "registration attempts" mix keep-alives with real mobility. Split by registration type.
  • Emergency attach in the lab needs the emergency APN and bearer configured in the core; a UE without a SIM will only ever try type 6.
  • Follow-on request matters for latency: a UE with FOR set keeps the NAS connection after registration and can start a PDU session at once instead of going idle and paging back in.
Interview Q&A
Q: What is the difference between EPS attach and combined EPS/IMSI attach?
A: EPS attach registers only for packet services. Combined also registers the UE in the CS domain through the SGs interface to the MSC/VLR, which is needed for CSFB voice and SMS over SGs. The Attach Accept then includes an LAI and TMSI, and the attach result says "combined".
Q: A UE sends a switch-off detach and no Detach Accept comes back. Bug?
A: No. With the switch-off bit set, the network does not answer because the UE is powering down. The MME just releases the S1 context (UE Context Release Command with NAS cause detach).
Q: List the 5GS registration types.
A: Initial (1), mobility registration updating (2), periodic registration updating (3), emergency (4), and in Rel-17 SNPN onboarding (5) and two disaster-roaming types (6, 7). The follow-on request and SMS-over-NAS indications are separate flags, not types.
Q: A UE's TAU is rejected with cause #10 after the core was restarted. What happened?
A: The MME lost or implicitly detached the UE context, so it cannot accept the TAU. The UE must perform a new attach. Expect a burst of these after a core restart, together with full attaches with authentication.
Q: Which NAS timer would you suspect when an attach attempt repeats every 10 s and then stops for 12 minutes?
A: T3411 (10 s retry between attempts) and, after five failed attempts, T3402 (12 min back-off). Check the reject cause or the missing Attach Accept that caused the retries.

In plain English
In an X2 handover the two base stations talk to each other directly. In an S1 handover they cannot (no X2 link, X2 not allowed, or the target belongs to another MME), so the MME acts as the go-between: the source eNB asks the MME to move the UE, the MME books a room at the target, hands the booking back to the source, and the source tells the phone where to go. Level 2 — keys, forwarding and how to test it
Security is different from X2. In an S1 handover the MME increments the NCC and computes a fresh NH, sent in the Handover Request. The target derives KeNB* from that NH (a "vertical" key derivation), and the NCC reaches the UE inside the HO command so it can derive the same key. In an X2 handover the source normally derives KeNB* itself from the current KeNB ("horizontal") unless it already holds an unused NH. Result: after an S1 handover the source eNB cannot compute the target key (forward security). An NCC mismatch shows up as the UE failing the reconfiguration and re-establishing.
Direct vs indirect forwarding. The source sets Direct Forwarding Path Availability when it has IP connectivity to the target (typically when X2 transport exists but X2 HO is not used). The MME decides: with direct forwarding the forwarding TEIDs in Handover Command belong to the target eNB; with indirect forwarding the MME first sends GTPv2 Create Indirect Data Forwarding Tunnel Request to the S-GW (message 166, response 167) with the target's forwarding TEIDs, gets S-GW TEIDs back and puts those in the Handover Command. DL packets the source still has (and the ones still arriving) go source → S-GW → target. After completion the S-GW sends End Marker packets on the old path so the target knows forwarding is finished, and the MME removes the temporary tunnels with Delete Indirect Data Forwarding Tunnel (168/169). If S-GW relocation happens too, two S-GWs take part.
Filters: s1ap.procedureCode in {0 1 2 4 23 24 25} for the HO messages, gtpv2.message_type in {34 35 166 167 168 169} for Modify Bearer and indirect tunnels, gtp.message == 254 for End Marker on S1-U.

Interview Q&A
Q: When does an eNB choose S1 instead of X2 handover?
A: When there is no X2 to the target, X2 handover is barred for that neighbour, the X2 preparation failed, or the target is served by a different MME (or needs an S-GW change the eNBs cannot handle). The S1 path is always available because every eNB has S1 to its MME.
Q: What is inside the Handover Request that the target eNB really needs?
A: The E-RABs to set up with QoS and the S-GW UL TEIDs, UE-AMBR, the UE security capabilities and the {NCC, NH} security context, the handover restriction list, and the source-to-target container with the UE capability and current radio config.
Q: What is indirect data forwarding and when is it used?
A: DL data is forwarded source eNB → S-GW → target eNB through temporary GTP tunnels created with Create Indirect Data Forwarding Tunnel, used when the source and target have no direct IP path. They are deleted after the handover completes.
Q: Why is eNB/MME Status Transfer needed?
A: It passes the PDCP COUNT (HFN + SN) of each RLC AM bearer to the target, so the target continues the same numbering for ciphering and delivers in order without loss or duplicates.
Q: How does security differ between X2 and S1 handover?
A: In S1 the MME provides a fresh NH with an incremented NCC, so the target key is derived from material the source never had. In X2 the source usually derives KeNB* from its own key, so the source can in principle compute the target key.

In plain English
A drive test means putting engineers, a car and test phones on the road to measure the network. MDT (Minimisation of Drive Tests) asks the phones that are already out there, the customers' own, to do part of that job. The network tells selected phones to report signal strength, quality and sometimes location, either live while they are connected (immediate MDT) or by keeping a diary while idle and handing it over later (logged MDT). The base station adds its own measurements (throughput, delay, loss) and sends everything to a trace collector. The result is a continuous, map-able picture from places a car never goes, such as indoors.
MDT activation and reporting paths
Management-based MDT selects any consenting UE in an area; signalling-based MDT follows one subscriber through the core. The eNB sends CellTrafficTrace to the MME so the collector can match the trace to the subscriber.

Level 2 — activation, signalling and how to verify it
Management-based (area-based): the OAM/EMS creates a trace job with the MDT configuration (which measurements, report interval/amount, area list of cells or TAs, collector address) and sends it to the eNB. The eNB picks UEs in the area, but only those for which the MME sent Management Based MDT Allowed in Initial Context Setup (it reflects the subscriber's consent in the HSS).
Signalling-based: the OAM activates a trace for one IMSI/IMEI at the HSS; the HSS passes trace data to the MME, which puts a Trace Activation IE with the MDT configuration in Initial Context Setup (or sends Trace Start). The trace follows the UE through handovers. User consent is required for both types when the data can be tied to a person.
Reporting: the eNB either streams records to the trace collection entity (TCE) or writes files (XML) that the EMS collects. The eNB also sends S1AP CellTrafficTrace to the MME with the trace reference, the E-UTRAN cell ID and the TCE address; the MME tells the TCE which IMSI/IMEI belongs to that trace reference. That is why CellTrafficTrace appears right after Initial Context Setup in the audited X2 capture: a trace/MDT session was active for that UE.
Split gNB and EN-DC (from the notes): the SgNB Addition Request carries the MDT activation to the en-gNB; the E1 Bearer Context Setup Request gives the CU-UP the PDCP-level measurements (M4, M6, M7); the F1 UE Context Setup Request gives the DU the radio-level ones (M2, M5, M6, M7); M1 reaches the UE as reportConfig/measId in the RRC Reconfiguration built from the SgNB Addition Request Acknowledge.

Interview Q&A
Q: What is the difference between immediate and logged MDT?
A: Immediate MDT collects measurements from connected UEs in real time through normal measurement reports plus base-station measurements. Logged MDT configures a UE to record measurements while idle (or inactive in NR) and hand the log over later, when it reconnects and the network requests it.
Q: Name the MDT measurements M1 to M7.
A: M1 RSRP/RSRQ, M2 power headroom, M3 received interference power, M4 data volume, M5 scheduled IP throughput, M6 packet delay, M7 packet loss rate.
Q: You see S1AP CellTrafficTrace in a capture. What does it mean?
A: A trace (often an MDT job) is active for that UE. The eNB reports the trace reference, cell ID and collector address to the MME so the collector can link the trace records to the subscriber identity.
Q: Management-based vs signalling-based MDT?
A: Management-based is configured by OAM for an area and the eNB chooses consenting UEs there. Signalling-based targets one subscriber via the HSS and MME and follows the UE across cells.
Q: Can MDT replace drive testing completely?
A: No. It gives continuous coverage and quality data from real users, including indoors, but it cannot test a network before users exist, cannot run scripted calls or benchmark competitors, and location accuracy depends on the UE.

Test-IDs · Group-IDs · Cadence-IDs · Thresholds · rx_limits — what every field means

Frequency point meanings (fm / fb / ft)
fm — mid-band
Channel center frequency
The nominal center of the operating band. For B3: 1800 MHz DL. This is the most representative operating frequency. All CI and smoke tests use fm only — fewest variables, fastest result.
fb — band-bottom
Lower band edge frequency
First channel in the operating band. Most affected by the high-pass response of the band-select filter. RSSI accuracy and blocking tests at fb reveal filter roll-off effects on receiver performance.
ft — band-top
Upper band edge frequency
Last channel in the operating band. Affected by the low-pass response of the band-select filter. Together fb/fm/ft give full coverage of performance variation across the band.
ETM — E-UTRA Test Model meanings
ETM 1.1
Full allocation 64QAM
All resource blocks allocated, 64QAM modulation, full power. Used for ACLR, EVM, output power — represents peak stress on the PA and spectral performance.
ETM 2a
Partial allocation
Sub-set of RBs allocated. Used for dynamic range tests where partial loading is required. Also used for time offset testing to see offset behavior under partial load.
ETM 3.1a
Multi-antenna reference signal
Includes cell-specific reference signals across multiple antenna ports. Used for EVM and ACLR OTA tests — the reference signal structure is needed for beam coherence measurements.

Timing accuracy of the transmitted frame vs. expected timing reference. Runs at ETM 1.1, 2a, and 3.1a — broadest ETM coverage of any single test. fm only.

Checks TX spectrum against 3GPP emission mask out to ±30 MHz and beyond the carrier. ETM 1.1 and 1.2. Broader than ACLR — covers all out-of-band emissions.

test_lte_Tx_Spurious
Transmitter spurious emissions
Measures harmonic and intermodulation products appearing outside the operating band. TS 36.141 clause checked by spectrum sweep across 30 MHz–12.75 GHz range.
test_Tx_dynamic_range
Output power dynamic range
Tests the RU can accurately produce power from maximum down to minimum (−6 dB, −10 dB, etc.). ETM 2a, 3.1a, 2.0, 3.1. Nightly and Sanity only. Verifies PA linearity across its range.
test_Tx_DLRS
Downlink reference signal quality
Checks the Cell Reference Signal (CRS) EVM and power accuracy. ETM 1.1 only. CRS must be accurate for UE channel estimation — degraded CRS = UE cannot decode DL data.
test_Tx_TimeAlignment
Time alignment error (TAE)
For multi-antenna MIMO: maximum timing difference between antenna branches. 3GPP limit: ≤ 65 ns (intra-band) for release 8+. Critical for MIMO spatial multiplexing quality.
test_Tx_modulation_analysis
Modulation analysis bundle
Compound test = [Output Power + EVM + Freq Error + DLRS + time offset] in one run. Used in Nightly and Sanity. Efficient: 5 measurements from one captured waveform.
Rx test deep-dive — uplink (base station receive)
test_Rx_Reference_Sensitivity_Level
Reference sensitivity (REFSENS)
The minimum signal level the RU can correctly receive. 3GPP defines this as the power level at which PUSCH throughput ≥ 95% of max for a fixed reference channel (FRC).
Wide Area BS: −69 dBm (1.4/3/5/10/15/20 MHz) — from your rx_limits_validation_conditions
Test signal: PUSCH QPSK, 1 layer, specific FRC
Channel: AWGN (baseline), EPA5, EVA70 for fading
Most critical UL test. If REFSENS fails, coverage shrinks — cell edge users cannot connect.
test_Rx_RSSI
Received signal strength indicator
Verifies the RU accurately reports RSSI — the total received power across the channel bandwidth including signal, interference, and noise.
Measured at fm (mid-band frequency)
Compared against expected value with ±2 dB typical tolerance
test_Rx_RSSI_Accuracy
RSSI accuracy at band edge
Tests RSSI accuracy specifically at fb (band-edge frequency) — where filter roll-off causes the most measurement error. P5 cadence only. ETM 1.1.
Band-edge is hardest: filter response is not flat, RU must still accurately report RSSI within spec. Most RUs show highest RSSI error here.
test_lte_Rx_ACS
Adjacent channel selectivity (ACS)
RU's ability to receive a wanted signal in the presence of a strong adjacent channel interferer. Tests all 3 frequency points (fb/fm/ft). Signal is on wanted channel, interferer is ±1 channel offset.
Wanted signal at REFSENS + 3 dB
Interferer: +16 dB above wanted signal (adjacent channel)
Pass: throughput ≥ 95% of max
test_lte_Rx_ICS
In-channel selectivity (ICS)
Ability to receive a weak wanted resource block allocation in the presence of a strong interferer within the same channel bandwidth. Tests all 3 freq points.
test_lte_Rx_NB_blocking
Narrowband blocking
RU must correctly receive wanted signal when a strong CW (narrowband) interferer is present just outside the operating band. Tests fb/fm/ft. Models real-world out-of-band interference.
test_lte_Rx_blocking
In-band blocking
Blocking by a strong signal anywhere within the operating band but on a different channel. fm only. Tests AGC and front-end linearity when a nearby strong signal is present.
test_lte_Rx_intermodulation
Receiver intermodulation
Two interfering signals create an intermodulation product that falls on the wanted signal's frequency. Tests the RU receiver's third-order intercept point (IIP3) — a measure of linearity.
Two interferers: f1 and f2, spaced so 2f1−f2 or 2f2−f1 falls on wanted channel
Tests fb/fm/ft

NR OTA Tests — TS 38.141-2 (Radiated Conformance)

Massive MIMO / AAS base stations · EIRP · TRP · EIS · CATR anechoic chamber · FR1 (sub-6 GHz)

OTA testing fundamentals — before any test
WHY OTA?
Why radiated testing exists
Modern 5G NR massive MIMO (AAS — Active Antenna Systems) has the antenna array integrated inside the RU with no external RF connectors. You cannot plug in a cable to the antenna port. The only way to measure the RU's radiated performance is over the air.
Your RU (Metro AAU) is exactly this type — the 3GPP calls it BS Type 1-O (FR1 OTA only) or BS Type 1-H (hybrid — some conducted TAB connectors + OTA at RIB).
EIRP
Effective isotropic radiated power
The power that a hypothetical isotropic (radiating equally in all directions) antenna would need to emit to match the power the DUT radiates in its peak beam direction. EIRP = TX Power + Antenna Gain.
Measured in the far field in the beam peak direction
Units: dBm (absolute) or dBi relative to isotropic
Used for TX conformance: output power, ACLR, EVM
TRP
Total radiated power
Integral of radiated power over the entire sphere (all angles). TRP is lower than peak EIRP — it captures the efficiency of the whole antenna pattern. Requires 3D sphere scan.
TRP = sum of EIRP in all measured directions, weighted by solid angle
Radiated transmit power test (TS 38.141-2 §6.2)
EIS
Effective isotropic sensitivity
Minimum signal power density (W/m²) from a far-field source that the receiver can successfully decode. EIS is the OTA analogue of conducted REFSENS. Lower EIS = more sensitive receiver.
Used for RX conformance: sensitivity, ACS, blocking
Measured in beam peak direction
CATR
Compact antenna test range
The anechoic chamber method used for OTA testing. A parabolic reflector converts the near-field spherical wave from a feed antenna into a plane wave (far-field equivalent) in a much shorter distance. The quiet zone (QZ) is where the DUT sits.
Far-field distance = 2D²/λ. At 2 GHz a 30 cm array needs 60m — CATR reduces this to 2-3m
3GPP-approved method per TR 38.810
BS TYPES
3GPP base station type taxonomy
3GPP defines which test standard applies based on BS type. Your Metro AAU is most likely Type 1-H or 1-O.
Type 1-C: conducted only (traditional macro BTS with external antenna) → TS 38.141-1
Type 1-H: hybrid — has TAB connectors AND OTA RIB → both TS 38.141-1 and 38.141-2
Type 1-O: FR1, OTA only, no connectors → TS 38.141-2 only
Type 2-O: FR2 (mmWave), OTA only → TS 38.141-2 only
OTA transmitter tests — TS 38.141-2 Chapter 6
§6.2 — Radiated TX Power
OTA base station output power (TRP)
Measures total radiated power across the full sphere. Compares measured TRP against the manufacturer's declared TRP value within the specified accuracy window. Requires full 3D sphere measurement.
Declared EIRP per beam identity and beam direction pair
Rated beam EIRP = max power at beam peak direction
Accuracy window specified per operating band in TS 38.104
§6.3 — OTA Output Power
OTA base station output power (EIRP)
Measured at the beam peak direction using EIRP. Verifies the RU hits its declared EIRP within the specified tolerance. Single direction measurement — faster than TRP but less complete.
Test at declared beam peak direction
EIRP tolerance: typically ±3 dB for normal conditions
§6.4 — Output Power Dynamics
OTA output power dynamics
Tests accurate power control across the full dynamic range. RU must hit target power at all levels from maximum down to minimum (−6/−10/−30 dB below max). Tests PA linearity and power control accuracy.
On/off power ratio: ratio of TX-ON to TX-OFF power level
Transient period: time for power to ramp up/down within spec
§6.5.1 — OTA Frequency Error
OTA carrier frequency accuracy
Same concept as conducted freq error but measured OTA. The radiated carrier must be within ±0.05 ppm of the declared frequency. Measured by demodulating the received OFDM signal and comparing subcarrier positions to nominal.
Wide Area BS: ±0.05 ppm (same as conducted)
At 3.5 GHz: ±0.05 ppm = ±175 Hz
§6.5.2 — OTA EVM
OTA error vector magnitude
Modulation quality measured OTA in the beam peak direction. Uses a probe antenna in the CATR quiet zone connected to the signal analyzer. Same EVM limits as conducted, but now includes antenna array effects.
QPSK: ≤ 17.5% · 16QAM: ≤ 12.5% · 64QAM: ≤ 8%
256QAM: ≤ 3.5% (where supported)
Uses NR test models (NR-TM 1.1, 2, 3.1 etc.)
§6.5.3 — OTA TAE
OTA time alignment error
Maximum timing difference between antenna branches, measured OTA. For AAS systems the timing of all antenna elements must be coordinated for correct beamforming. TAE error degrades MIMO and beamforming gain.
Intra-band: ≤ 65 ns (Rel-15/16)
Measured between beam pairs at known angular positions
§6.6.2 — OTA OBW
OTA occupied bandwidth
Bandwidth containing 99% of total radiated power. Must remain within the allocated channel bandwidth. For a 100 MHz NR channel: OBW ≤ 99 MHz (leaving 0.5 MHz guard each side).
§6.6.3 — OTA ACLR
OTA adjacent channel leakage ratio
Measured OTA in beam peak direction. Power leaking into adjacent NR/LTE channels. Adds beamforming pattern effects on top of conducted PA nonlinearity.
NR ACLR: ≥ 45 dBc (sub-6 GHz)
UTRA ACLR: ≥ 45 dBc
§6.6.4 — OTA OBUE
OTA operating band unwanted emissions
Spectrum emission mask measured OTA — checks unwanted emissions across the operating band from the carrier edge out to the channel edge. Tests the overall spectral cleanliness of the radiated signal.
§6.6.5 — OTA Spurious
OTA transmitter spurious emissions
Harmonic and intermodulation products measured OTA across the full spurious domain (9 kHz–12.75 GHz). These can interfere with completely different services (GPS, aviation, emergency services). Strict absolute power limits.
§6.7 — OTA Tx Intermod
OTA transmitter intermodulation
A second signal is injected into the RU transmitter path. The resulting intermodulation products (2f1−f2, etc.) are measured OTA. Tests PA linearity when the antenna port faces a strong reflected signal (antenna mismatch or nearby transmitter).
Requires a second signal generator injecting into the antenna port — different test setup from all other TX tests.
OTA receiver tests — TS 38.141-2 Chapter 7
§7.2 — OTA Sensitivity
OTA reference sensitivity (EIS)
OTA equivalent of conducted REFSENS. The signal generator illuminates the RU via a probe antenna in the CATR. Level is swept down until PUSCH throughput falls below 95%. The level at which this happens (expressed as EIS in dBm/m²) is the sensitivity.
EIS = EIRP of source − path gain + DUT sensitivity angle correction
Measured in beam peak direction
Equivalent to conducted: −69 dBm for Wide Area BS
This is the single hardest OTA test to pass — any beamforming loss, PA noise leakage, or antenna inefficiency shows up directly as degraded EIS.
§7.3 — OTA Dynamic Range
OTA receiver dynamic range
Tests the RU can receive correctly when a strong in-band signal is present simultaneously. AGC must handle the level difference. Measured OTA with wanted signal and interferer both transmitted from the CATR.
§7.4/7.5 — OTA ACS/IB Blocking
OTA in-band selectivity and blocking
ACS: wanted signal + adjacent channel interferer transmitted simultaneously from different angles (DFF chamber) or same angle (CATR). RU must correctly receive the wanted signal at 95% throughput.
Wanted: fm at REFSENS + 3 dB
Interferer: +16 dBm above wanted, ±1 channel offset
§7.6 — OTA OOB Blocking
OTA out-of-band blocking
Strong CW interferer well outside the operating band. Tests the RU receiver front-end filter rejection. If the filter is inadequate, the interferer desensitizes the LNA or saturates the ADC.
§7.7 — OTA Rx Spurious
OTA receiver spurious emissions
The RU receiver can itself radiate spurious signals via the antenna (LO leakage, oscillator harmonics). These must be below specified absolute limits. Unique to OTA — the antenna is radiating these spurious signals into free space.
§7.8 — OTA Rx Intermod
OTA receiver intermodulation
Two strong interferers at f1 and f2 create an intermodulation product at 2f1−f2 that falls on the wanted channel. Tests RU receiver front-end IIP3. Critical for deployments near existing base stations on adjacent bands.

PA efficiency test plan — 5-band AAU, Dynamic Vdd

PA efficiency test method:
Measure DC input power (V × I) and RF output power simultaneously. Efficiency = P_RF_out / P_DC_in × 100%. Test at: rated power, 3 dB backoff, 6 dB backoff. Repeat with Dynamic Vdd enabled and disabled. Expected: Dynamic Vdd improves average efficiency by 10–15 percentage points at 6 dB backoff.
Dynamic Vdd step configuration:
Vdd steps are configured in the PA_VDD_TABLE register. Each step corresponds to an output power range. Number of steps and threshold power levels are configurable. More steps = smoother efficiency curve but more switching transients. Typical: 4–8 steps from minimum Vdd (low power) to maximum Vdd (rated power).

Measurement procedure (B1B3 example)
Vdd_Nominal = 40 V: Measure ACLR/EVM/Tx Power at 100%, 50%, 30%, 0% occupancy — this is the reference.
Vdd_Low1 = 32 V, Occupancy = 50%: Compensate CFR and adjust Tx power via DAC Current to match 40 V reference. Measure 50%, 30%, 0% occupancy.
Vdd_Low2 = 25 V, Occupancy = 50%: Same — compensate CFR + DAC, measure all occupancies.
For each Vdd point: measure current from main PSU (−48 V), PSU #1–3, DC-DC converters (via CB-MCU). Calculate drain efficiency = RF power out / DC power in.
Also measure: temperature sensors (FHGW / RFFE / Common-Board). Verify ACLR/EVM stay within 3GPP spec throughout all Vdd transitions.
What the measurements prove
Beamforming gain verification: at coherent phases across all elements, verify ~+12 dB gain for B1/B3/B41 (12-element arrays) and ~+6 dB for B8/B28 (6-element arrays) relative to single PA TX power. This is the antenna array gain in action — phase alignment across all branches producing constructive interference in the beam direction.

FHGW embedded RCT — standalone UL test, CLI commands

FHGW standalone mode:
FHGW can run a subset of RCT without full DU connection. In this mode: FHGW generates its own timing, enables RU RF, configures EXM via SCPI, reads get_rssi, and compares against embedded limits. Useful for: initial hardware bring-up, field deployment without full lab setup, quick smoke test.
Key CLI commands in FHGW mode:
fhgw_rct start --band B1 --bw 10M: starts embedded RCT for B1.
fhgw_rct status: shows current test progress.
fhgw_rct results: prints PASS/FAIL per test case.
fhgw_rf_enable B1: enables B1 RF path.
fhgw_exm_set --freq 1950e6 --power -95: configures EXM.
Why it exists
Traditional UL RCT needs: DU + PHY Docker + FHSRV Docker + RU + signal generator + grandmaster + networking. The embedded RCT removes everything except the RU and signal generator. One CLI command. Catches RX-chain regressions at the box level, fast, before DU integration.
Prerequisites
FHGW with embedded RCT firmware image (includes ru-ulsim and ru-dvt-cli)
Signal generator with 3GPP FRC waveforms (A1-3, A3-x, A5-x at target bandwidth)
RF cabling from signal generator to target antenna port
NO DU required · NO external test PC required for execution · NO external test scripts

Constellation diagram diagnosis — reading IQ impairments

Constellation shape → root cause:
Tight clusters at ideal points: excellent EVM, all good. Spread/fuzzy clusters: phase noise (LO quality) or thermal noise (SNR too low). Offset from grid: DC offset / LO leakage. One axis compressed: IQ amplitude imbalance. Grid rotated: IQ phase imbalance. All points compressed inward: PA compression (DPD failure or over-driven). Asymmetric spread: phase noise on one sideband (LO filtering issue).
EVM floor — what sets it:
Phase noise: LO quality sets the irreducible EVM floor regardless of SNR. Better SNR will not improve EVM once phase-noise-limited. Quantisation: 12-bit ADC SQNR = 74 dB → EVM floor from ADC ≈ 0.02% (negligible). Nonlinearity: P1dB compression → EVM increases sharply. At rated power with DPD: EVM < 3% typically. Without DPD: EVM > 10%.
▶ Watch: Interpreting Constellation Diagrams (YouTube) — covers how to diagnose signal impairments from the IQ scatter plot. Here is everything the video teaches, applied to your EXM and RU work.
What a constellation diagram is
A constellation diagram plots received IQ samples as dots on a 2D plane. The ideal symbol positions are shown as reference points (circles or crosses). Every received sample should land exactly on an ideal point. The spread, shape, and position of the cloud around each ideal point tells you exactly what is wrong with the signal.
How to read it on your EXM
On the E6640A EXM: Meas → EVM → Display → Constellation. You see all received symbols as dots. Perfect signal: tight clusters at each constellation point. Impaired signal: clouds, rings, rotations, or asymmetric spreads.

EVM floor breakdown (what limits your minimum EVM)
Total EVM² = EVM_noise² + EVM_phase² + EVM_IQ² + EVM_BFP² + EVM_DPD² EVM_noise: from thermal noise and receiver NF EVM_phase: from LO phase noise (at subcarrier offsets within channel BW) EVM_IQ: from IQ imbalance (gain + phase mismatch) EVM_BFP: from BFP compression in eCPRI fronthaul (~0.1–0.3%) EVM_DPD: residual from imperfect DPD model Practical floor: a perfectly calibrated system still has ~0.3–0.5% EVM from noise + BFP alone. What ACLR actually measures (the physics)
When a PA amplifies an OFDM signal, its nonlinearity creates intermodulation products. These fall at frequencies outside the original channel — in the adjacent channels. ACLR measures how much power leaked out: it is the ratio of the power in the adjacent channel to the power in the main channel, expressed in dBc (negative = adjacent is quieter). Higher dBc value = less leakage = better.
ACLR = 10×log₁₀(P_adjacent / P_carrier) [dBc, always negative] 3GPP limit for LTE Wide Area BS: E-UTRA offset (±1 carrier BW): ≥ 45 dBc UTRA offset (5/10 MHz offset): ≥ 50 dBc PW internal gate: typically 54–55 dBc (tighter than 3GPP)

Spectrum analyser deep dive — FFT, RBW, VBW, dynamic range

RBW — Resolution Bandwidth:
RBW sets the width of the IF filter. Narrow RBW = fine frequency resolution, slow sweep, lower noise floor. Wide RBW = coarse resolution, fast sweep, higher noise floor. Rule: RBW ≤ signal bandwidth / 100 for spectrum mask tests. For ACLR: 100 kHz RBW (standard LTE measurement). For power: 1 MHz RBW OK. Never use RBW wider than the signal you are measuring.
VBW — Video Bandwidth and trace averaging:
VBW averages the detected power over time — reduces trace noise but does not affect measurement accuracy. VBW < RBW: smooth trace but slower. VBW = 3×RBW: typical for signals. VBW >> RBW: use for CW carriers. For noise floor measurements: reduce VBW to average out noise and see the true noise floor level clearly.
DANL — how to find the true noise floor:
DANL (Displayed Average Noise Level) is the EXA noise floor in dBm in the current RBW. DANL_total = DANL_per_Hz + 10·log(RBW). With preamp ON, 1 Hz RBW: DANL ≈ −130 dBm/Hz. At 100 kHz RBW: DANL = −130 + 50 = −80 dBm. If your signal is near this level, EXA is measuring its own noise — turn on preamp or narrow RBW. Your RX chain noise floor at 10 MHz BW: −98.25 dBm — well above EXA DANL.
▶ Watch: Understanding Spectrum Analyzers (YouTube) — FFT, RBW, dynamic range. Here is the complete teaching from that video.
How a spectrum analyzer works internally
A modern spectrum analyzer (your EXA N9010B) is a swept heterodyne receiver combined with an FFT engine. The signal is downconverted to IF, filtered (RBW filter), detected (RMS power detector), and the result plotted as power vs frequency. Modern instruments also do FFT-based analysis for speed.
RBW — the most important setting to understand
RBW (Resolution Bandwidth) = bandwidth of the IF filter before detection Effect on noise floor: Noise floor (dBm) = DANL + 10×log₁₀(RBW_Hz) EXA DANL ≈ −163 dBm/Hz (with preamp ON) RBW = 1 MHz: Noise floor = −163 + 60 = −103 dBm RBW = 100 kHz: Noise floor = −163 + 50 = −113 dBm ← ACLR standard RBW = 1 kHz: Noise floor = −163 + 30 = −133 dBm ← spurious search RBW = 100 Hz: Noise floor = −163 + 20 = −143 dBm ← phase noise meas
Narrower RBW = lower noise floor = can see weaker signals AND spurs. But narrower RBW = slower sweep (sweep time ∝ span/RBW²). For ACLR: 3GPP mandates 100 kHz RBW to match the integration bandwidth correctly. Using wrong RBW changes ACLR reading by exactly 10×log₁₀(RBW_used/RBW_correct).
VBW — Video Bandwidth (trace smoothing)
VBW is a post-detection filter that smooths the displayed trace. It does NOT change the noise floor — it only averages the noise fluctuations visually. Rule: VBW ≥ RBW always. Setting VBW < RBW suppresses noise peaks that could actually be real spurs — dangerous for spurious emission tests.
Dynamic range of a spectrum analyzer
Dynamic range = displayed range you can measure simultaneously without errors Limited from below: DANL (noise floor) — sets the minimum detectable signal Limited from above: mixer compression — too strong input causes clipping, false spurs Practical dynamic range: EXA with 30 dB attenuator: ≈ 70–80 dB simultaneous range EXA with 0 dB attenuator + preamp: ≈ 80–90 dB range but compression at −30 dBm input For ACLR of 55 dBc: if carrier = −15 dBm at EXA input, adjacent = −70 dBm Need noise floor below −70 dBm → use RBW 100 kHz → floor ≈ −113 dBm ✓
Sweep time — the trade-off
Swept analyzer sweep time ≥ k × Span / RBW² k ≈ 2 for most analyzers Example: Span = 100 MHz, RBW = 100 kHz → min sweep time = 2 × 100e6 / (100e3)² = 0.02 s = 20 ms Example: Span = 100 MHz, RBW = 10 kHz → min sweep time = 2 s (100× slower!)
Zero Span mode — time domain at one frequency
Setting Span = 0 Hz converts the spectrum analyzer into a power-vs-time recorder at one fixed frequency. Used for: viewing TDD frame structure (DL on, UL off), measuring PA switch-on transient, seeing DPD convergence in real time. Critical for B41 TDD debugging.
Noise figure of the spectrum analyzer itself
EXA N9010B typical DANL: Without preamp: −135 dBm/Hz (NF ≈ 39 dB — too noisy for sensitivity testing) With preamp: −163 dBm/Hz (NF ≈ 15 dB — usable for Rx sensitivity) For REFSENS test (−69 dBm in 10 MHz): Signal at EXA ≈ −69 − cable_loss dBm Need noise floor well below signal → always use preamp for Rx tests
The −174 dBm/Hz figure: this is thermal noise at room temperature (290K) — kTB where k=1.38×10⁻²³ J/K, T=290K, B=1 Hz → kT = 4×10⁻²¹ W = −174 dBm. Every 3 dB increase in temperature adds 3 dB to this floor. Every 10× bandwidth increase adds 10 dB. This is the absolute physical minimum noise any receiver can ever achieve.

RF engineering topics — signal chain, IQ, mixers

Signal chain mental model:
Every RF system is a chain of blocks: source → TX chain (gain up) → channel (loss) → RX chain (amplify) → ADC. dB rule: track power level through chain by adding gains (+) and losses (−) in dB. Noise figure accumulates — dominated by first lossy/noisy element. Dynamic range: difference between maximum signal and noise floor. Design goal: maintain signal > noise floor through entire chain from source to ADC.
IQ representation — why everything is I+Q:
Any narrowband RF signal can be written as: s(t) = I(t)cos(2πft) − Q(t)sin(2πft) where f is carrier frequency. I and Q capture full amplitude and phase information. Demodulation: multiply received signal by cos(2πft) and sin(2πft), low-pass filter → get I and Q separately. All modern radio systems — LTE, 5G, WiFi — use IQ representation internally. EXM generates IQ waveforms. EXA demodulates to IQ for constellation display.

The complete receiver signal chain — component by component
Antenna → Duplexer/Switch → BPF (image reject) → LNA → BPF (channel select) → VGA → Mixer+LO → BPF (IF/baseband) → ADC → DSP. Each stage has a specific job and adds specific impairments. Understanding this chain is the foundation of every RF test you run.
Why component ORDER in the chain matters so much
System NF dominated by FIRST stage (Friis): NF_sys ≈ NF_1 + (NF_2 − 1)/G_1 + ... Put a 3 dB attenuator BEFORE the LNA: NF_sys = 3 + (NF_LNA − 1)/0.5 ← the attenuator's loss is added directly If LNA NF = 2 dB, G = 20 dB: With attenuator: NF_sys ≈ 3 + (1.58−1)/0.5 = 3 + 1.16 = 4.16 dB Without attenuator: NF_sys ≈ 2 + tiny = 2.01 dB → The 3 dB attenuator before LNA costs 2.15 dB in system NF = significantly worse sensitivity
IQ architecture — how direct conversion works
In a direct-conversion (zero-IF) receiver, the LO runs exactly at the carrier frequency. Two mixers multiply the RF signal by the LO and by the LO shifted 90°, producing the I (in-phase) and Q (quadrature) baseband components. These are the two outputs of the ADC — both are needed to recover amplitude and phase information.
RF input: A·cos(2π·f_RF·t + φ) LO_I: cos(2π·f_RF·t) LO_Q: sin(2π·f_RF·t) ← 90° shifted I output = A·cos(φ) ← amplitude × cosine of phase Q output = A·sin(φ) ← amplitude × sine of phase From I and Q: amplitude = √(I²+Q²), phase = arctan(Q/I)
How IQ data relates to RSSI and dBFS
RSSI from IQ samples: P_IQ = (1/N) × Σ(I_n² + Q_n²) [linear, sum of squared amplitudes] RSSI_dBFS = 10×log₁₀(P_IQ / FS²) [relative to ADC full scale] Converting dBFS → dBm: RSSI_dBm = RSSI_dBFS + ADC_offset ADC_offset = known gain from antenna port to ADC input Example: RSSI_dBFS = −44.9 dBFS, ADC_offset = +50.6 dB (RF chain gain) RSSI_dBm = −44.9 + 50.6 = −(100 - 44.9 - 50.6) ... Actual calculation uses the ADC_ADJUST table in hardware.json ADC_ADJUST accounts for: RF gain, cable loss, analog filter, ADC scale factor This is why the calibration sets a fixed CW tone and measures the offset directly

Pitfalls
• startup.xml edits that vanish. On AAU builds the startup file is regenerated at every boot from another source (CM17). If your change is gone after reboot, edit the source, not the generated file, and always verify with sysrepocfg after the reboot.
• Wrong MAC, silent failure. A wrong o-du-mac-address or cuMac/ruMac gives no error: the carriers activate and nothing flows. Compare startup.xml, ip link show and arp -n for the same port.
• Core clashes look like RF faults. L1 real-time cores shared with other pods make DL packets late at the RU, which shows up as EVM or throughput loss (CM19).
• Forgotten re-offset after a BW change leaves PRACH misaligned: the DL looks perfect and no UE attaches.
• Model string typos are accepted by the menu; the damage shows later as missing-file or unidentified-unit faults. Read the model back before upgrading.
Interview Q&A
Q: What is the minimum you check before starting L1/L2 on a freshly flashed FHGW?
A: Model string read back, firmware version in rfsoc_fru_detail, PTP "synchronized" with small offsets, the startup.xml DU MAC matching the DU port, the re-offset for the BW, and carriers active per antenna (sysrepocfg and md.l). Only then start l1 and l2 and verify with power-monitor.
Q: How do you compute the re-offset for a 15 MHz carrier without CA?
A: X = PRACH offset − N_RB/2 + 3 = 62 − 37.5 + 3 = 27.5, re-offset = 288·X − 12 = 7908. For 10 MHz: 37 − 25 + 3 = 15, giving 4308.
Q: Why are nonRtCores written as "1,33" on a 32-core server?
A: The second number is the hyper-thread sibling of the first (core + N). The same pattern gives l1RtCores 5,6,37,38. Check /opt/cpualloc.json so the L1 real-time cores are not already taken by another pod.
Q: Carriers show active and L1/L2 run, but power-monitor reads nothing. Where do you look?
A: Fronthaul addressing first: DU MAC in startup.xml, cuMac/ruMac in oammgrconfig.xml, and the physical port in vfs-data.json. Then PhyStartMode (7 for split 7.2), the library swap for flex-run, and the fhgw.log greps for TRX Carrier / DAC Channel / Fault lines.

Level 3 — the SR-IOV gate and the hardware surprises behind it
The original failure. A server with SR-IOV disabled in BIOS installed fine. Weeks later dpdk.sh wrote the VF count to /sys/class/net/<if>/device/sriov_numvfs, the write failed, the fronthaul containers never got their virtual functions, and what reached a customer was "the RRH will not come up", with nothing pointing at BIOS.

Three gates: (1) bios-precheck.sh in the installer early-commands, before the disk is touched: SR-IOV absent from BIOS aborts the install; present but disabled is staged as enabled. (2) bios-report.sh after the install reboot writes /opt/pw/rct/bios-report.json (board, BIOS version, SR-IOV value, NIC driver and firmware); a report, not a gate. (3) check-sriov.sh inside run-startup.sh, just before dpdk.sh: if disabled, enable it and reboot after a 10 s countdown, because BIOS applies staged values only at POST. A stamp file stops an endless enable-reboot loop if the BIOS silently refuses the change; it is cleared once SR-IOV is seen enabled.

Why not Redfish? Reading BIOS attributes over Redfish returned 403 "OemLicenseNotPassed": it needs a separate per-node licence, even for reads. The vendor's in-band update manager (SUM) reaches the same settings over the local IPMI KCS channel (/dev/ipmi0) with no BMC address, credentials or licence. The SUM version is pinned and checked twice at ISO build, because its licence handling changed between versions.

Why no BIOS-version gate? Approved BIOS versions are board-specific and not monotonic: on one board a newer version was "do not use" while an older one was approved. A "version at least X" check would accept forbidden firmware. Gate on the capability you need (does this BIOS offer SR-IOV), not on a version number.

Fronthaul NIC facts worth knowing on these servers: on a 4-port E810 all ports share one PTP hardware clock: the grandmaster-facing port disciplines it and the other ports act as PTP masters to the radios. Each port gets 6 VFs: VF0 is bound to vfio-pci for fh-srv, VFs 1-5 stay on iavf. fh-srv numbers RRH0..RRH3 in the order of its PCI list, not the physical port order, a classic trap when mapping radios to ports.

Interview Q&A
Q: Why does the RCT ISO always boot in Standalone mode first?
A: A factory station has no DHCP and no OAM network. A fixed link-local address on the OAM port lets a laptop on a direct cable reach the box with no configuration on either side. Lab mode is then one command, with conflict checks and rollback.
Q: A server with SR-IOV off installs fine. What breaks, and when?
A: Nothing at install time. Later dpdk.sh fails to write sriov_numvfs, fh-srv gets no VFs and the radio never comes up, with no hint at BIOS. The ISO now checks BIOS before touching the disk, reports after install, and re-checks (enable and reboot) before VF creation.
Q: Why not just check sriov_totalvfs in sysfs?
A: On this hardware it still reported 64 VFs with SR-IOV disabled in BIOS, so it would always pass. The gate reads the BIOS setting itself through the vendor tool over the local IPMI channel.
Q: How does Dual Boot avoid wiping the other OS?
A: It decides from the layout alone before writing anything: two partitions means first install (shrink the other OS to 70%, add RCT), three with RCT last means reinstall (format RCT only), anything else aborts with the disk untouched. The storage layout keeps every partition and formats only RCT.
Q: fh-srv shows RRH2 down but the radio on physical port 2 is fine. Why?
A: fh-srv numbers RRHs in the order of its PCI device list, not physical port order. Map RRH index to PCI address to port before chasing the wrong radio.

Interview Q&A
Q: Why does a PHY lab use an external loopback cable between two NIC ports instead of an internal path?

Q: fhsrv binds both VFs. What do you see and why?

Q: How does fh-srv address the RU without knowing its PCI address?

Q: What does a byte-exact IQ match with the test vector prove?

Q: Why must non-RT FHS threads stay off isolated cores?
A: They block and sleep; on an isolated RT core they delay the per-symbol threads and cause late ticks and missed symbols.

In plain English
An NB-IoT cell is not a radio of its own: it is a single 180 kHz carrier tucked into the guard band of an LTE carrier. Getting one on air end to end means getting five things to agree at once: the NB-IoT L2/L3 stack pod, the NB-IoT PHY pod (talking to the stack over the shared-memory ICC/FAPI link), the fronthaul to an O-RU whose grid has been widened to cover the guard band, an EPC, and real or simulated UEs. This card is the integration-bench view: how such a bench was assembled on a containerised vBBU (Kubernetes namespace pw), the traps that cost days (a derived RU MAC address that points nowhere, a neighbouring LTE PHY grabbing the shared fronthaul, an ICC endpoint collision), the bring-up order that works, the evidence chain that proves the cell is up, and the list of things the bench has not proven yet. The no-RF trap. Symptom: cell comes up, FAPI flows, nothing on the spectrum analyser. Cause: the configuration builder derives the U-plane RU MAC as management MAC OR 0x02 for every vNode whose RAT string is not the LTE 7.2-split string. Interview Q&A
Q: The NB-IoT cell is "up", FAPI is flowing, but there is no RF in the guard band. Where do you look?
A: The U-plane RU MAC the PHY uses. The configuration builder derives it as management MAC OR 0x02 for non-LTE-7.2 RAT strings, so NB-IoT targets a MAC that does not exist. Check the ConfigMap, the file mounted in the PHY pod and finally the FHS log line mapping DU NIC to RU MAC plus the eAxC enable mask — the FHS line is the authoritative one.
Q: Why can the neighbouring LTE PHY break an NB-IoT standalone PHY even if it carries no traffic?
A: Both would program the fronthaul server for the same RU. Per-cell xRAN set-up happens when the PHY receives CONFIG/START, so keeping the LTE PHY from ever receiving FAPI (parking it on an unused ICC quartet, or undeploying the cell) keeps it off the FHS.
Q: You restarted only the stack pod and the cell never came back. Why?
A: The stack sends CONFIG/START once at start-up and the PHY watchdog aborts when its FAPI peer disappears. Every stack restart must be followed by a PHY restart, in the order PHY first (listening on ICC), then stack.
Q: Is "2/2 Running" enough to say the PHY is healthy?
A: No. The bench saw a Running pod with a dead PHY application. Use the evidence chain: S1 up, ~2400 FAPI packets/s, a cell-activate ACK in the log DB and, if needed, the ICC handshake trace through SLOT and DL/UL config.
Q: Initial access works 100 % but ping works only ~21 % of the time. What would you suspect?
A: Connected-mode RACH: contention resolution with a C-RNTI MAC CE in Msg3 failing ~95 % of the time, so UL grants starve. It is a different code path from initial access, which is why one works and the other does not.

Level 3 - The ID-length trap: teach the maths, not the screen hint
What the source guide says (do not copy): it tells you to enter a "14-bit gNB ID, 1-16383", or a "4-bit gNB ID, 1-15" when the gNB ID length is 32, and a "PCI from 1-503". Those statements mix up the two halves of the cell identity and borrow an LTE habit. The correct rules are:
  • NR Cell Identity (NCI) is 36 bits = gNB ID (left-most L bits, L = gNB ID length, 22 to 32) + local cell ID (the remaining 36 - L bits). NCGI = PLMN + NCI.
  • With length 22 the gNB ID can use 22 bits and the cell ID gets 14 bits (0-16383). With length 32 the gNB ID gets 32 bits and only 4 bits (0-15) remain for the cell ID. The "14-bit / 4-bit" numbers describe the cell-ID part, not the gNB ID.
  • So the DU field "cell ID 1-16383" is only valid when gNB ID length = 22. Raise the length and the cell-ID range shrinks - a value that fit before may silently overflow into the gNB ID bits.
  • NR PCI range is 0-1007 (3 x 336). 0-503 is LTE. Keep PCIs unique among neighbours (no collision / confusion), and plan mod-3 for SSB/PSS separation.

In plain English

Level 3 — what integration proved, and the traps
Core availability is the real blocker for 2G. The in-house LTESIM core had no media gateway (signalling-only voice), one commercial core supported only the EFR codec, and the Amarisoft core has no 2G at all. End-to-end 2G voice with AMR therefore needs a real or third-party core — plan for it before promising codec tests (see G2FEAT01 for the AMR test matrix).

Bring-up traps: a cluster that only succeeded after a retry can show vBSC pods that are created but never reach Running — re-create rather than debug; the node OS image without the hook files never boots; routes are needed both ways between the vBSC core subnet and the core-sim subnet; development milestones went CS signalling with simulators → CS call with UEs on the same 2G vNode → CS handover → PS with data, which is also the sensible test order.

CPA integration results (4G, release 7.1): a 32-core server ran 3 dual-cell vNodes (6 cells) on one shared PHY cluster with two CPAs; a 14-core server ran one dual-cell vNode with one CPA; core = an Amarisoft EPC. Findings worth remembering:
  • Intra-vNode handover went over X2AP; intra-CPA inter-vNode and inter-CPA handovers went over S1AP (via the MME). In 7.1 the X2 set up between two CPAs was used only for neighbour-table (NRT/ANR) updates, not for handover.
  • UE-based ANR (UE reports the neighbour eCGI → NRT updated) worked in every case — but one build wrote the neighbour PLMN as 000-00 into the NRT, and MeasObject was sent three times instead of once. Always read the RRC reconfiguration and the NRT, not just the HO success counter.
  • Alarms checked end to end: VBBU_DISCONNECTED, LTE_CELL_DOWN, TASK_RESTART, ENODEB_DETECTED_PCI_CONFUSION, MME_S1_DOWN, CWS_X2_DOWN, ALARM_S_PLANE_INACCURATE_PACKET raised correctly; SYSTEM_MAX_CRASH_THRESHOLD_REACHED did not clear itself (a bug).
  • Also passed: MSS clamping, S1-Flex with three MMEs in a pool, MOCN roaming on a single core. VoLTE was not yet working in that drop.
  • Scale plan: CPA as device under test with UniPerf, up to 6 vNodes and 1000 UEs attach/detach.
Interview Q&A
Q: What are the two core-facing interfaces of a BSC and what runs on each?
A: A towards the MSC for CS voice/SMS — BSSAP over SCCP, here carried by SIGTRAN M3UA over SCTP; Gb towards the SGSN for packet data — BSSGP over the Network Service layer, here NS over UDP/IP.
Q: Why does the vBSC need an NRI length and a null-NRI?
A: With MSC/SGSN pooling (A-Flex/Gb-Flex) the BSC reads NRI bits from the TMSI/P-TMSI to route a subscriber to the MSC/SGSN that owns it. The length must match the core configuration; the null-NRI is used for load re-distribution (offloading a pool member).
Q: Pods are Running but CS calls fail at the A interface. What do you check?
A: SCTP association to the MSC M3UA port, M3UA ASP state, matching routing context and point codes (vBSC SCCP network vs MSC peer), network variant (ITU), the MSC pool NRI settings, and that the MSC zone LAC matches the cell LAC. Then routes between the core subnet and the core.
Q: In the CPA integration, why did inter-vNode handovers go over S1 rather than X2?
A: In that release X2 between CPAs was only established for neighbour-relation updates; handovers between vNodes on different CPAs (and between vNodes of the same CPA) were executed as S1 handovers through the MME. Only intra-vNode HO used X2AP.
Q: Why can you not test 2G AMR voice end to end on just any core?
A: Because the core must include a media gateway and support the codec: the simulator lacked a MGW, one core supported only EFR, and the Amarisoft core has no 2G. A full-featured 2G core is a prerequisite.

Level 3 — lab build notes and pitfalls
  • OpenStack lab build (five VMs: HNG, LTESIM, ACS master, IOND/stats worker, ACS worker): bring all VM interfaces up before creating the Kubernetes cluster for the ACS, or cluster creation fails; disable port security on the private networks, otherwise OpenStack drops traffic from the many secondary addresses the pods use. Verify with kubectl cluster-info and kubectl get nodes -o wide.
  • Serial naming is functional: the vNode serial is derived from the vBBU serial with an instance and RAT suffix; a typo creates an orphan device that never receives configuration.
  • LAC:RAC / SAC must match what the emulated MSC / SGSN expects for the HNG peer (RNC ID, LAC, SAC, RAC, PLMN) — a mismatch shows up as location-update or attach rejects, not as a cell-down.
  • Scrambling code planning: with two lab cells on the same UARFCN both on PSC 1 the UE cannot distinguish them; give neighbouring lab cells different PSCs.
  • Stats: the IOND stats application on the worker node keeps its logs under the platform log directory; use it for PM counters such as the IRAT handout counters in IRAT34G01.

In plain English
A vBBU is not one program on one server any more - it is a set of Kubernetes pods (BBU, vNodes for the stack, phynodes for PHY, netcon for backhaul, XDB, resource manager and more) running on a single bare-metal worker. Most of the time you never touch Kubernetes; the SMO deploys everything. But in the lab, when a cell does not come up or a pod keeps restarting, you need to know where each pod writes its logs on the host, which container inside a pod to look at, what deleting a pod really does, and a few traps that look like software bugs but are actually a full disk or a lost firewall rule. This card is that field guide. Platform tuning (CPU isolation, huge pages, SR-IOV) is in CM29; FOCOM-based bring-up is in CM39 and NR5GUP01.
Where a vBBU pod's logs end up
The sidecar forwards each pod's syslog to a per-pod directory on the host, so most log reading needs no kubectl exec at all.
Level 1 - Core facts: pods, containers and the host log tree
  • All PW pods run in one namespace (pw on current releases; very old StarlingX-based builds used a longer name). Each pod = main container + rsyslog sidecar, sometimes an init container (e.g. dependency-wait) that blocks until its dependencies are up.
  • kubectl logs <pod> without -c is ambiguous for a multi-container pod - always name the container: main container for application stdout, sidecar for syslog forwarding problems, init container when a pod is stuck in Init.
  • Deleting a pod is a reset, not a removal. The Deployment recreates it at once (with a new name suffix). To really remove a pod, undeploy it from the SMO/PWDS (preferred) or uninstall the helm release.
  • helm list -A shows every chart in use; helm list -n pw shows the PW release and its version - the quickest way to see what is actually deployed.

Level 2 - How to debug: crash-loop order, one-liners, IP budget

Crash-loop triage order (CrashLoopBackOff, constant restarts, containers not Ready):

  1. kubectl describe pod - the Events section (image pull errors, failed mounts, OOMKilled, probe failures, unschedulable).
  2. The host messages file for that pod - survives restarts, so it holds the run that crashed.
  3. The container log with -c; add --previous to see the last crashed instance.
# resolve a pod by substring, then act on it
pod_str="vnode01"; pod=$(kubectl -n pw get pods | grep $pod_str | awk '{print $1}')
kubectl -n pw describe pod $pod            # read the Events section first
kubectl -n pw logs $pod -c stack --since 5h  # main container (phy: -c phy, bbu: -c bbu-container)
kubectl -n pw logs $pod -c rsyslog-container --since 5h
kubectl -n pw exec -it $pod -c stack -- bash

# from the host, without entering the pod
sudo grep <STRING> /var/log/pw-share/pods/stack/vnode01/messages
sudo tail -f /var/log/pw-share/pods/stack/vnode01/messages

# inside the stack container
cat /opt/pw-share/uniRanConfig.ini          # stack configuration actually in use
tcpdump -nni any port <port>               # watch one interface/port
cat /etc/*release                           # which OS base image this pod runs

Base OS can differ per pod. During OS migrations some pod images moved to a newer Ubuntu base while others stayed on the older CentOS base for a release, so tools and paths inside pods may differ - check with cat /etc/*release rather than assuming.

Testing a private build in the BBU pod (older K8s releases): on the host create the BBU pod's rpm/ directory under the pod share, drop the RPMs there with an rpmlist file (dependencies first), add a .debug marker and an entry script, then delete the BBU pod. On restart it enters debug mode, installs the RPMs and runs the script. Remove the marker afterwards or every restart keeps the private build.

IP budget for a legacy single-server EKS-A site: at least 5 addresses (host OAM, Kubernetes control plane, Tinkerbell provisioning, BBU, XDB) plus one per vNode - a 4G/2G site with 3 vNodes needs 8. A 5G CU+DU site needed 7 on early releases and 9 from release 7.1 (extra addresses for the common VCL network, CU GTP-U and DU GTP-U). Reserve gateway and switch-management addresses on top.

Level 3 - Expert detail: two RCAs and the SMO migration

RCA 1 - PHY core dumps fill the disk.

SymptomKubernetes/EKS-A system pods in Unknown / ContainerStatusUnknown, PW pods misbehaving
Evidenceroot filesystem at 84 %; du -ckh showed 173 GB under the PHY node's crash directory
Cause530 PHY core files of about 380 MB each, written a few seconds apart by a crash-looping PHY
Recoveryfind the big directory with du -ckh -d 1 from /, delete the cores, reboot, then undeploy all pods and redeploy them one by one

Lesson: a disk that is "only" 84 % full can still break Kubernetes, because the kubelet starts evicting and failing pods based on free-space thresholds well before 100 %. During soak and stability runs, monitor the crash directory size and the number of core files as a test metric - a growing count is itself a failure, and it will eventually take down unrelated pods.

RCA 2 - the silently missing firewall rule. A boot script added iptables rules (drop TCP 80, drop/reject syslog UDP 514) while other services were also calling iptables. Without -w, iptables fails immediately if another process holds the xtables lock - so on some boots the DROP rules were simply not there, with nothing obvious in the logs. Fix: add -w 5 (wait up to 5 s for the lock) to every iptables call, check the script with bash -n, reboot, and verify the rules with iptables -S. Test lesson: verify security rules after every reboot in a loop, not once.

Moving a server to a new SMO (legacy EKS-A flow): undeploy all PW pods (helm delete pw -n pw), re-initialise the worker from the same admin server that installed it, change the SMO address (docker, helm and web URLs), re-run the configure step (RT kernel, VFs, MTU, huge pages, CPU isolation) and wait for the reboot, then upload the images to the new SMO's registry and recreate the vBBU and vNodes in the new ACS.

Pod never comes up after deployment: usual causes are a missing BBU/vNode entry in ACS, wrong core/gateway configuration, or a deployment request that has to be resent.

Interview Q&A
Q: A vNode pod is in CrashLoopBackOff. What are your first three steps?
A: kubectl describe pod and read Events; read the pod's messages file on the host under /var/log/pw-share/pods/stack/vnodeXX; then kubectl logs with -c for the main container, using --previous for the crashed instance.
Q: You deleted the vnode01 pod to remove it, but it is back. Why?
A: The pod is owned by a Deployment, which recreates it immediately - deletion acts like a reset. To remove it, undeploy from the SMO/PWDS or uninstall the helm release.
Q: Why do PW pods have an rsyslog sidecar and why does it matter for debugging?
A: The sidecar forwards each pod's syslog to a per-pod file on the host, so logs survive pod restarts and can be read without entering the pod. If those files stop growing, check the sidecar container, not the application.
Q: System pods go Unknown on a vBBU server. What non-software cause do you check?
A: Disk space - in one case a crash-looping PHY wrote 530 cores (173 GB). Use df and du -ckh -d 1, clean the crash directory, reboot and redeploy.
Q: Why can a boot script's iptables rule be missing on some boots only?
A: Concurrent iptables calls compete for the xtables lock; without -w the losing call fails immediately. Adding -w 5 makes it wait for the lock.
HNGOPS01 Running an HNG gateway pair — side-by-side releases and boot priorities, config backup/restore, ISO reinstall and OpenStack stack upgrade, HA cluster create/status/switchover Docs click to expand ▾
In plain English
HNG01 explains what the HetNet Gateway does and which show commands tell you whether calls flow. This card is the operations side: how software releases are installed and switched, how configuration is saved and restored, how a node is reinstalled or an OpenStack deployment is upgraded, and how two gateways are joined into an active/standby HA pair.

Three ideas make the HNG different from an ordinary Linux server:
  • Several releases live side by side. Installing a new release does not run it. A boot-option table decides which release (and which saved configuration) starts at the next reboot – and keeping an older entry as a fallback is your safety net.
  • The system is “closed”. Everything is meant to be done from the gateway CLI (ConfD-based, SSH on a non-standard port, jailed home directory), not by editing files or restarting services from bash.
  • One configuration file serves both nodes. Each node carries a tag (primary or secondary) and applies only the parts of the config written for its tag; floating addresses live only on whichever node is active.
For a radio test engineer this matters whenever the HNG in a lab is upgraded, rebuilt or switched over in the middle of a test campaign: knowing these steps prevents losing certificates, MAC-dependent licences or the whole HA pair. Related: HNG01 (functions and CLI), PKIBH01 (gateway certificates you must back up), VBSC01 (2G controller on the same platform family).

Level 2 — the procedures
A. Switch to a new release (the standard MOP).

system software releases                                              # 2 new release installed?
system boot-option add priority 0 release  use-backup /pre-upgrade.tgz
system boot-option add priority 1 release  use-backup /pre-upgrade.tgz   # fallback!
system boot-option list
system reboot
# after boot: verify with show commands, then take a fresh backup and point the
# boot option at it (an automatic config up-conversion happens in memory only)
B. Binary-only upgrade: system software install file-url <sftp or file url to the .bin>, then reboot both active and standby.

C. Image upgrade on OpenStack (VM deployment): back up the config to another machine → openstack stack delete <stack> → openstack stack create <stack> -t <main-template>.yaml -e <environment>.yaml with the new image → when both instances are up, restore the backup on active and standby (or set it as use-backup at priority 0) → system reboot.

D. Bare-metal reinstall from ISO (e.g. moving to a new base OS):
  1. Copy off the saved config directory, all of /etc/cert (gateway factory and operational certificates – see PKIBH01) and the boot-config directory; record ip link show so you know the old interface names and MACs.
  2. Mount the ISO as a virtual drive in the server's out-of-band console (iLO-type) and power-cycle; the install is zero-touch and reboots into an unconfigured system.
  3. From the console give the OAM port an address, restore /etc/cert and the config backups, and set the boot option (same release + restored config at priority 0) on both nodes.
  4. On the second node run system nodetag secondary (it reboots); reboot the first node at the same time – both come up and re-form the cluster.
E. Create an HA pair. Give each node a redundancy interface on a private per-cluster network (in VMs an internal/host-only network – never a shared lab LAN), set NTP, configure the full network on the primary and only the redundancy interface on the secondary, then on each node: 
system cluster create preferred-role primary   self-ipaddr  peer-hostname  peer-ipaddr    # node A
system cluster create preferred-role secondary self-ipaddr  peer-hostname  peer-ipaddr    # node B
# later releases: config mode  system cluster node primary|secondary interface  ; admin-state enabled
system cluster status        # both nodes Online, one Master one Slave, floating-IP resources Started on master
show redundancy status       # node ACTIVE/STANDBY, last transition, switchover count, per-task state
show confd-state ha          # master on active, slave on standby
show running-config          # on standby: proves config replication
Then load the application config on the primary only, back it up and make it the boot-option config – otherwise the pair is not re-created correctly after a reboot.

F. Switchover tests. Kill an individual task on the active node (it restarts and pulls its check-pointed state from the peer task); stop the gateway service on the active node, or stop the active VM – the standby must be promoted. After each event: switchover count incremented, floating addresses moved, SCTP peers re-established towards both radios and core (HNG01).

G. Dissolve the pair: first point the boot option at a non-HA configuration, then run system cluster destroy on both nodes (it reboots).
Level 3 — behaviour rules and pitfalls
  • Upgrade both nodes together. ConfD replication requires identical data models on active and standby; a pair running different releases may not replicate or may refuse to form.
  • Which change goes where. Port parameters and VLANs are applied locally and mirrored to the standby. Interface addresses and routes are applied only on the node whose role matches the entry's system-role / node block. Floating addresses exist only on the active node.
  • Adding a port flushes it. When a network port is added to the gateway config, every existing address on it – and every route via it – is removed. If the management port gets its address by DHCP, leave it out of the gateway configuration or you will cut your own session.
  • Ports are explicit. Later releases stopped auto-discovering NICs; each port must be listed per node, which also allows different port names on the two machines.
  • Config up-conversion is in memory only. When a newer release boots with an older backup it migrates the config at runtime but does not rewrite the file – take a new backup straight away. HA settings created with old action commands were not stored in the config DB and must be re-created by hand.
  • Tag changes need a reboot so the previously applied node config is cleaned up; the reboot is triggered automatically.
  • Do not manage the service from bash. Starting or stopping it outside the CLI also starts/stops the cluster stack and can force a switchover; files copied manually into the config store may not be read in future releases. A hidden debug shell exists for emergencies only.
  • Lab VM sizing. The DPDK fast path reserves 2048 huge pages of 2 MB by default, i.e. 4 GB of hugepages, so a VM needs about 8 GB RAM. In a lab, the hidden engineering setting fastpath huge-pages 512 plus a reboot lets the gateway run in a 4 GB VM (other fast-path knobs: core-port map, EAL options, memory channels, mbuf count). Never apply lab sizing to a production node.
  • Out-of-band console and ISO install depend on a stable network path from your desktop for the whole install – a dropped virtual-media session leaves a half-installed node.
Interview Q&A
Q: You installed a new HNG release and rebooted, but the old release is still running. Why?
A: Installing only adds the release. The boot-option table decides what starts; you must add the new release at priority 0 (with a config backup via use-backup) before rebooting. Keep the old release at a lower priority as a fallback.
Q: What must you back up before reinstalling a gateway node from ISO?
A: The full configuration backup, all certificates under /etc/cert (factory and operational – otherwise IPsec peers cannot authenticate), the boot-configuration directory, and a record of interface names and MACs.
Q: How does one configuration file work on both nodes of an HA pair?
A: Each node has a tag stored outside the config DB. The config contains node primary and node secondary blocks for hostname, ports and interfaces; a node applies only the block matching its tag. Floating addresses are applied only on the active node.
Q: How would you test HA switchover in a lab, and what do you check afterwards?
A: Kill a task on the active node (state recovered from the peer), stop the gateway service, or stop the active VM. Afterwards check cluster status, show redundancy status (state and switchover count), confd HA master/slave, that floating addresses moved, and that all access- and core-side SCTP associations re-established.
Q: Why can adding a port to the gateway configuration lock you out?
A: Adding a port flushes all existing addresses and routes on it. If that port carried your DHCP-assigned management address, the session drops. Keep a DHCP management port out of the gateway config.
